# 截图读写与预览

截图识别继续使用 `Device.screencap()` 返回的内存图像，JPEG 编码时机、截图间隔和任务调度逻辑保持原样。

## 数据流

```text
设备截图 → 内存图像 → 自动识别
               ↓ JPEG 编码（仍在截图线程）
          不可变的编码数据
               ├─ 最新一帧 → /screenshot/latest → 网页预览
               └─ 写盘队列 → 写盘线程 → 历史截图

独立清理线程 → 定期清理已完成写入的历史截图
```

提交截图只复制编码后的数据并尝试入队，不创建目录、不写文件。最新普通截图立即更新到内存，特殊用途的截图不覆盖预览。图片数组后续变化不会改变待写数据。

待写截图默认最多 128 张、编码数据合计最多 64 MiB，两项限制均包含正在写入的一张。达到任一上限时，优先淘汰队列中最旧的普通或调试截图，为新截图腾出容量；已在写入的截图和 `run_order`、`workshop`、`solve_captcha` 关键截图不参与淘汰。若腾出容量后仍无法容纳新图，或单张图超过字节上限，则保持现有队列并跳过新图保存。保留下来的截图仍按提交顺序写入。

容量不足不会等待磁盘，也不会影响最新一帧的内存预览。跳过保存的截图不重试；计数记录在日志中，告警最多每 30 秒输出一次。两项上限限制的是待写编码数据，不包括额外保留的一帧预览和识别图像。

## 文件布局与清理

- 普通截图：`screenshot/YYYYMMDD-HH/<纳秒时间戳>.jpg`，每小时一个目录。
- 跑单、合成、验证码截图：保留 `run_order`、`workshop`、`solve_captcha` 目录，使用纳秒时间戳文件名，避免同一秒覆盖。跑单历史读取逻辑已经支持这种格式。
- 这三个关键目录继续各保留最近 100 张；其他调试截图按配置的保留时间清理。
- 普通旧截图不迁移、不建立旧路径映射；旧根目录里的时间戳 JPG 仍参与到期清理，避免永久残留。
- 清理线程启动时执行一次，之后每次完成后等待 30 秒再执行。因此保留时间是清理阈值，不是文件到期即刻删除的硬期限。
- 未过期的整小时目录不扫描内部文件。扫描使用迭代器，删除每 100 张短暂让出时间，不一次性加载整个目录列表。
- 写盘先写同目录 `.jpg.tmp` 文件，关闭后原子替换为 `.jpg`。清理只操作完成的 JPG，不删除非空小时目录或正在写入的临时文件。
- 写盘和清理异常会被记录，后台线程继续处理后续任务。写盘失败的该张截图不自动重试排队，避免磁盘故障时形成无限重试；排队截图在正常退出时尝试排空，最多等待 5 秒。强制终止进程不保证队列中的截图落盘。

## 网页预览

`GET /screenshot/latest` 复用服务端的 `require_token` 装饰器，按全局配置校验 token 请求头，直接返回内存 JPEG。旧的历史截图接口没有这项校验，新实时预览接口与服务端其他受保护接口保持一致。还没有截图时返回 `204`；客户端携带匹配的 `If-None-Match` 时返回 `304`，避免重复传输同一帧。

网页完成一次请求后等待 1 秒再请求，不依赖日志消息或历史文件路径。每个预览实例只进行一次请求，设置 10 秒网络超时。关闭预览、切到后台或离开页面会取消请求、清除定时器并释放 Blob URL；重新打开时立即请求最新帧。

历史文件接口 `/screenshots/<path:filename>` 仍可访问已落盘的相对路径；旧 `/latest-screenshot` 接口返回最后成功写入的普通截图路径，实时预览不再使用它。日志消息不再携带截图路径，前端同步移除已无消费者的 `sc_uri` 状态。

## 诊断

`runtime.log` 每轮清理后输出 `截图存储状态`，包含：

| 字段 | 含义 |
| --- | --- |
| `pending_count` | 待完成写入数量，包含正在写入的一张 |
| `pending_bytes` | 待完成写入的编码数据字节数，包含正在写入的一张 |
| `max_pending_count` / `max_pending_bytes` | 待写数量 / 编码数据字节数上限 |
| `saved` / `failed` | 本进程成功写入 / 写入失败总数 |
| `dropped` / `dropped_bytes` | 因容量不足跳过保存的截图累计数量 / 字节数，包含被淘汰的旧图 |
| `dropped_important` | 因容量不足未能入队的关键截图累计数量 |
| `queue_wait_ms` | 最近一张完成处理的截图排队时间 |
| `write_ms` | 最近一次写入尝试耗时 |
| `cleanup_ms` | 最近一轮清理耗时 |
| `cleanup_failed` | 清理错误累计次数 |

这些数值不包含识别图像、OCR、其他日志队列和 HTTP 请求占用的内存。持续故障的错误日志最多每 30 秒输出一次，计数逐次累计。

排查内存问题时，应同时记录进程 RSS 和这些指标。如果待写占用接近上限且 `dropped` 持续增长，应先检查存储性能；待写占用稳定而 RSS 增长，则继续排查识别及其他组件。当前日志里的“截图用时”仍包含采集与 JPEG 编码，不包含后台写盘和清理。
