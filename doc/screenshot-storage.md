# 截图读写与预览

截图识别继续使用 `Device.screencap()` 返回的内存图像，JPEG 编码时机、截图间隔和任务调度逻辑保持原样。

## 数据流

```text
设备截图 → 内存图像 → 自动识别
               ↓ JPEG 编码（仍在截图线程）
          不可变的编码数据
               ├─ 最新一帧 → /screenshot/latest → 网页预览
               └─ 写盘队列 → 写盘线程 → 历史截图

独立清理线程 → 定期清理已完成写入的历史截图
```

提交截图只复制编码后的数据并尝试入队，不创建目录、不写文件。最新普通截图立即更新到内存，特殊用途的截图不覆盖预览。图片数组后续变化不会改变待写数据。

“截图保存时间”默认 `1` 小时，用户可以自定义过期时间，已有配置值继续沿用。设为 `0` 时，日常截图（含 `run_order`、`workshop`、`furniture`、`solve_captcha`）停止写盘，实时预览照常更新；已编码画面只在内存中滚动保留最近 5 分钟，缓存最多 16 张、32 MiB；超过容量时淘汰最早的画面。出现符合条件的异常后，归档报错前 5 分钟内缓存的全部截图，以及后 5 分钟的新截图，不建立普通截图文件。设为正数可重新开启日常保存。关闭日常保存后，尚未开始写入且不在异常窗口内的排队截图会跳过，已经开始写入的一张允许完成。主动关闭日常保存不计入容量不足的 `dropped` 统计。

待写截图默认最多 128 张、编码数据合计最多 64 MiB，两项限制均包含正在写入的一张。达到任一上限时，优先淘汰队列中最旧的普通或调试截图，为新截图腾出容量；已在写入的截图和 `run_order`、`workshop`、`furniture`、`solve_captcha` 关键截图不参与淘汰。若腾出容量后仍无法容纳新图，或单张图超过字节上限，则保持现有队列并跳过新图保存。保留下来的截图仍按提交顺序写入。

容量不足不会等待磁盘，也不会影响最新一帧的内存预览。跳过保存的截图不重试；计数记录在日志中，告警最多每 30 秒输出一次。两项上限限制的是待写编码数据，不包括额外保留的一帧预览和识别图像。

## 文件布局与清理

- 普通截图：`screenshot/YYYYMMDD-HH/<纳秒时间戳>.jpg`，每小时一个目录。
- 跑单、合成、家具分解、验证码截图：保留 `run_order`、`workshop`、`furniture`、`solve_captcha` 目录，使用纳秒时间戳文件名，避免同一秒覆盖。跑单历史读取逻辑已经支持这种格式。
- 这四个关键目录继续各保留最近 100 张；其他调试截图按配置的保留时间清理。
- 普通旧截图不迁移、不建立旧路径映射；旧根目录里的时间戳 JPG 仍参与到期清理，避免永久残留。
- 清理线程启动时执行一次，之后每次完成后间隔 1 小时再清理，与最初的清理频率一致。清理继续独立于写盘线程运行；新增截图、空闲或修改保留时间均不改变清理频率。保留时间是清理阈值，实际删除可能延后约 1 小时，磁盘占用需要为这段时间内的截图留出余量。
- 保存截图开启时，普通截图至少保留 5 分钟，以便异常发生后归档此前的画面。出现符合归档条件的 ERROR 或指定 WARNING 日志时，独立归档线程把前 5 分钟的已保存截图复制到 `screenshot/errors/<首次报错时间戳>/`，后 5 分钟新写入的截图也复制进去。后续异常若与现有窗口重叠，复用同一条记录，并把截图和日志窗口延长到末次报错后 5 分钟；空档中的已保存截图会补入归档。`event.json` 记录首次、末次报错时间及次数，窗口结束后写入 `logs.json` 保存关联日志。异常归档独立于普通截图保留时间，按末次报错时间保留 168 小时（约 7 天），与每小时滚转的运行日志保留 168 份使用同一期限；清理线程启动时及之后每小时清理过期归档。用户可在“数据图表 → 日志调度”中查看或经确认后删除单条异常归档。删除会取消该记录尚未完成的截图和日志归档，不影响其他异常记录、普通截图及运行日志。截图保存时间设为 `0` 时，报错前缓存的最多 16 张截图来自内存；发生异常前不会为这些画面写盘。缓存超过数量或字节上限时，较早画面可能已被淘汰。
- 存储与后台线程都不在导入时建立，第一次提交截图时才建立；主进程启用文件日志时若已有报错归档，也会启动清理线程，避免没有新截图时旧归档长期残留。导入 `utils/log.py` 的进程（测试、开发服务器、各种脚本）不会顺带做一次全量清理。清理线程仍然按进程各建一个：多个进程同时对同一批历史截图调用 `unlink` 时，Windows 会让其中一次以 `WinError 5` 失败并记一条清理错误。
- 报错归档使用第三个后台线程；正常运行期间没有报错时它保持等待。主进程已启用文件日志后，首次符合条件的 ERROR 或指定 WARNING 也会建立截图存储并安排归档。进程重启后会从尚未结束的报错记录恢复归档窗口。
- 自动归档针对截图有助于排查的 ERROR，以及少数达到最终失败条件的 WARNING。其他 WARNING 不归档；代码可对个别日志显式关闭或开启归档。下表列出当前会触发归档的来源。

| 类别 | 会自动归档的错误来源 |
| --- | --- |
| 主运行循环 | 页面识别失败、与画面有关的运行时恢复失败、任务执行失败；ADB 未成功连接不归档 |
| 游戏场景与任务 | 基建调度、场景求解、验证码最终失败、作战、公招、玩家信息、隐秘战线相关求解器 |
| 底层画面操作 | 设备操作、场景图、图像匹配、调度任务、图像分割与通用求解器 |
| 跑单漏单 | 基建跑单读取倒计时后判定漏单；“上一个订单漏单”仅保留数据库记录和通知，历史订单回放不会触发归档 |
| 最终画面警告 | 基建连续返回 5 次仍无法识别场景、隐秘战线或生息演算持续出现未知场景、训练室倒计时与面板连续 5 次不一致、作战失败 |

配置、资源更新、数据库、邮件、网页接口等非画面问题，以及识别和验证码的中途重试、ADB 连接与恢复失败，不自动复制截图；这些日志仍照常写入 `runtime.log` 并显示在实时日志中。基建调度模块中与画面无关的 MAA 模块导入、活动关卡导航更新、周计划切换、森空岛签到和自动专精配置错误也不自动归档。
- 未过期的整小时目录不扫描内部文件。扫描使用迭代器，删除每 100 张短暂让出时间，不一次性加载整个目录列表。
- 写盘先写同目录 `.jpg.tmp` 文件，关闭后原子替换为 `.jpg`。清理只操作完成的 JPG，不删除非空小时目录或正在写入的临时文件。
- 写盘和清理异常会被记录，后台线程继续处理后续任务。写盘失败的该张截图不自动重试排队，避免磁盘故障时形成无限重试；排队截图在正常退出时尝试排空，最多等待 5 秒。强制终止进程不保证队列中的截图落盘。

## 网页预览

`GET /screenshot/latest` 复用服务端的 `require_token` 装饰器，按全局配置校验 token 请求头，直接返回内存 JPEG。旧的历史截图接口没有这项校验，新实时预览接口与服务端其他受保护接口保持一致。还没有截图时返回 `204`；客户端携带匹配的 `If-None-Match` 时返回 `304`，避免重复传输同一帧。

网页完成一次请求后等待 1 秒再请求，不依赖日志消息或历史文件路径。每个预览实例只进行一次请求，设置 10 秒网络超时。关闭预览、切到后台或离开页面会取消请求、清除定时器并释放 Blob URL；重新打开时立即请求最新帧。

历史文件接口 `/screenshots/<path:filename>` 仍可访问已落盘的相对路径；旧 `/latest-screenshot` 接口返回最后成功写入的普通截图路径，实时预览不再使用它。日志消息不再携带截图路径，前端同步移除已无消费者的 `sc_uri` 状态。

## 诊断

后台每 30 秒检查一次统计，只有写入、失败、跳过数量等状态发生变化，或仍存在待写积压时，才向 `runtime.log` 输出 `截图存储状态`。首次全零和空闲期间清理耗时的波动不会重复输出；积压与新增错误仍可观察。统计包含：

“日志调度”页面可选择时间，读取前后 5 分钟的运行日志，并按时间戳为每条日志关联之前 30 秒内最近的截图。报错列表展示单独保存的画面；运行日志仍保留原始异常栈，实时界面显示易读的错误摘要。点击“导出日志与截图”可下载当前时间窗口的 ZIP，包含完整窗口日志（`日志.txt`）、仍可读取的截图和时间范围说明。选中报错记录后会优先使用其归档日志和画面；普通截图过期后，归档画面仍可导出。下载包只包含实际已保存的文件。

| 字段 | 含义 |
| --- | --- |
| `pending_count` | 待完成写入数量，包含正在写入的一张 |
| `pending_bytes` | 待完成写入的编码数据字节数，包含正在写入的一张 |
| `max_pending_count` / `max_pending_bytes` | 待写数量 / 编码数据字节数上限 |
| `saved` / `failed` | 本进程成功写入 / 写入失败总数 |
| `dropped` / `dropped_bytes` | 因容量不足跳过保存的截图累计数量 / 字节数，包含被淘汰的旧图 |
| `dropped_important` | 因容量不足未能入队的关键截图累计数量 |
| `queue_wait_ms` | 最近一张完成处理的截图排队时间 |
| `write_ms` | 最近一次写入尝试耗时 |
| `cleanup_ms` | 最近一轮清理耗时 |
| `cleanup_failed` | 清理错误累计次数 |

这些数值不包含识别图像、OCR、其他日志队列和 HTTP 请求占用的内存。持续故障的错误日志最多每 30 秒输出一次，计数逐次累计。

排查内存问题时，应同时记录进程 RSS 和这些指标。如果待写占用接近上限且 `dropped` 持续增长，应先检查存储性能；待写占用稳定而 RSS 增长，则继续排查识别及其他组件。当前日志里的“截图用时”仍包含采集与 JPEG 编码，不包含后台写盘和清理。
