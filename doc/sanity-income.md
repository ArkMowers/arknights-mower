# 理智算法介绍

理智算法把排班演算已有的产出和消耗，按同一份材料价值表折算为日均理智收益，用于比较制造、贸易、回收、公招刷新和线索信用的综合收益。搓玉也使用这套算法，允许负净收益。

## 使用与比较

1. 在排班表中打开「计算收益」，选择「理智算法」。首次使用和恢复默认时选择此算法；已有的显式选择继续保留。
2. 在同一窗口检查材料价格、办公室潜能预设、黄票兑换预设和信用有效额度，修改后保存。
3. 使用相同价格、练度、设施等级、库存条件、预热和统计时间比较排班。随机抽单模式还应固定相同种子；单次抽样差异不等于长期收益差异。
4. 查看日均理智收益、产出与消耗，以及赤金、源石碎片的净数量。出现「部分」时先检查未估值项目。

该算法及专用估值配置仅用于排班的「计算收益」。基建报表仍默认使用原 0.23456 算法。估值不改变排班、生产、库存和无人机分配。

## 材料表与计价单位

每项收益采用以下计算方式，消耗以负数计入：

```text
日均理智收益 = Σ（日均净产出 × 单位理智价值）
```

内置材料表采用 SS 活动估值，包含活动代币价值；合成估值采用九色鹿的绿色材料联立计算、蚀清的蓝合紫固定副产品、年的紫合金随机副产品。其参数、来源和日期见[材料价值快照](../arknights_mower/data/growth_values.json)。它是离线计算表快照，不是实时获取的最新活动价格，也不是把所有材料都按常驻关卡或 1-7 定价。

实际演算使用 Mower 当前保存的材料表，用户导入和手动修改的价格优先生效。合成玉同样直接使用 @32767 提供的表中价格，内置快照为 0.9225 理智/个。修改一项材料价格不会在本地重新求解整套合成材料价格；碎片和凭证等明确列出的兑换估值会随其基础价格重新计算。

| 项目 | 净数量与单价 |
| :--- | :--- |
| 经验 | 经验产出 × 中级作战记录单价 ÷ 1000 |
| 赤金 | （制造数量 − 订单消耗）× 赤金单价 |
| 龙门币 | （订单收入 − 制造消耗）× 龙门币单价 |
| 源石碎片 | （制造数量 − 订单消耗）× 碎片单价 |
| 合成玉 | 产出数量 × 合成玉单价 |
| 固源岩、装置 | 消耗数量 × 对应单价，计为负值 |
| 回收站 | 普通生产周期数 × 单周期期望价值 |
| 公招刷新 | 刷新次数 × 每次新增黄绿票的期望价值 |
| 会客室 | 有效信用数量 × 信用单价 |

特殊订单溢价已包含在龙门币收入中，不再作为实物赤金重复计价。初始库存、预热产出和外部补入不作为新增收入。理论模式使用现有连续期望数量，抽样模式沿用选定的订单产出规则。

## 碎片与搓玉

碎片自动估值沿用赤金在普通兑换中所占的价值比例：

```text
赤金价值比例 = 赤金单价 ÷（500 × 龙门币单价）
碎片单价 = 10 × 合成玉单价 × 赤金价值比例
```

普通赤金按每个 500 龙门币，碎片按每个兑换 10 合成玉作为基准。这里是制造与贸易的价值分配约定，不表示两条生产链耗时相同，也不包含特殊订单溢价。固源岩和装置两种配方使用相同的碎片单价，各自扣除实际耗材。

可手填非负碎片单价，包括 0；清空覆盖后恢复自动估值。基础价格缺失或龙门币分母无效时，自动价格保留未估值。

日均搓玉明细分为：

```text
制造净收益 = 碎片产量 × 碎片单价 − 龙门币、固源岩、装置的消耗价值
贸易净收益 = 合成玉产量 × 合成玉单价 − 消耗碎片 × 碎片单价
搓玉合计 = 碎片净数量 × 碎片单价 + 合成玉价值 − 制造耗材价值
```

这些金额已经包含在全基建总收益中，不再额外相加。碎片产销平衡时，其中间价格抵消；产销不平衡时，结余或缺口按同一单价计入，因此比较时也要看碎片净数量。它是本次计价产出减交付消耗，可能与含初始库存、外部补入的实物余额变化不同。

以下示例使用内置快照，其他价格表应代入自己的值：

| 材料 | 理智单价 |
| :--- | ---: |
| 龙门币 | 0.0036 |
| 赤金 | 1.377792 |
| 合成玉 | 0.9225 |
| 固源岩 | 3.35648 |
| 自动推导的源石碎片 | 7.061184 |

制造 2 个碎片消耗 4 固源岩和 3200 龙门币，随后卖出换得 20 合成玉：

| 环节 | 净理智收益 |
| :--- | ---: |
| 制造 | −10.823552 |
| 贸易 | 4.327632 |
| 合计 | −6.49592 |

负数表示按当前统一价格计算，消耗资源的价值高于所得资源；合成玉产出仍为正。算法保留这一结果，不把负数截成 0，也不另外换一套搓玉权重。当前计算没有额外扣除占用设施的机会成本。

## 回收站

单个普通生产周期的价值为：

```text
普通池材料期望价值
+ 普通池平均积分 ÷ 积分门槛 × 额外池材料期望价值
```

再乘以演算产出的周期数，也可以手填单次价值。模型使用长期期望，不预测单次掉落，也不生成材料库存。当前演算未提供投入回收站用于提效的材料成本，因此不扣这部分消耗。

原手填回收站效率已移除；回收站统计及 Excel 保留固定 100% 和 10% 效率参考。

## 办公室与凭证

办公室按演算已有的刷新次数估值。单次刷新以无保底三星结果为对照，分别计算黄票和绿票增量：

```text
新增某种凭证期望 = Σ 星级概率 ×（该星级奖励 − 三星奖励）
单次刷新价值 = 新增黄票期望 × 黄票单价 + 新增绿票期望 × 绿票单价
```

潜能提供以下预设：

| 星级 | 默认：黄票／绿票 | 满潜：黄票／绿票 |
| :--- | ---: | ---: |
| 三星 | 0／10 | 0／10 |
| 四星 | 1／30 | 1／30 |
| 五星 | 5／0 | 13／0 |
| 六星 | 10／0 | 25／0 |

「当前森空岛数据估算」按本地拥有状态、潜能和当前公招池，在同星级内等权平均。未拥有按首次获得的 1 黄票处理；已拥有未满潜按三星 5 绿票、四星 30 绿票、五星 5 黄票、六星 10 黄票处理，满潜包含多余信物兑换。潜能仅近似获得次数，通用信物、未使用信物及中坚获取历史会造成偏差；缺失潜能时保留未估值。每次演算重读本地缓存，不自动远程同步。

概率使用[一图流公招标签统计](https://ark.yituliu.cn/survey/maarecruitdata)的固定快照，默认每次新增黄票约 0.202，满潜约 0.278。假设只刷新无保底标签，不模拟掉标签、无保底出高星、具体标签选择或潜能随招募改变；这些数值不是实测净收益或官方概率。刷新次数假设及时使用，不模拟存满停工。

| 凭证估值 | 单张价值 |
| :--- | :--- |
| 黄票：抽卡券 | 38 × 600 × 合成玉单价 ÷ 258 |
| 黄票：六星皇家信物 | 720 × 采购凭证单价 ÷ 135 |
| 绿票：合成玉 | 30 × 合成玉单价 ÷ 50 |

黄票预设由用户选择，不按持有量超过 258 自动切换。信物估值假设有兑换需求和可用库存；绿票忽略前置兑换。黄票和绿票单价可独立覆盖为 0；手填刷新新增黄票期望仅覆盖黄票数量，不修改绿票估计。兑换及重复获得奖励参考 [PRTS 凭证交易所](https://prts.wiki/w/采购中心/凭证交易所)。

## 会客室与信用收益递减

会客室假设自产线索全部赠送、好友持续补齐整套线索，并连续开启交流：

```text
日均信用 = 自产线索数 × 40 + 210（已建会客室）
日均信用价值 = min（日均信用，每日有效额度）× 信用单价
```

每条自产线索的 40 信用由搜集 20、赠送 20 构成；210 是连续交流的日均奖励，未建会客室不计。数量参考 [PRTS 信用说明](https://prts.wiki/w/信用)。每日免费线索、接收线索、访问和信息板奖励没有额外加入。

信用单价默认采用当前购物性价比门槛，是参考边际价值，不是实际购物平均回报。每日有效额度应扣除其他信用收入已经覆盖的需求：留空不限制，0 不计价值；先分配交流，再分配线索。例如日均产生 370 信用、有效额度 250、单价 0.2，则计入 50 理智/天。

该额度近似表达「更多信用已无用途」，不逐日模拟商店库存、折扣、材料需求和实际交流时刻。修改估值不改变购物策略或信息板按需领取行为。

## 缺价、价格更新与历史结果

- 显式填 0 表示认为该项目没有价值；留空覆盖通常表示采用自动估值。
- 非零净产出或成本缺价时，显示「部分」收益并列出未估值项目。某个环节缺少碎片价格，但完整生产链的碎片净量为 0 时，链条合计仍可能完整。
- 每次演算保存当次价格、预设和结果。后续改价只影响新演算，旧结果及其图片不会自动重算；旧结果没有新增搓玉明细时，需要重新演算。
- 材料价格与回收站统计、养成统计和信用购物共用。更新共享表会影响这些功能，但不回写历史收益。
- 新材料首次进入 SS 活动后，应以实际活动统计替换假定掉率，并重新计算受影响的九色鹿联立价格及蚀清、年的合成价格。更新需要保留活动代币、副产品概率及合成策略，记录数据日期和来源。直接替换一项价格不能保证整张表仍然一致。

完整行为边界由 [Arknights Mower 排班编辑子系统说明](../docs/subsystems/plan-editor.md#sanity-income)维护；共享材料价格的保存与导入规则见 [Arknights Mower 基建调度子系统说明](../docs/subsystems/base-scheduler.md#recycling-valuation)。
