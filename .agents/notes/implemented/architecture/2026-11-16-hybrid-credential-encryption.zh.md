# 本地凭据的混合加密

## 问题

Mower 已有配置以明文保存凭据，此次首次引入本地凭据加密。需求要求所有支持的平台都采用
X25519 与 ML-KEM-768 的混合封装，安全迁移真实存在的明文来源，并保留原有设置操作。
[配置备份子系统说明](../../../../docs/subsystems/config-backup.md#configuration-credential-storage)
负责存储、迁移与备份规则。此前没有已发布的加密凭据格式需要兼容。

## 决策

[`credential_store.py`](../../../../arknights_mower/utils/credential_store.py)
采用 `cryptography==50.0.2` 的 HPKE，组合 X-Wing（`MLKEM768_X25519`）、
`HKDF_SHA256` 与 `AES_256_GCM`。程序为所选保护方式初始化一份固定接收方私钥，
普通凭据保存复用该私钥；每次加密仍由 HPKE 生成新的封装结果和密文。

Windows DPAPI、macOS Keychain 或 Linux Secret Service 直接保护私钥。
没有桌面凭据服务的部署使用私有文件，也支持显式指定已有私钥文件。
读取时可用显式提供的同一原私钥跨保护方式恢复，同时验证原文件头和公钥标识；程序不会自动切换来源。
默认私钥由同一系统用户、使用相同存储设置的实例共享；显式选择不同私钥可隔离部署。
凭据文件只记录保护方式、公钥标识和密文，不再保存一份私钥。
HPKE 上下文将文件头与密文绑定；准确格式和平台路径由子系统说明统一定义。

固定私钥省去另一层主密钥，普通编辑也不会改变接收方身份。
初始化记录与密钥标识使私钥缺失或不匹配时明确报错，不自动创建替代私钥。
原子写入及读回验证保证失败时恢复原字节；真实明文来源只在加密目的文件写入并验证成功后清除。

## 考虑过的替代方案

本轮未提交的实现曾考虑每份凭据文件生成新私钥，再由独立主密钥保护。
该方案增加了密钥材料和生命周期职责，而项目没有已发布的加密格式需要兼容。
直接保护固定混合私钥，用更少的持久内容满足此次存储要求。

仅由平台能力直接加密凭据，无法满足所有平台采用混合封装的要求。
所选库负责 X-Wing 的组合，不由应用自行编写密码学算法。

## 后果

此次只引入一种格式，不为先前未发布的实验实现保留读取或升级路径。
已有明文配置和备份仍作为迁移来源。普通 ZIP 不包含凭据或私钥。
独立于正常配置加载的恢复入口允许用户明确重置不可读凭据，同时保留排班和其他设置。
程序保留可用私钥及可读凭据，将无法读取的旧密文另存，只有确认后才修复丢失或损坏的默认私钥。
随后用户重新启动并填写凭据。

可选的口令业务凭据备份让用户无需迁移受系统账户保护的私钥。
固定成本的 scrypt 从导出口令派生 AES-256-GCM 密钥，目标机解密备份后，
再用本机的混合私钥加密其中的凭据，访问令牌保持本机值。
备份不包含源机器私钥，也不改变本地混合加密方案。子系统说明统一定义校验、范围和回滚要求。
口令找回、日常密钥轮换和独立管理者密钥体系仍不属于本次实现。

固定接收方私钥不提供私钥泄露后的前向保密；能够读取私钥或访问其保护服务的进程可以解密凭据。
X-Wing 与名称相近的 TLS 密钥交换组不同，本次不配置 HTTPS。

[运行库说明](../../../../docs/cookbook/packaging.md#credential-encryption-runtime)
统一定义后端要求和能力检查；其中的 macOS Intel 源码编译条件与 Android Debian ARM64 部署范围同样适用。
