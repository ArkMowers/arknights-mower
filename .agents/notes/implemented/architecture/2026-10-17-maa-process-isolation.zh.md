# 桌面 MAA 进程隔离

## 问题

排查的 macOS 主机完成更新后安装了 v6.20.0-beta.1，但四个 Mower 进程仍持有已改名至备份目录的 v6.19.0 核心。连接测试使用新建子进程，因此显示已安装版本。既有[核心代次决策](../../implemented/bug-fix/2026-10-05-maa-core-generation.zh.md)阻止不安全的原生重载，但要求 macOS 重启 Mower。

## 决策

每个桌面 MAA 实例使用由 [`maa_process.py`](../../../../arknights_mower/utils/maa_process.py) 管理的新建子进程，源码和独立包采用共享工作入口。Mower 保留调度、库存记账和回调解释，通过有界本地通道转发既有实例操作和有序回调。连接前确认工作进程版本与安装身份。完成、更新、失败及父进程退出时关闭工作进程；工作进程不可用时使当前调用失败，不自动重放任务。共享安装锁协调采用该实现的 Mower 实例，独占安装与备份清理要求原生工作进程先释放共享锁。Windows 在安装前释放原生文件锁。按用户要求，Android 保留现有原生桥接及服务重启要求。

本决策部分替代旧决策的桌面激活机制，核心校验、任务准入和备份归属仍然适用。领域概念和持久化配置含义保持不变，无需修改术语表。[MAA 运行子系统说明](../../../../docs/subsystems/maa-runtime.md)继续拥有完整行为规则。

同一边界也保护共享客户端文件：Windows 使用官方安装目录互斥锁协议，macOS 在写入和清理备份前检查已映射的核心文件。[软件更新子系统说明](../../../../docs/subsystems/software-update.md#17-maa-package-validation-and-backups)规定包文件清单校验、完整包修复和安装目录内的 `.old` 备份。新工作进程拒绝加载时恢复活动导航的旧内容，布局选择及恢复规则由 [MAA 集成子系统说明](../../../../docs/subsystems/maa-integration.md#6-desktop-activity-navigation)规定。

## 考虑过的替代方案

删除 macOS 检查可以恢复以前关闭并重开动态库的尝试，但不能确认原生映像和 Objective-C 注册已释放。重启 Mower 可以实现隔离，却会中断其他调度和网页。仅隔离连接测试已经可用，但不会替换实际自动化使用的核心。

## 验证

MAA 定向离线测试通过。[工作进程测试](../../../../arknights_mower/tests/maa_process_tests.py)覆盖实际工作进程启动、有序回调、回调内修改任务参数、父子进程回调队列容量限制、任务准入、启动失败、超时、父进程管道断开、进程退出、清理、共享安装锁及版本字符串不变的核心替换。调度器测试覆盖正式桌面入口和保持原有行为的 Android 桥接；更新任务测试确认成功激活时没有重启提示。源码启动器分派与独立包启动命令分别检查。官方 macOS v6.17.0 核心的无设备检查替换核心文件后，在同一父进程下成功初始化两个工作进程。治理结构检查独立于上述行为结果通过。

## 后果

桌面更新通过新工作进程激活，无需重启 Mower 或在主进程卸载原生映像。每轮 MAA 运行增加进程启动成本。通信失败终止当前操作，不重放已接受任务。Windows 客户端互斥锁阻止写共享文件期间启动客户端；macOS 映射检查只能观察当时占用，无法阻止随后未协调的启动。既有同级备份目录保持原状。已经把核心加载进 Mower 的旧版本仍需重启一次，才能切换至隔离实现。本地未运行 Windows 原生核心、独立包或 Android 真机；离线检查不能证明这些平台结果或真实自动化行为。
