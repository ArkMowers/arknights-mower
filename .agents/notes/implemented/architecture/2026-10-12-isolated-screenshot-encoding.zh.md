# 截图编码进程隔离

[English](2026-10-12-isolated-screenshot-encoding.md)

## 问题

此前截图 JPEG 编码与设备调度处于同一主实例，原生编码器退出或挂起可能中断自动化；旧历史帧也不能阻塞更新的预览帧。既有逐快照复用规则继续适用。

## 决策

既有[共享截图编码](../../implemented/simplification/2026-09-29-shared-screenshot-encoding.zh.md)决策负责逐快照复用。本决策负责原生 JPEG 故障的独立进程边界。Python 线程无法隔离访问冲突，也无法终止挂起的原生编码器。

实现复用现有 Pillow 依赖，去除 JPEG 颜色转换时的分配。公开 `img2bytes` 的 ndarray 包装保留附件兼容性，并允许一般图片尺寸。[编码所有者](../../../../arknights_mower/utils/screenshot_encoding.py)复用一个主编码进程处理历史帧和可立即执行的预览。主进程繁忙时才启动最多一个辅助预览进程；辅助进程空闲三十秒后自动回收，即使没有新帧到来也会回收。主编码进程继续保留。只有一个串行进程而没有辅助进程时，挂起的历史帧会阻塞更新的预览。固定共享映射避免向管道写入整图，也不增加帧积压。在 Windows 10 及以后版本，编码槽位将启动器原子创建在专属的关闭即终止 Job 内，再恢复执行。内核所有权覆盖启动器后代，以及父进程在原生调用持有 GIL 时死亡的情形。最后句柄关闭即删除的映射文件也在异常终止后消失。跨平台控制通道监测线程在导入原生 Pillow 前启动，但需要取得 GIL。清理保留尚未退出的 Job，不积累替代进程。

[JPEG 进程边界](../../../../docs/subsystems/device-control.md#jpeg-process-isolation)维护完整接口说明。既有归档排空、编码近期缓存和逐帧复用规则继续适用。标准画面帧、实例绑定和实际驻员的含义保持不变，无需修改词汇表。

## 考虑过的替代方案

同进程 OpenCV 4.11 在所测环境中更快，但原生故障仍会影响主实例。两个编码进程在首次使用后一直保留可以维持预览独立推进，但空闲成本更高。Pebble 可以管理进程任务超时，逐帧共享传输、有界接纳、Windows 内核所有权和冻结入口仍需适配与验证。当前实现保留 Pillow 和既有进程所有权，并回收空闲辅助进程。

## 后果

顺序执行的历史和预览编码只需要一个编码进程，竞争时仍可使用两个；回收后的辅助进程再次启动会重新承担进程启动成本。共享映射与编码器分配继续受容量限制。其他原生识别调用和直接图片附件编码仍在主实例中执行。冻结程序安装和真实设备长期运行仍不在当前测量范围内。

## 验证范围

最初的截图编码隔离实现由编码、管线、集成与存储定向套件在 OpenCV 4.11.0、NumPy 1.26.4 和 Pillow 10.3.0 的隔离环境中用时 23.92 秒通过 125 项测试及 33 项子测试。真实测试子进程覆盖退出、挂起、返回不完整或逐字节慢速响应、返回无效 JPEG 数据、分配拒绝及启动失败。断言覆盖后续新帧恢复、失败快照只尝试一次、有界容量、源数组释放、预览独立推进及真实 Device/Recognizer 调用继续。Windows 测试以 `ctypes.PyDLL` 调用无限原生休眠，在编码及启动时持续持有 GIL，再终止未归属 Job 的测试父进程；实际 worker、启动器后代及共享文件均消失。原生超时也会终止完整 JPEG Job。启动器先于挂起后代退出时，必须等已保留且已核实 Job 归属的成员句柄发出完整退出信号，才能接纳替代进程。模拟清理拒绝保留所有权，不启动替代子进程；其他进程不能关闭原所有者的子进程。

编码测试覆盖 RGB 颜色、灰度尺寸、只读及跨步输入、一般图片尺寸和真实邮件附件的 ndarray 兼容性。定向集成测试证明可选诊断快照的 `MemoryError` 保留成功的 RGB 和灰度观测。受影响 Python 文件的 lint、格式检查及结构治理通过。最初的独立评审确认进程边界、期限、所有权与清理行为。测试不调用实际设备，也不耗尽宿主机内存。源码启动器执行真实的早期 worker 分派，并检查冻结命令路由；证据不包括已安装冻结程序及实际设备长期运行。

此前的 worker 等待修改另由受影响的编码套件验证：用时 18.94 秒通过 21 项测试及 13 项子测试。其中统计并发回归使用真实 Windows 子进程，在锁外句柄等待前设置抢占屏障。仅在独立诊断进程内还原旧等待方法时，同一测试复现 `WinError 6`；当前等待采用加锁轮询和预算内短暂休眠。所有诊断子进程均已回收。

当前[编码测试](../../../../arknights_mower/tests/screenshot_encoding_tests.py)还覆盖单进程复用、没有新帧时自动回收辅助进程、回收后重建，以及辅助进程超过空闲阈值时仍保留正在执行的帧。[管线](../../../../arknights_mower/tests/screenshot_pipeline_tests.py)、[集成](../../../../arknights_mower/tests/screenshot_integration_tests.py)和[存储](../../../../arknights_mower/tests/screenshot_tests.py)测试继续检查逐帧复用和关闭边界。

变基及辅助进程生命周期调整后，截图、进程恢复、设备恢复、桌面生命周期、进程控制、状态及预约启动定向套件在 61.43 秒内通过 285 项测试与 88 项子测试。恢复状态、App 集成和任务状态存储通过 22 项前端测试。语法、Ruff 与结构治理分别检查。当前生命周期内存测量由[监督资源证据](2026-10-12-owned-instance-supervision.zh.md#资源测量)持有。

## 性能证据

离线测量使用同一张既有 1920×1080 游戏截图的只读 RGB 数组，JPEG 质量为 75，每条路径随机交替执行 81 次暖态样本。两个环境均使用 Python 3.12.10、NumPy 1.26.4、Pillow 10.3.0 及 OpenCV 默认的 16 个线程。辅助进程回收调整之前，两个独立槽位的中位耗时如下：

| 编码路径 | OpenCV 4.9 环境 | OpenCV 4.11 环境 |
| --- | ---: | ---: |
| OpenCV RGB→BGR 及 JPEG | 28.0 ms | 5.1 ms |
| 同进程 Pillow | 6.8 ms | 6.3 ms |
| 历史 worker 暖态完整往返 | 7.9 ms | 7.6 ms |
| 预览 worker 暖态完整往返 | 7.5 ms | 8.0 ms |

每个环境各执行五次全新 worker 样本，首次编码中位耗时分别为 0.325 秒及 0.350 秒，包含进程创建和编码器导入。worker 暖态测量包含共享内存传输、控制 IPC 及完整 JPEG 字节返回；所有测量均不含截图采集、原有父进程快照复制、排队及写盘。同一图片在所有路径返回完全一致的 JPEG 字节，源数组保持不变。这些是同一宿主机上的源码环境观察；冻结程序启动及其他图片内容尚未测量。

此前约 22→7 ms 的比较描述 OpenCV 4.9 与 Pillow 编码，不能代表完整 IPC 路径，也不能代表相对 OpenCV 4.11 的提速。专用 worker 为原生故障的局部清理和预览独立推进而保留。新增进程内存、传输和启动开销换取这项故障边界；进程隔离不是性能优化。
