# 自有实例监督

[English](2026-10-12-owned-instance-supervision.md)

## 问题

主进程原生退出会绕过 Python 任务恢复。普通 Python 工作线程异常沿用既有失败处理，不应因此启动完整的进程恢复观察。恢复必须保留用户停止、配置空间所有权，以及既有高层任务与补偿边界。

## 决策

Windows 桌面启动器将实例监督与持有 HTTP 和设备调度的 Python 进程分离。监督进程导入轻量运行时协调模块，持有一个配置空间的独占所有权，并检测进程退出及 HTTP 持续不可用。初始快速尝试结束后，有上限的冷却间隔继续保持恢复能力。主动关闭、更新和显式进程替换结束旧监督进程，避免它与替代实例竞争。

[进程恢复说明](../../../../docs/subsystems/process-recovery.md)持有完整的启动、意图、重试和观察边界。既有设备恢复继续遵循待办保留和不确定输入规则。实现复用保存状态启动、SQLite 检查点、高层任务求解器、库存失效处理及桌面父进程监测，没有增加另一套调度引擎或新的运行依赖。

## 恢复

监督进程在主进程原生故障后恢复服务。原方案还将普通 Python 工作线程故障接入常驻恢复控制器，原因是仍在响应的 HTTP 服务不能自行修复已退出的自动化线程。本次调整后，普通 Python 工作线程异常不新建或重新激活进程恢复；对这类异常执行完整恢复观察，会反复中断仍然存活的实例。常驻恢复控制器在暂时的启动、快照或观察失败后，继续已有的监督进程恢复。旧版工作线程异常记录不再授权重试，后来真正发生的监督进程故障以自身原因建立恢复记录。恢复流程自动读取房间实际驻员、心情及相关任务状态，保存检查点，再返回既有求解器恢复。普通停止取消该意图；成功接纳的普通开始重新启用它。恢复无需单独确认、手工填写任务完成结果或新增操作回执系统。

到期动态跑单与菲亚梅塔充能需要重新规划，因为中断前的操作可能已经完成。既有任务类型提供重新进入路径，同时保留已保存的原班补偿和未来预约。加工站库存记录在仓库观察提供所需数量前保持未核实；这会延期加工，其他调度继续。服务健康时日志安静不能证明挂起。该边界不保证不可撤销操作只执行一次，不重建仅存于中断时 Python 调用栈内的原班，也不修复已确认的配置错误。

模拟器实例绑定、标准画面帧和基建排班表的含义保持不变。运行监督文件与用户配置分离；概念影响评估无需词汇表变更。进程恢复子系统以行为名称说明独立的进程所有权规则。

## 考虑过的替代方案

WinSW 可以管理 Windows 服务及失败重启，但服务部署会改变桌面会话、窗口和安装前提，Mower 的任务意图、HTTP 健康检查与状态核验仍需保留。Pebble 和 loky 管理进程任务，不能直接管理完整桌面实例。当前监督复用桌面入口和既有更新、进程替换协调。

## 后果

意外退出和 HTTP 持续不可用会获得后续恢复尝试；恢复等待重新观察和保存检查点，不重播不确定输入。监督进程本身占用内存，也不能证明 HTTP 正常时调度仍在推进。用户明确选择的清零或清任务模式在恢复失败后继续有效；成功的新检查点才替换原 SQLite 快照。

## 验证状态

最初的 Windows 定向[实例监督](../../../../arknights_mower/tests/instance_supervisor_tests.py)、[进程崩溃恢复](../../../../arknights_mower/tests/process_crash_recovery_tests.py)和[自动恢复](../../../../arknights_mower/tests/automatic_process_recovery_tests.py)套件通过 72 个用例，覆盖真实临时解释器退出、持续冷却重试、进程创建失败、HTTP 可用性、Job 归属、无关 PID 拒绝、启动器先退出、存活子进程独占、替换所有权释放及退出意图写入失败时的停止。生产自动化线程及调度入口检查覆盖普通异常、内部致命故障关闭、取消、严格读房、损坏 SQLite 数据及保留任务和补偿的真实 SQLite 检查点往返。动态订单、菲亚梅塔及库存测试验证既有重新进入路径。现有[设备恢复监督](../../../../arknights_mower/tests/device_recovery_supervision_tests.py)及[空闲场景监测](../../../../arknights_mower/tests/idle_scene_watchdog_tests.py)套件通过 37 个兼容用例，包括不确定输入后的观察恢复与取消。

[桌面父进程退出测试](../../../../arknights_mower/tests/desktop_parent_death_tests.py)通过三个用例，使用真实启动提示、托盘及窗口进程创建路径，并将 GUI 目标替换为离线等待函数。父进程监测修复前，三个合成辅助进程在主进程终止后均继续存活；修复后均退出。[复制后更新器入口测试](../../../../arknights_mower/tests/supervisor_deployment_tests.py)通过一个用例：仅使用既有四个复制的标准库模块并禁止工作树导入，验证独立源码安装期间仍可等待监督所有权释放。现有[进程控制测试](../../../../arknights_mower/tests/process_control_tests.py)覆盖显式替换及保留其他实例。

变基及启动模式修复后，截图、恢复、桌面、进程控制、状态和预约启动定向套件合计通过 285 项测试与 88 项子测试，另有 22 项前端测试通过。新增回归通过真实 HTTP 启动路由与 SQLite 快照验证模式 `0`、`1`、`2`，明确清零时绕过损坏快照，观察失败和主进程再次退出后保留该选择，并在后续独立故障时回到普通恢复。

2026-10-13 的评审将工作树变基到 alpha 提交 `52dba896f`。在已有 Windows 隔离环境中，使用 OpenCV 4.11.0.86、NumPy 1.26.4 和 Pillow 10.3.0，截图、恢复、桌面、进程控制、状态、预约启动及更新定向套件用时 86.74 秒，通过 408 项测试与 326 项子测试。三项 POSIX 或 macOS 用例跳过；三份前端套件通过 22 项测试。评审修复将两份生成的 Python 脚本明确写为 UTF-8，以支持中文临时路径，并补齐既有桌面更新启动测试对自动接纳参数的断言。修复前已复现脚本编码错误与旧断言失败。Python 静态检查和格式检查单独通过。

启动资源评审新增六项 Windows 聚焦回归，覆盖意图映射和 Job 分配失败、Job 归属设置失败及原生恢复执行失败。六项修复前均复现监督进程终止，修复后均通过，验证有界退避、已取得映射和 Job 的关闭，以及再次启动前已创建的自有子进程确实退出。该修复补齐既有启动失败边界，后续进程身份验证保持原有处理。

2026-10-15 的评审将分支变基到 alpha 提交 `ee1c554a3334142ae0a89333f18c717e17388e6f`。确定性回归使用真实维护锁和恢复记录，交错执行已接纳的开始与停止：修复前，停止后恢复意图仍被启用；修复后，停止取得锁时再次取消恢复，保留停止记录并阻止另一次自动启动。独立探测区分了 Windows 共享意图保护与无映射路径：前者在修复前阻止另一个工作线程启动，但仍发生错误的恢复尝试；后者可以再次启动工作线程。截图、监督、恢复、桌面、更新及 Android 发布定向离线套件通过 354 项测试与 237 项子测试，一项平台特定用例跳过。本次本地环境为 Python 3.12.10、OpenCV 4.9.0、NumPy 1.26.4 和 Pillow 10.3.0，不能据此声称已验证锁定的 OpenCV 4.11 环境行为。恢复状态与任务状态存储前端套件通过 23 项测试。App 套件因现有本地依赖缺少 `sass-embedded` 无法加载；上文先前的前端和性能结果保留为独立历史证据。

源码与打包参数构造、工作进程提前分派已检查。完整打包安装及真实设备长期运行仍不在本次验证范围。验证不连接真实设备，也不操作既有实例。

## 资源测量

同一宿主机上的源码环境对照使用一张只读 1920×1080 游戏截图，执行三轮测量，每条通道各接收 31 帧。旧双槽位实现从变基前 stash 中读取，用于对照；两个版本使用当前 Pillow 编码器和进程所有者。各阶段均包含同一组已加载的监督模块、自有 Job 与实际本机 HTTP 健康探测，存活编码进程组及启动器后代，以及实测父进程控制私有内存增量。

| 阶段 | 编码子进程数 | 新增私有提交内存中位数 |
| --- | ---: | ---: |
| 旧双槽位实现 | 2 | 55.1 MiB |
| 历史和预览顺序复用主编码进程 | 1 | 37.7 MiB |
| 主编码进程繁忙，辅助进程处理预览 | 2 | 55.3 MiB |
| 辅助进程达到默认空闲期限后回收 | 1 | 37.6 MiB |

已加载的监督进程组占 20.2 MiB。主编码进程继续工作时，辅助进程在最后一帧完成后 30.5–30.6 秒回收。回收后的单编码进程阶段约节省 17.5 MiB，约为这部分新增私有提交内存的 32%。竞争时仍使用两个编码进程，暖态内存与旧实现相近。所有测量子进程都在移除临时所有权文件前回收。

一个存活编码进程的固定文件映射容量为 13.8 MiB，两个合计 27.7 MiB；该容量单独记录，不与私有提交内存相加。Windows 私有提交内存不等于物理驻留内存，暖态双进程观察也不代表同时峰值。源码测量不能证明冻结程序内存占用或连续运行稳定性。[截图编码证据](2026-10-12-isolated-screenshot-encoding.zh.md#性能证据)保留此前编码器与 IPC 耗时；辅助进程回收后重新使用时，需要再次承担进程创建成本。
