# 独立于启动器的按需共享 OCR

## 问题

改动前，每个 Mower 实例独立构造 OCR 会话。18 个实例可能同时保留 18 份模型，而实际只有少数实例需要识别。原有检测输入上限减少了单次分配，但没有共享模型。用户希望多开管理器仍然是可以独立退出的启动器。

## 决策

当不止一个 Mower 实例需要识别时，实例使用独立、按需启动的 OCR 服务，多开管理器保留启动器职责。[识别子系统说明](../../../../docs/subsystems/recognition.md#independent-shared-ocr)规定准入、请求预算、模型回收、失败行为、服务协议与选择规则。轻量协调进程拥有一个模型工作进程，账号、设备和任务状态保留在调用方。共享模型限制推理并行度，此时替代每个实例各加载一份模型的做法。

服务生命周期属于安装，而不属于启动它的调用方。服务空闲后退出，并在已完成的请求之间更换工作进程，使原生分配不必等待垃圾回收即可释放。服务锁保证同一时刻只有一个协调进程；协调进程退出后，仍在原生调用中的工作进程以模型锁阻止替代模型重叠。模型工作进程在构造模型前独立登记，因此协调进程退出后，更新仍能看到那个孤立模型。[软件更新退出流程](../../../../docs/subsystems/software-update.md#shared-ocr-update-lifecycle)会等待该服务；更新恢复不重新拉起它，之后需要共享的调用方再按需创建新服务。端点元数据保存在可写数据根目录内、更新缓存之外，软件更新替换文件时不会接管存活服务的状态。

共享按存活消费者数量门控。`initialize_ocr` 统计同一安装与数据根下存活的 `instance` 登记：只有一个实例时使用进程内引擎，两个及以上才使用共享服务。`MOWER_OCR_MODE` 可强制 `auto`、`local` 或 `shared`，非法值直接报错而不回退。该门控沿用 MAA 的非对称结构：MaaCore 的 OCR 是进程级单例，进程内共享不额外起进程；对 Mower 来说，第二个进程才构成新的消费者，共享协调进程也只在此时划算。单独消费 OCR 的进程仍把模型留在自身进程内。没有实例登记的进程，例如直接启动的 Web 服务或 Android 宿主，按单个本地消费者处理；该模式下的多实例部署必须显式选择共享模式。

## 考虑过的替代方案

把 OCR 放回多开管理器，关闭启动器会中断识别；让每个实例各自识别，又会重复识别同一项工作。为每个实例创建子进程仍会重复加载模型。多工作进程池能提高峰值吞吐量，但会成倍占用模型内存；因此先用有界准入验证一个共享工作进程，再考虑增加数量。只使用线程无法隔离原生崩溃，也无法从进程外限制原生推理时间。既有后台进程都不具备所需生命周期：JPEG 编码工作进程只在任务期间存活，更新工作进程只执行一次任务，Windows 监督进程按实例归属且仅限 Windows。复用其中任何一个都会把 OCR 生命周期绑定到任务、一次更新或单个实例，而不是安装。

管道或文件请求队列需要一个进程接收请求，从而重新引入对调用方生命周期的依赖；回环套接字让任意实例都能连接比创建者存活更久的服务。通用 HTTP 服务会为一个二进制请求/响应引入请求框架和更大的接口面。Unix 域套接字和 Windows 命名管道各自需要平台专属的端点路径与访问策略；同一个回环套接字、端点文件和既有文件锁即可提供发现、认证和单实例仲裁。

## 验证

最终验证运行中，[共享 OCR 测试](../../../../arknights_mower/tests/shared_ocr_tests.py)通过 45 项定向离线检查，[共享 OCR 更新生命周期测试](../../../../arknights_mower/tests/shared_ocr_update_lifecycle_tests.py)通过 10 项，两者合计用时 119.42 秒；同一次运行还包含 [OCR 门控测试](../../../../arknights_mower/tests/ocr_gate_tests.py)的 26 项与[运行时内存测试](../../../../arknights_mower/tests/runtime_memory_tests.py)的 32 项。共享 OCR 覆盖安装隔离与网络命名空间隔离、18 路客户端共享一个模型、并发启动竞争、图像准入、参数隔离、传输上限、失败与超时清理、空闲退出、存在等待请求时更换工作进程、12 项参数化的工作进程回收阶段管道关闭回归、更新期间关闭服务，以及源码启动的服务在首个客户端退出后继续存活。独立包入口使用替代服务实际执行，并拒绝 GUI 导入。

生命周期检查覆盖孤立工作进程仍留在更新停机快照中、两类登记均被恢复排除，以及更新准入之后启动的工作进程被拒绝构造模型；门控检查覆盖单实例本地与两个实例共享的选择、模式覆盖与非法值、每次调用重新评估与切换、失败回退、数据根过滤、并发初始化以及本地引擎与共享客户端一致的调用选项；运行时内存检查覆盖检测张量上限、并发客户端初始化以及日志与截图的内存上限。

[家具回归](../../../../arknights_mower/tests/furniture_ocr_tests.py)在本地与共享两条路径通过 36 项检查。相关登记、更新器、管理器与内存检查通过 59 项，其中一项平台专属检查被跳过；识别回归通过 169 项，桌面与准备阶段的生命周期检查通过 21 项。这些分组有重叠，不能相加作为独立测试总数。

macOS 本地对照使用三个独立客户端、三张相同的家具截图，两种模式下每个 ONNX 会话的算子内线程上限均为两个。所有客户端完成任务并保持存活后，各进程 RSS 合计由独立模型的 1252.8 MiB 降至共享方案的 822.0 MiB，共享数字包含协调进程和模型工作进程。家具名称与数量全部一致。采样对象是三个客户端，以及共享模式下的协调进程和模型工作进程；不计两种模式共用的测量程序及 multiprocessing 资源跟踪辅助进程。这是任务完成后保持进程存活状态下的 RSS 测量，不是峰值、18 个模拟器的实测或长时间稳定性结论。

请求预算、空闲退出与回收阈值仍取 60 秒、60 秒和 256 次，依据为本机测量。16 逻辑核 Windows 主机上的只读探针使用两个 OpenCV 线程和每个 ONNX 会话两个算子内线程：全帧推理中位 1.07 秒、首次调用 2.8 秒，模型构造冷启动 1.66 秒、页缓存热启动 0.54 秒。18 路突发在 13.5~17.2 秒内完成，剩余 71%~77% 的请求预算；若某主机每次调用需要 2.8 秒，18 路约 54 秒，只剩约 10%。空闲退出后的冷启动会多花 2.1~3.5 秒。处理 256 次请求后更换工作进程约需 4 秒，摊薄到每次请求约 16 毫秒。宿主机更慢、负载更高或突发期间更换工作进程，都会进一步压缩余量。这些是单台主机源码启动下的测量，不是端到端服务保证。

## 后果

顺序推理增加集中请求时的等待时间，准入和请求预算可能拒绝任务。空闲退出或工作进程更换后会再次冷启动。共享限于同一安装、数据根目录及网络命名空间，不减少模拟器或其他实例状态的内存。本机回环认证不构成跨主机服务。共享模式下的已发送请求不会重放，失败也不会回退到进程内模型。协调进程异常退出后，父进程管道 EOF 监测依赖 GIL；原生工作进程仍存活时，其模型锁阻止替代模型重叠加载，而该工作进程自身的登记使它仍处于[软件更新退出流程](../../../../docs/subsystems/software-update.md#shared-ocr-update-lifecycle)的等待范围内，直到它退出。

单实例不再承担共享协调进程与模型工作进程。两个实例起是否省内存取决于 Windows 主机上的口径：峰值 WorkingSet 下，单实例共享比本地多约 10%~52%，盈亏点约 1.1~1.6，两个实例已净省；保留 WorkingSet 下，单实例共享多约 71%~77%，盈亏点约 2.8~3.1，两个实例仍多约 14%，约三个实例才盈亏平衡。门控去掉了在所有口径下都更差的单实例场景；再往上，收益取决于部署受哪种内存指标约束。PR 的 macOS 保留 RSS 对照属于另一口径，不能直接比较。

模式切换在下一次 `initialize_ocr` 调用时收敛：登记只读取一次且不重试，因此几乎同时启动的实例可能短暂选择不同模式，扫描失败时回落为本地，没有后台监视或轮询。切换先构造新引擎再发布，构造失败时保留旧引擎；在途请求持有自己的引擎。释放进程内模型只去掉本模块的引用，ONNX Runtime 与分配器内存可能保留到进程退出，因此切回本地不承诺立即降低常驻内存。

## 限制

Android 宿主执行、Windows/macOS 打包产物与真实设备长跑均未实测。

账号、设备和排班概念的含义与归属保持不变。本次调整改变了无状态识别的执行位置及进程生命周期，不需要修改术语表。
