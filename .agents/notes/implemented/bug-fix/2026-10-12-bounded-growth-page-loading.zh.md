# 养成页面加载上限

## 问题

养成页面加载所有干员的完整材料数据，并深度监听整个响应。使用内置资源构造的 432 位未精英化干员产生 84.03 MiB JSON 和 705414 个嵌套对象。多个实例同时打开会叠加解析、监听和渲染开销。这些测量证实负载过大，但尚无 WebView 崩溃记录证明用户所述白屏的确切原因。既有养成决策负责材料核算，未规定页面资源上限。

## 决策

[页面加载上限规则](../../../../docs/subsystems/growth-planning.md#bounded-page-loading)将不含材料数据的概览与选中干员的详情分开。既有调用者保留默认完整响应。页面每页渲染三十张概览卡片，只保留一份详情。替换详情时取消前次请求，迟到响应不能覆盖当前选择。详情请求有有限超时和局部重试。计划草稿继续深度监听，服务端快照只监听整体替换。

## 考虑过的替代方案

串行请求仍使每个渲染进程接收并保留 84 MiB 数据。仅改为浅层监听可减少代理，却仍保留完整响应。通过可选材料开关复用既有计算器，保持单一材料核算实现，不增加第二套预览计算器或跨实例共享缓存。简化检查识别出混合深度监听中的冗余遍历；计划草稿仍需要深度监听。

## 验证

相同的 432 位干员测试数据在概览模式下产生 0.64 MiB 响应和 6700 个嵌套对象，修改前为 84.03 MiB 和 705414 个对象。本地开发机的生成耗时从约 2.1 秒降至 0.07 秒。这些是合成数据测量，不是用户进程的内存读数。

`python -m pytest arknights_mower/tests/growth_page_loading_tests.py arknights_mower/tests/growth_planning_tests.py arknights_mower/tests/web_routing_tests.py -q` 通过 39 项测试。新增[加载测试](../../../../arknights_mower/tests/growth_page_loading_tests.py)验证概览不计算材料、响应小于一 MiB、单个干员材料费用保持一致、实际 HTTP 路由和并发读取不改写资源目录。

覆盖页面、专精状态、养成计划编辑、等级控件及养成和调查工具的定向 Vitest 测试通过 49 项。[页面测试](../../../../ui/src/pages/MasteryRecommendation.test.js)覆盖分页、全局筛选、取消、迟到响应、重试与卸载清理；[状态测试](../../../../ui/src/stores/mastery.test.js)覆盖轻量请求、浅层快照和不同前端实例的状态隔离。生产 Vite 构建、定向 Ruff/ESLint 和空白检查通过。

`python scripts/verify_governance.py --base origin/alpha` 通过结构检查，保留两条既有归档引用警告。标准审查确认材料核算、独立临时状态和详情数量上限保持有效。需求审查确认实际页面读取概览、筛选覆盖完整列表，并仅为展开干员读取材料。领域语义与配置无变化，无需编辑术语表。

## 后果

展开干员增加一次本地请求。自动化和旧客户端仍能使用默认完整 API。打包版多实例 WebView 行为需要手动验证；响应体测量不能单独确认崩溃原因。领域概念、调度和配置保持原义，无需修改术语表。
