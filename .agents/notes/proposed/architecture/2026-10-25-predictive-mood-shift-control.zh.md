# 根据心情预测协调普通上下班

## 问题

用户希望开启“实时心情计算调控”后，Mower 根据预计工作和恢复时间自主协调上下班，减少临时等待、重复演算与进房检查。用户已选择允许普通主班为避免后续替班或床位冲突提前下班，优先保障轮班连续性；明确配置“用尽下班”的干员仍须遵守个人下限。

现有调度并非只读心情而不规划。主班用尽和工作替班已经能够预约个人下限；回班和个人上限离宿也已有预测入口。[`resting()`](../../../../arknights_mower/solvers/base_schedule.py)仍主要依据当前心情余量、普通下班阈值、理想休息人数和当前资源决定谁下班；[`plan_metadata()`](../../../../arknights_mower/utils/scheduler_task.py)负责恢复与回班时刻。缺少的是在同一时间线上比较“保持现状”和“提前轮休”，检查后续替班、恢复床位和执行窗口是否接得上，而不是另造一套换人执行器。

[Arknights Mower 基建调度子系统说明](../../../../docs/subsystems/base-scheduler.md)规定实际驻员、预演、绑组、宿舍分配和失败任务的现行规则。[共用心情公式的决策](../../implemented/architecture/2026-10-25-shared-runtime-mood-engine.zh.md)继续负责计算模型与运行时边界。本提案独立决定如何用预测选择上下班时机，不替代该公式决策。

## 提案

采用有界的事件预演：在当前有效排班、实读校准和已有任务基础上，比较少量可执行轮班顺序，仅提交下一次可以落实的安排；后续预测作为建议保存，不提前占用真实干员或床位。真实观测和已完成动作不断校准下一次安排。

本轮实际改动仅包括设置改名和本提案。以下调控算法尚未实现，不因设置名称改变而宣称生效。开关继续放在排班编辑的高级设置，沿用 `test_mood_calculation`、默认关闭和原导入导出格式。正式实现后，开启此设置同时选择计算心情和本提案的普通轮班策略；关闭时沿用原识别及轮班策略。

### 目标与边界

1. 先满足硬约束，再优先减少预测中因心情不足或缺少合法接班而无法持续工作的情况。已到个人下限的请求优先处理，提前轮休不得抢占它需要的资源。
2. 在连续性相同的方案中，优先避免不必要的提前离岗和换人；结果仍相同时保留当前预约和原有稳定排序。首版不以加权收益最大化为目标，不声称达到全局最优。
3. 保留当前有效主班、替班名单及顺序、绑组和多绑规则、零心情工作名单、个人上下限、强制回满要求、恢复层级、床位保护、跑单让路和专项预约。已有候补和支援路径继续由现有规则准入；预测不能自行扩大候选名单。
4. 宿舍隔离沿用现有的分床偏好及无法分开时允许同宿的规则，不在本提案中改成绝对隔离。训练、加工、实际菲亚梅塔充能及自动救急的启动和退出条件继续由原有流程负责；普通调控不能用预测擅自进入救急或操作受保护训练位。
5. 普通下班阈值仍是基准方案。只有预演证明提前轮休改善后续连续性，而且完整替班和床位匹配成立时，才允许普通主班在该阈值之前下班。用尽干员及受其约束的绑组不适用此例外；不可借普通组员绕过用尽限制。

### 输入与输出

一次规划使用同一个时刻和不可变的输入快照：有效主副表、实际驻员及观测来源、模型与技能参数、个人限制、真实床位和单回目标、现有任务的阶段与预约、已有跑单及执行耗时预算。模型里的经过时间、预测值与房间实读保持分离。

事件预演须有显式的虚拟时钟和独占模型：先按旧驻员与旧速率推进到事件时刻，再按各房间预计操作完成时刻应用驻员变化，之后重算技能与恢复速率。同一时刻的释放、回班和下班依赖按既有任务先后关系处理，不能先消费尚未释放的资源。复用的匹配、恢复和副表函数须接收统一的 `now` 与配置快照；不得通过修改全局时钟或 `config.conf` 实现预演。当前 `project_arrangements()` 主要负责顺序位置投影且内部仍读取当前时间，不能把重复调用它当成完整的未来时间线，实施时需要扩展显式时间参数或提供受控适配入口。

规划输出包含下一次有依据的唤醒时刻、拟议上下班组、原因、依赖的干员和位置、预计恢复及交接时刻，以及“已确认可行／证据不足／预演预算耗尽”的结论。这里只是内部返回数据，不新增持久化配置或对外接口。工作下限、休息完成、技能边界及已知任务的完成均可成为事件；没有恢复速率或有效心情时，不能制造一个定时重试。

```text
实读校准、有效排班、已有任务
  → 同一时刻的独立预演
  → 比较当前策略与可行的提前轮休
  → 选择下一次动作或有依据的事件时刻
      ├─ 未到执行窗口 → 保留建议，不占用真实替班和床位
      └─ 已到执行窗口 → 现有准入与副表收敛 → 现有换人流程
                                                → 实读确认 → 更新后续预测
```

### 普通下班与回班

候选包括保持当前安排、按原规则下班、让一个具备完整匹配的普通休息组提前下班，以及由已有合法回班释放资源后再下班。每个候选同时预演工作替班能撑到何时、休息组何时按既有规则允许回班、床位何时真正释放，以及交接是否撞上关键任务。不得只看当前空床或把预测回班当成已经释放资源。

普通组可提前离岗，但没有完整替班和合法床位时不执行。回班时机复用已有恢复目标、回满要求、组内恢复差异及其等待上限；本方案不授权降低恢复目标。非强制回满组只有满足原有回班规则，且后续轮班可衔接时，才使用较早的合法回班时刻。个人上限强制离宿仍独立生效，离宿不等于获得上班岗位。

提前轮休不增加一次专门的心情巡检。正常执行进房时读取并校准；只有计算达到个人下限的用尽和替班确认才保留该下限实读。执行前发现实际驻员或可用资源改变时，未开始的建议重新规划；已开始换人则按原任务完成剩余安排与补偿，不能从中间驻员重新启动普通轮休。

以下是用于验收的简化示例，并非实测收益：A、B 共用一个恢复床位和一个工作替班；A 距下限 2 小时，B 距下限 3 小时。A 提前轮休后，按既有规则到完成回班需 1 小时，包含 A 自己的下班和回班操作；随后 B 的离岗交接还需 5 分钟，不能与 A 共用替班的交接重叠。假定替班心情足以覆盖这两组的合法恢复段，其余后续接续可行，两方案均观察到第 4 小时。若等 A 到下限才开始，会把 B 的交接挤到其下限之后；若 A 现在开始，则能在 1 小时后回班，把床位和替班交给 B。预演可选择后者，但不宣称这个起点是最晚或最优的提前时刻。若 A 配置用尽下班，就不能采用这个提前方案，必须尝试其他合法资源或明确保留无法接续的请求。

### 预演范围与成本

首版采用滚动的有限搜索，查看每个候选下一次离岗、合法回班及接续组的下限，至少验证提前动作有没有把冲突转给下一组。对所有参与比较的组使用相同的观察终点，终点覆盖这些接续事件，并受既有模型的时间范围限制。无法在范围内覆盖关键恢复事件时标记证据不足，不能当作已证明连续可行。

连续性比较使用固定参与岗位和同一观察终点，依次最小化：到个人下限后尚未开始合法交接的请求累计等待秒数、没有有效工作覆盖的岗位累计秒数。第二项包括空岗和心情耗尽后失去有效工作的时段，按配置允许零心情工作者不计入。用尽下限是开始确认的条件，不强求在该时刻前完成换人；所有方案均计入相同的实际操作预算。前两项相同时，依次比较换人次数、相对原策略提前离岗的总时长，再沿用稳定顺序和有效预约。提前候选至少必须严格改善前两项中的一项，且不恶化更高优先级项；相同连续性不构成提前离岗理由。

按既有紧急程度和稳定顺序选择候选，保持原策略候选始终在内。候选起点来自当前时刻、资源释放、合法回班、工作下限及扣除真实操作预算后的事件边界；跨技能或副表边界时重新求值，不假设恢复时间始终线性，也不在未证明单调的整个区间上二分查找。

拟定首轮离线验证上限为每批 16 个候选、每个候选 64 个离散事件节点；这是计算预算，不是轮询次数或阻止任务继续的条件。候选中的未来组选择复用现有确定性匹配，不枚举所有人员组合。达到预算后保留仍有效的原安排；若没有原安排，交还现有合法调度处理，并报告没有完成优化，不能把预算不足写成无解。只对涉及提前下班的候选要求完整的接续可行性证据。

复用现有心情轨迹缓存和同一时刻批量查询；不要在每个组、每个节点从实机重建全体干员。首版允许在相关事实变化时重算一个有界批次，不先建立复杂的逐干员依赖缓存。记录规划总耗时、候选及事件数、模型计算耗时、是否复用、是否耗尽预算，避免将已有副表计时与新增规划耗时重复相加。上线预算须以相同真实快照的对照测量校准，不能由桌面测试推断手机或多开延迟。

### 什么时候重新规划

| 事件 | 拟议处理 |
| --- | --- |
| 启动或重启，初始化实读完成 | 按实际状态重建未开始的预测，保留已开始及失败保留任务 |
| 正常进房取得新观测；换人、充能或加工实际完成 | 更新模型与相关资源，合并到本次操作结束后的一个规划批次 |
| 生效副表、产物、技能练度、个人限制、恢复目标或关键任务预约变化 | 使相关预测失效，重新检查完整交接 |
| 已预约事件到期 | 先验证当前事件；输入未变且已有完整安排时执行；技能、资源或前提发生改变时合并为一批重算 |
| 只经过时间，输入与下一事件不变 | 复用原期限，不把“当前时间”或单纯模型 revision 当成失效原因 |
| 观测失败、没有床位或替班 | 保留原任务、时间和剩余工作，让其他任务继续；相关观测或资源状态变化后才能重试 |

计算耗时到达上限、同值重复调度以及失败任务自己产生的无变化读回，都不创建周期唤醒。新成功观测可解除之前的读取失败，但应与“换班条件真的改变”分开记录。外部正常任务释放资源后，必须能恢复对应请求，不能因为缓存未失效而永远等待。

### 与现有调度的连接

拟新增一个不操作设备的 Python 规划模块，由 `plan_solver()` 的普通主班规划入口调用。它复用 `Operators.project_arrangements()`、现有替班与床位匹配、组恢复和副表收敛，不建立另一套资源准入。只读预演不得向真实队列追加任务、修改实读记录、库存或单回确认状态。

`plan_metadata()` 继续负责已有回班、离宿任务的生命周期；新模块向它提供选中的时机与依赖。用尽和工作替班的个人下限任务保留原有身份和所有者，规划器消费并去重这些事件，不再创建第二份同用途任务。普通未开始预约由一个入口替换，避免原 `resting()` 与新策略分别生成下班任务。关闭设置时保留原入口。

当前 `_prepare_ordinary_departure()`、`_ordinary_coordination_needed()` 和 `_validate_calculated_arrangement()` 会再次验证普通下班阈值，`_prepare_shift_cycle()` 内也会调用预演副本的 `resting()`。实施必须将这些入口统一到同一策略准入：任务携带普通数据形式的提前理由、输入版本和依赖，只有仍有效的提前证据允许越过普通软阈值及理想休息人数的限制；硬性用尽、回满、组约束、资源与训练保护一律不豁免。首次实际换人前的新读数会触发重新验证或重算，不能用一个永久标记跳过检查；开始执行后继续保留原任务义务。完整副表预演中的后续轮休也要使用同一策略，不能重新调用旧筛选把提前意图丢掉。

派发前通过原有关键任务准入和 `_prepare_shift_cycle()` 完成最终安排验证，操作时长使用已有房间和阶段预算。预测计划仅在执行窗口到达、当前依赖核验通过后生成正常队列的具体安排并取得预约；排队期间发现变更必须重新准入。预约最终只由现有任务系统持有。预测建议与中间搜索缓存不跨重启持久化，已有任务及其保留状态继续按现有快照格式保存。

调度主循环目前按 `find_next_task()` 决定休眠和空闲任务预算，内部返回一个时刻本身不会唤醒它。拟复用空计划的 `SchedulerTask`、`NOT_SPECIFIC` 类型和普通数据标记 `mood_control_event`，最多保留一个最近预测事件；它参与时间排序但不取得人员、岗位或床位预约。必须在默认 `NOT_SPECIFIC` 的心情读取分支前走专用纯内存处理，不借此触发额外进房。事件携带类型、目标、恢复周期、输入观测版本和绝对时刻，输入变化时替换；同一版本的过期事件消费一次后不重新入队。依赖不成立时改做一批重算或等待具体依赖，不静默丢掉请求，也不加固定延迟。重启或关闭开关时移除未开始的纯预测唤醒，初始化后按当前模式重建；这不移除实际换人任务或失败保留请求。

### 收益模拟同步

当前收益模拟始终计算心情，但[`mowerAdvancedAssumptions()`](../../../../ui/src/riic/vendor/scheduler/mowerAdvancedSettings.ts)尚未消费 `test_mood_calculation`，其[`普通下班实现`](../../../../ui/src/riic/vendor/scheduler/mowerAlphaDormPlanning.ts)和[`恢复任务实现`](../../../../ui/src/riic/vendor/scheduler/mowerAlphaMetadata.ts)是独立的 TypeScript 调度代码。共用公式并不自动同步新的调控策略。

正式实现必须同时把这个已有设置传入模拟策略：关闭时模拟继续使用当前轮班策略，开启时采用同样的预测调控。两种模式都继续模拟实际心情变化。Python 与 TypeScript 共用输入场景和期望事件轨迹，比较候选排序、任务时刻、资源占用及失败保留；不能只比较最终收入。记录策略版本与所用开关，修改模拟缓存的策略版本，避免显示旧策略结果。快照输入、操作时间与观测假设相同时应得到相同的策略决定；真实设备的误差由实读校准承担。

### 实施顺序

1. 明确规划输入、输出与旁路诊断，建立保留原策略的对照轨迹。诊断模式只用于开发验证，不新增用户开关，也不创建游戏操作。
2. 实现有界事件预演和稳定候选比较，覆盖当前资源足够、共享资源冲突和无法接续三类场景。
3. 接入现有派发、期限更新及失败恢复，验证取消未开始建议与保留已开始任务的边界。
4. 同步收益模拟及配置映射，完成跨实现事件轨迹对照和真实快照性能测量。
5. 所有离线验收通过后才启用新策略，再以获授权的设备验证确认观察和操作误差。实施期间帮助文案只描述已交付行为；调控完成后再补充提前轮休的含义。

## 考虑过的替代方案

- 维持当前阈值和队列，只提高预测精度：改动小，但无法比较共享替班或床位的未来使用顺序。
- 所有干员一律等个人下限再下班：清晰但不能满足用户允许普通主班提前轮休、优先保障连续性的选择；仍用于明确配置用尽的干员。
- 一次计算数天的全局最优排班：容易受实读误差、副表、技能边界及设备耗时影响，搜索成本也难以约束。首版选择滚动有限搜索，接受不能保证全局最优。
- 再加一个独立调控设置：能分开选择计算与调控，但用户明确要求合并为“实时心情计算调控”。沿用现有键，避免两个开关形成额外组合。

## 验收条件

以下均为待实现的行为验收，本提案没有执行新调控算法的测试。

| 场景 | 必须观察到的结果 |
| --- | --- |
| A、B 共享床位和替班的提前轮休示例 | 普通 A 可提前并形成完整接续；A 用尽时不能提前 |
| 个人下限 0 与非零、绑组含用尽成员 | 保留个人限制，不借同组普通成员绕过 |
| 当前可休息但下一组将无法接续 | 不把局部匹配成功当成全链路成功；预算不足明确返回未完成 |
| 强制回满、个人上限离宿、单回、受保护床位与宿舍隔离 | 复用对应现行规则，不为预测改善而破例 |
| 输入相同重复派发、已有预约及持续时间推进 | 不重复完整演算、不重复预约、不推迟原恢复窗口 |
| 高于下限的实读、新技能输入、同值新成功观测 | 正确校准或解除读数失败；自身无变化读回不造成循环 |
| 床位不足、读数失败、重启与独立任务并存 | 原任务及时间保留，独立任务执行，真实依赖释放后恢复 |
| 同一输入推进到未来事件及同时刻资源交接 | 旧阵容先消耗／恢复到事件时刻，资源确认释放后才可接管，不污染真实时钟和配置 |
| 预测唤醒到期、依赖失效、重启或关闭开关 | 按期进入专用内存分支，不额外巡检；无重复过期事件，实际请求不丢失 |
| 提前任务通过首次进房和完整副表预演 | 有效策略证据被所有准入入口一致使用，旧软阈值不误取消，硬限制仍生效 |
| 部分换人、副表循环、跑单占用执行窗口 | 不丢剩余任务，不从中间驻员重建，不违反关键任务准入 |
| Python 与 TypeScript 使用相同场景 | 对齐关键决策、时刻、预约和失败轨迹，开关关闭时原策略保持 |
| 实例快照、嵌套副表与多批重复规划 | 报告冷／热耗时、模型调用、峰值候选和事件数；不宣称手机或多开性能已经验证 |

## 风险

心情技能缺项、满练与宿舍氛围假设、实际操作时间和突发读数偏差都会改变预计接续。未来库存、订单产出和外部动作不由心情模型补造；预演结论须声明所用的排班与条件假设，实际副表条件变化后使其失效。必须保留实际观测与临执行准入，不能保证任何排班都不会断档。有限搜索可能找不到存在的方案，结论应为未找到可证明的改善而非判定用户配置非法。

提前下班改变普通下班阈值在启用模式中的作用，正式实施须明确更新设置说明、行为规则及模拟映射。开关关闭恢复原策略，但不能撤销已经实际完成的换人；已开始与失败保留任务不能因关开关被丢弃。建议缓存可丢弃，真实任务继续执行和恢复。

本提案沿用心情、个人上下限、实际驻员／预演驻员、替班、绑组和恢复目标的现有含义；新增的是时间选择与预演流程，无需修改术语表。规划的上下文关系以本提案为准，现行实现仍由子系统说明负责；算法完成并通过验证前保持 proposed 状态。
