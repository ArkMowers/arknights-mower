# Mower PR

输入是需求、最终 diff、已有 PR 和验证记录，输出是中文标题与正文。执行范围和发布授权沿用[项目工作流](../../AGENTS.md#1-task-selection)。正文采用 show-me 的 Summary、Evidence、Merge Danger 三个栏目，按下面的流程组织事实。

## 1. 提取最终事实

确认实际 base/head 或工作区范围，读取完整 diff、已有 PR 和相关子树指令。按[根指令](../../../AGENTS.md)、[编码规范](../../../CODING_STANDARDS.md)及用户要求核对材料，区分已提交内容与准备提交的修改。

先整理供写作使用的事实提纲：每项主要变化包含具体对象、原问题、最终结果、方案理由和对应证据。原行为以比较基线为准；旧正文和讨论用于查证。文档和工程改动说明使用或维护方式的变化，不强套运行时故障。

进入提纲的事实必须能解释最终方案、取舍、证据可信度或合并后果。将材料中的调试、局部改名和未交付改稿过程排除后，再开始写作；保留已发布问题的实际影响、仍有关的验证失败、重要覆盖缺口及明确要求的审计事项。更新已有 PR 时重新取材，不以保留旧文全部信息为目标。

## 2. 合成标题

从提纲选出核心变化、具体对象和前后结果，先确定标题的完整宾语，再选择动作并合成单一动宾短语。一个主要动作支配一个完整对象；对象中可以包含辨认变化所需的条件、场景和结果。次要变化进入正文，不将多条完整规则压入标题。

标题必须遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。以下规则补充项目类型选择和中文表达要求。

格式为 `<type>[optional scope]: <description>`。type 从 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 中按主要目的选择。scope 选填，沿用项目已有英文范围名称；冒号后一个空格，中文描述末尾不加句号。

| 目的 | 描述结构 |
| --- | --- |
| `fix`：修复问题 | 动作 + 发生场景或流程 + 具体不良现象 |
| `feat` / `fix`：补充能力 | 动作 + 业务流程 + 特定情形下的处理能力 |
| `docs`：修改文档 | 动作 + 具体功能或模块 + 修改的说明文档或规范内容 |

从使用者或维护者视角命名具体对象，将内部验证手段、局部实现动作和宽泛系统名词转换为实际用途。`docs` 的宾语是具体说明文档或规范内容，功能或模块名称用于限定这份文档；完成时能回答“修改了哪项说明或规范”，规则本身在正文解释。描述不含开发过程编号或临时标记，不用 `+`、`/`、`、` 串联不同动作。

## 3. 按审阅顺序组织段落

使用[正文模板](assets/pr-body.md)，先写各主题的加粗短标签和结论句：按主要变化排列 Summary 的结论，为每项结论安排对应的 Evidence 结果，再写 Merge Danger 的影响和恢复条件。提纲能单独说明改动、验证发现与合并后果后，才补解释、证据和条件。展开时只使用已筛选事实，不从原始讨论重新摘抄。

每个主题用加粗短标签和完整结论句引出，再按内容关系选择结构：

- 有先后顺序的操作或推导步骤，用编号列表，每步单独换行。
- 同层且可分别核对的规则、结果或条件，用 Markdown 项目列表，每项单独换行。
- 解释、因果或递进关系，用连贯自然段；一句能清楚表达的简短枚举无需拆成列表。

列表前留空行，每项保留自身的条件和例外，不用逗号或分号把多项独立要点挤在同一段。同一主题可以包含引导段和列表，标签只放在主题开头，列表项不必重复加粗。Summary 和 Evidence 中对应变化使用可相互辨认的主题标签；Merge Danger 使用影响范围和可逆性定位后果与恢复条件。

**Summary** 首段交代原问题和最终变化，后续段落解释方案及必要取舍。跨组件、状态或职责关系需要图或短 diff 时，紧邻整体方案放置。小改动可用一段完成。

**Evidence** 按 Summary 的主要变化顺序，逐项说明实际验证结果和具体问题。段首直接给出结果，随后解释检查了什么、依据是什么、失败或缺口有什么影响。有同一场景的前后对照时，在对应主题下将 **Before / After** 分为两个列表项，标明两侧结果和来源；没有执行记录时只说明已有文档或源码依据。一次检查支持多项变化时，在首次相关处集中交代，后文按需引用。

**Merge Danger** 先说明采用后的实际影响，再交代恢复条件。按变化区分代码或文档回退、已有状态恢复和外部操作结果恢复；只写确实涉及的对象，条件未知时指出待确认环节。风险已在 Evidence 说明时，此处只补合并决策或恢复所需的信息。

采用[项目文风规范](../mower-prose-standard/SKILL.md)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)。检查句内分句和相邻句子是否确有解释、因果、条件或并列关系；无关事实分开表达。每段或列表只围绕标签所指的主题展开；不能靠加粗或连接词拼接无关事实。

## 4. 核验证据和依据

按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)区分程序检查、行为观察及语义评审。对照必须使用同一场景并定位两侧依据；只有旧版源码或文档时，明确其来源。说明示例、给定材料和本次实际执行结果分别归属，旧结果只支持它实际验证过的版本与结论。

将工具结果翻译为具体事实：什么通过、什么未通过、原因及影响。精确命令、版本、哈希和方法细节由对应证据记录承载；没有独立记录时在一处简短附注。正文不以退出码、诊断码或整串参数充当结论。链接文字说明内容，版本放入链接目标。

将证据排除句改成已验证的具体结果或与本 PR 主张有关的待验证行为，同一缺口只写一处。真实失败要说明失败对象、原因和影响，不能软化为泛泛的语义复核。未测量的指标或未执行的项目只有影响主要结论或属于明确审计要求时才进入正文，不自动转为待办。

简短记录实际使用的指令版本，以及影响方案、验证或交付边界的要求，采用“来源 + 已发生的动作”。正文已有来源和证据时直接复用；尚未定位的依据可在末尾集中补充，不重复解释规则。临时要求保留核对结论所需的原文，规则变化时区分执行依据与交付版本。

## 5. 回读与交付

先单独读标题、加粗标签和结论句，检查对象、结果及方案与证据的对应，再检查段落与列表是否准确表达内容关系。并列要点逐项核对，有序步骤核对先后关系；不能把列表数量或加粗数量当成清晰度结论。合并重复解释与辩护，核对仍有审阅价值的取舍、真实影响和恢复条件；同步示例、数量、链接及证据版本，清除模板提示。

发布前将仓库路径转为实际提交的可访问链接。按已有授权发布后，回读远端标题、正文和最新提交，核对成稿一致并检查当前 CI 与评审状态；草稿请求以交付标题和正文结束。

[评估用例](evals/evals.json)用于同一请求、相同材料下的独立对照。执行者只获得请求和必要输入，期望结果留给后续评估。程序检查格式、数量与路径；语义评审核对主要动宾结构、具体对象、标签定位、结论句、段落与列表的选择、证据对应和恢复条件；用户判断中文文风。分别记录这些结果，不用格式通过替代写作效果。
