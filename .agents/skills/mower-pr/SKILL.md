# Mower PR

## 输入与输出

这是依赖 Mower 仓库及其契约的项目本地 skill。输入是本次需求、实际变更范围、验证结果和已有执行或评审记录。输出是一份 PR 标题和正文，使用[正文模板](assets/pr-body.md)，默认只写中文。双语决策记录和词汇表仍按各自契约维护。

写说明沿用[项目工作流](../../AGENTS.md#1-task-selection)，复用本次实施与评审记录。仅要求写 PR 时交付草稿；发布、推送和合并按用户已有授权执行。

## 工作流

1. 确认说明覆盖的需求和变更。分支使用实际比较基准与 head；工作区同时检查暂存、未暂存和范围内未跟踪文件。复用已确认的比较范围，缺少必要基准时获取它。区分已提交内容和准备提交的修改。
2. 按变更范围确定适用要求。读取[根指令](../../../AGENTS.md)、[编码标准](../../../CODING_STANDARDS.md)的相关部分、受影响的子树指令和直接关联契约。使用已有不变量编号和决策依据；概念评估、记录归属与审批沿用[工作流的权责规定](../../AGENTS.md#2-authority-and-record-ownership)。
3. 核对并注明证据对应的代码版本和检查范围。按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)分别整理结构检查、行为测试和语义评估，写实际命令、结果与覆盖行为。同一版本下同一次检查的完整命令、结果和来源集中写一处，其余位置引用具体场景或检查。Before/After 分别保留前后证据，补充检查表按实际需要保留。证据不足的部分写清待核实的行为。复用已有验证结果，必要补查遵循项目的定向离线验证要求。
4. 用[模板](assets/pr-body.md)说明最终变化和必要原因。概览必须放一种最小结构化展示，选择流程图、时序图、伪代码、调用树、组件树、文件树或小段 diff。验证必须保留 Before 和 After，对照同一场景的修改前后证据。截图、实际输出和测试结果优先；修改前运行记录缺失时，在 Before 写已有的旧版代码、文档或评审依据，并标明运行记录待补充。相关契约用直接链接，长解释留在原文。风险写具体受影响的平台、配置、持久化数据或操作，分别说明代码回退方式与状态恢复方式。
5. 简短记录本次已遵守的要求，再按下方文风规则回读。更新已有 PR 时保留仍有效的证据和评审反馈，并标明哪些问题已补做。标题描述最终行为，沿用仓库已有的类型和范围写法。

## 指令记录

用简短条目写本次有证据支持的已遵守要求，标明来源、对应行为和证据位置。优先保留影响本次实现、验证或表达的要求，引用已有验证或执行记录。已有不变量编号直接复用。

注明实际使用的指令版本。已提交的文件用提交及路径定位；使用过未提交的规则或临时用户要求时，保留必要原文或差异。长期项目指令、实际使用的 skills 和本次用户要求分别定位，执行依据与本 PR 修改后的规则分开。

补充测试、评审发现、处理结果和待核实事项保留在验证证据中，写清发生顺序与后补事实。

积累若干 PR 后，复盘从当时指令版本与实际变更重新判断全部适用要求，再核对测试、评审和过程记录。按适用次数统计确认遗漏、后补、证据不足和执行后仍有问题，结合失败案例判断如何调整指令；过程记录不足时记为证据不足。

## 文风

采用[项目文风规范](../mower-prose-standard/SKILL.md)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)。正文以审阅者需要知道的事实为准：

- 开头写触发条件、原行为和修改后行为，让读者直接从 PR 理解改动。
- 写具体主体和动作，例如“切换实例时清空 `last_serial`”。泛泛的“提升稳定性”要换成已有证据支持的行为，缺少事实就缩短说明。
- 精简时保留条件、时序、例外、失败后果与验证限制。命令、字段、数字和正式术语保持准确。
- 一段表达一个主要意思，使用完整、自然的中文句子。原因只写帮助理解方案的部分，执行过程只保留验证证据和指令记录所需的事实。
- 用肯定句直接说明实际行为、适用条件、证据范围和下一步。比如“结构检查覆盖文档格式与链接；Windows 启动待实测”。业务中的拒绝、失败和保留规则按实际语义表达。
- 把声明排除事项、解释证据不能证明什么的防御性句子改写为具体事实或待验证事项。删除开场套话、装饰性总结、自我评价和空泛保证。证据缺口集中写一处，专业术语按需要使用。
- 交付前逐句检查范围说明：把“本次不会……”改成“本次……”，把“不作为……”“不能因此……”改成证据覆盖范围或待验证事项。例如“验证采用文档检查；Windows 启动待实测”。引用用户要求时保留原文。

措辞示例：“完善设备连接逻辑，全面提升健壮性”可改为“切换实例时清空 `last_serial`，避免连接测试复用旧地址”。

模板沿用本机通用 `pr` 的结构化概览、Before/After 证据与风险结构，可直接在项目内使用。文风借鉴 DeepSeek Harness 的[完整事实原则](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-prose-standard/SKILL.md#preserve-the-complete-proposition)和[文档规范](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/AGENTS.md#writing-rules)，PR 的前后变化、实际验证与项目约束按各自用途表达。

## 完成条件

标题与正文对应最终范围，概览有最小结构化展示，证据保留 Before/After，模板提示已替换或删除。每项验证结论有实际依据，已遵守的要求有来源及证据，待核实项集中明确。若要发布，将仓库路径转换为实际仓库及相应提交的可访问链接；授权只覆盖草稿时，到交付草稿结束。

[评估用例](evals/evals.json)覆盖行为修复、仅文档改动和相似任务边界。独立试跑时只给执行者请求和必要输入，期望结果留给后续评估；中文文风是否符合偏好交给用户判断。
