# Mower PR

输入是用户需求、最终 diff、已有验证与评审记录。输出是中文标题和正文，执行范围与发布授权沿用[项目工作流](../../AGENTS.md#1-task-selection)。展示方法改编自 frontmatter 标注的 show-me，保留其三段结构；每段结合 Mower 的行为规则、验证要求和影响范围写具体事实。

## 准备

确认实际 base/head 或工作区范围，读取最终 diff、已有 PR 及受影响模块的规则和子树指令。复用实施记录，按[根指令](../../../AGENTS.md)、[编码规范](../../../CODING_STANDARDS.md)和用户要求核对事实；区分已提交内容与准备提交的修改。将相关事实填入[正文模板](assets/pr-body.md)，更新 PR 时围绕最终方案重写。

## 标题

- 使用 `<type>(<scope>): <description>`；scope 选填，省略时同时省略括号，冒号后保留一个空格。type 限于 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`，按最终 diff 的主要目的选择；scope 使用实际影响的功能、模块或维护对象名称。
- 从最终 diff 提炼主要对象及最终变化，用中文单一动宾短语描述共同实现的结果。业务改动以具体功能、流程或配置为主体，工程改动写明具体维护对象及结果；条件、例外和次要变化放入正文。
- `fix` 写明问题发生的场景与不良现象，或补足的处理逻辑；`feat` 写明新增能力；`docs` 写明具体功能或模块的文档变化。
- 省略开发过程记录、内部局部实现细节、任务追踪单号与临时标记。描述末尾不加句号，不用 `+`、`/` 或 `、` 串联多个独立动作。

## Summary（改动与方案）

先说明具体触发条件、原问题和改动后的结果，再用关键调用、状态分支、短 diff 或职责图解释方案。视图紧邻相关文字，保留理解顺序和边界所需的内容。

结合本次相关处理规则解释方案理由、适用条件和例外，用行为名称链接规则或决策记录。文档、工作流或 skill 改动说明使用者怎样完成实际任务。涉及边界、格式或工作流取舍时，说明收益、主要代价、保留条件和审阅重点。仅保留理解本次改动所需的内容，篇幅与实际变化相称。

## Evidence（验证与评审）

证据按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)组织，并对应 Summary 的关键结论：

- 围绕主要行为或使用场景说明 Before 与 After，定位版本、观察结果及比较方法。已有失败和通过记录直接使用；旧版只有源码或文档依据时写明来源，新版写实际结果。文档、工作流或 skill 改动可对照同一任务的操作与产物；流程定义的变化注明文档依据，实际演练注明执行范围和结果。尚未验证的主要效果保留为具体待验证项。
- 集中记录实际命令、结果和覆盖行为；只提供脚本和解释器版本时保留这两项。注明评审后补做检查对应的版本，区分行为测试、结构检查与静态复核。截图和运行输出用于展示实际可观察结果。
- 将影响本次工作的要求逐项关联到实际动作及证据。过程记录或行为验证缺失时，说明具体缺项。

## Merge Danger（影响与回退）

**可逆性** 用中文说明改动可回退、满足条件后可回退或难以恢复。依据实际变化分别交代改动回退、已有状态及外部操作结果的恢复条件；条件未知时定位待确认环节。

**影响范围** 写清受影响的模块、入口、调用方或使用流程及合并后的后果。结合本次规则说明兼容边界和验证缺口的实际影响，引用 Evidence 中已有结果。

## 表达、链接与依据

采用[项目文风规范](../mower-prose-standard/SKILL.md)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)。正文用中文准确表达主体、条件、动作和结果，规则或约定使用其具体内容名称。

链接文字说明目标内容；提交版本放在链接地址里。需要区分版本时，使用版本在本次工作中的角色描述，命令中的实际版本参数按记录保留。

末尾用简短“依据”定位实际使用的指令版本与影响本次工作的用户要求，采用“来源 + 已发生的动作”，引用正文证据。临时要求或未提交规则保留必要原文或差异；规则本身变化时，分别定位执行依据与修改后的规则。

回读时按证据注明实际验证结果与具体待验证行为。同一事实集中写一处；核对历史归因、方案理由和回退步骤的材料依据。各段篇幅随需解释的事实调整。

## 完成

标题符合上述格式与事实约束，读者能看懂问题如何解决、方案依据、验证结果、适用要求落实情况、合并影响和回退条件。模板提示已替换，链接文字可读，发布链接固定到实际版本；草稿请求以交付标题和正文结束。

[评估用例](evals/evals.json)覆盖行为修复、文档改动、技能新增和原始 diff 写作。事实整理用例检查准确性，原始材料用例检查能否提炼关键方案与证据。评估时用同一请求和材料比较基线与当前正文，期望结果交给后续评估；人工判断方案、证据对应和合并条件是否清楚。
