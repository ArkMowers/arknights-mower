# Mower PR

输入是用户需求、最终 diff、已有验证与评审记录。输出是中文标题和正文，执行范围与发布授权沿用[项目工作流](../../AGENTS.md#1-task-selection)。展示方法改编自 frontmatter 标注的 show-me，保留其三段结构；每段结合 Mower 的行为规则、验证要求和影响范围写具体事实。

## 准备

先确认实际 base/head 或工作区范围，再读取对应的最终 diff、已有 PR 及受影响模块的规则和子树指令。结合已有实施记录，按[根指令](../../../AGENTS.md)、[编码规范](../../../CODING_STANDARDS.md)和用户要求核对事实，并区分已提交内容与准备提交的修改。

正文面向未参与讨论的审阅者，以比较基线到最终方案的变化为主线。旧正文和讨论用于查证，不能单独证明原有行为。区分目标分支的既有行为、已发布的影响与本 PR 内未交付的中间稿。

取材时判断一项事实是否帮助理解最终方案、取舍、验证可信度或合并后果。仅反映改稿、补漏、误解纠正和往返讨论的内容留在讨论记录中。开发中发现的问题若仍影响最终风险或证据范围，就说明其当前影响；用户明确要求保留的审计事项也应如实记录。将筛选后的事实填入[正文模板](assets/pr-body.md)。

## 标题

- 标题遵循 [Conventional Commits 官网最新正式版](https://www.conventionalcommits.org/)。按最终 diff 的主要目的选择 type；scope 选填，使用实际影响的功能、模块或维护对象的英文名称，优先沿用仓库已有写法。
- 从最终 diff 提炼主要对象及最终变化，用自然完整的一句中文概括主要结果，让读者单看标题就能理解解决了什么问题或改变了什么行为。保留识别主要变化所需的场景、问题性质或结果，详细条件、例外和次要变化放入正文。
- 业务修复写清具体错误或修复后的行为，保留辨认问题所需的条件；文档和工程改动写出具体规则或使用方式怎样改变。只写维护对象和“规范”“完善”等动作，尚未说明主要变化。不要为了缩短标题省略这种区别。
- 省略开发过程记录、内部局部实现细节、任务追踪单号与临时标记。描述末尾不加句号，不用 `+`、`/` 或 `、` 串联多个独立动作。

## Summary（改动与方案）

先说明具体触发条件、原问题和改动后的结果，再用关键调用、状态分支、短 diff 或职责图解释方案。视图紧邻相关文字，保留理解顺序和边界所需的内容。

解释方案时，用本次相关处理规则说明理由、适用条件和例外，并用行为名称链接规则或决策记录。若本次修改的是文档、工作流或 skill，就围绕使用者完成实际任务的过程解释这些变化。若方案涉及边界、格式或工作流取舍，同时交代收益、主要代价、保留条件和审阅重点。这些说明以读者理解本次改动为限，篇幅与实际变化相称。

## Evidence（验证与评审）

证据按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)组织，并对应 Summary 的关键结论：

- 围绕主要行为或使用场景说明 Before 与 After，定位版本、观察结果及比较方法。Before 说明比较基线的行为，不能把未交付的中间稿当作用户已遇到的问题；旧版只有源码或文档依据时写明来源。对文档、工作流或 skill 改动，可比较同一任务的操作与产物，分别注明规则定义与实际演练的依据。
- 集中记录实际命令、结果、覆盖行为及对应版本；只提供脚本和解释器版本时保留这两项。区分行为测试、结构检查与静态复核，将未验证的主要效果写成具体待验证项。审阅者应能判断最终版本具有什么证据，无须复述每次补测经过。
- 示例、对照输出和检查结果都要核对其适用版本。规则变化后仍引用旧结果时，明确它能支持的结论；过时示例删除或更新。新写的说明示例应标明用途，不能冒充实际生成或测试结果。缺少最终版本的执行记录时如实保留缺口。

## Merge Danger（影响与回退）

**可逆性** 用中文说明改动可回退、满足条件后可回退或难以恢复。依据实际变化分别交代改动回退、已有状态及外部操作结果的恢复条件；条件未知时定位待确认环节。

**影响范围** 写清受影响的模块、入口、调用方或使用流程及合并后的后果。结合本次规则说明兼容边界和验证缺口的实际影响，引用 Evidence 中已有结果。

## 表达、链接与依据

采用[项目文风规范](../mower-prose-standard/SKILL.md)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)。正文用中文准确表达主体、条件、动作和结果，规则或约定使用其具体内容名称。

先围绕一个审阅问题组织一段，再检查句内分句和相邻句子的关系。说明同一对象的原因、处理方式、条件或后果时，关系须有材料支持；独立事项分句、分段或并列列出。不能用逗号、分号或连接词把无关事实接成推论。

链接文字说明目标内容；提交版本放在链接地址里。需要区分版本时，使用版本在本次工作中的角色描述，命令中的实际版本参数按记录保留。

末尾用简短“依据”定位实际使用的指令版本，以及影响最终方案、验证或交付边界的要求，采用“来源 + 已发生的动作”并引用正文证据。临时要求或未提交规则只保留核对这些结论所需的原文或差异；规则本身变化时，分别定位执行依据与修改后的规则。无需重述用户怎样提出反馈或逐轮修改的经过。

回读时检查标题是否说明具体变化，正文是否脱离讨论上下文仍能理解，分句之间是否有实际关系。更新已有 PR 时，按取材标准重新核对原文，保留仍适用的方案、取舍、证据和回退条件，同时清除失效结论与中间过程。逐一核对示例、数量、链接和验证版本是否与最终方案一致；同一事实集中写一处。

## 完成

标题能独立说明具体变化；正文无需讨论背景即可解释最终方案、依据、验证与合并后果，句内和句间关系清楚，示例与证据归属准确。模板提示已替换，链接文字可读，发布链接固定到实际版本。发布或更新后回读远端标题和正文，核对其内容与已核验的成稿一致；草稿请求以交付标题和正文结束。

[评估用例](evals/evals.json)覆盖行为修复、文档改动、技能新增和原始 diff 写作，用于检查事实准确性和方案提炼。评估时用同一请求和材料比较基线与当前正文，执行者只获得请求和必要输入，期望结果交给后续评估。人工评审结合具体用例判断句间关系、方案与证据的对应及合并条件是否清楚。
