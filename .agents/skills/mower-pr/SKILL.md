# Mower PR

输入是需求、最终 diff、已有 PR 和验证记录，输出是中文标题与正文。执行范围和发布授权沿用[项目工作流](../../AGENTS.md#1-task-selection)。正文采用 show-me 的 Summary、Evidence、Merge Danger 三个栏目，按下面的流程组织事实。

## 1. 提取最终事实

确认实际 base/head 或工作区范围，读取完整 diff、已有 PR 和相关子树指令。已有 PR 的改动范围以实际 base/head 为准；评审修复或写作演练使用的版本只定位各自的验证结果。按[根指令](../../../AGENTS.md)、[编码规范](../../../CODING_STANDARDS.md)及用户要求核对材料，区分已提交内容与准备提交的修改。

先按主要变化整理事实项，将实际对象、修改前的行为或要求、修改后的行为或要求、方案理由、验证结果及来源分别记录。同时记录材料中的既有产物和本次交付的状态，分别确定影响范围与恢复对象。

对照文档时，读取两版原文，确认与本次变化有关的具体规定，以及本次补充了哪些原文未规定的要素。文档和工程改动说明使用或维护方式的变化。

文档要求展开为具体格式、内容或操作。材料只给概括时，先补读原文；原文仍只提出方向时，写清能核实的要求及与本次变化有关的未规定内容；缺少必要原文时，记录缺少的依据。事实项写出这些具体内容，原文摘录单独作为来源。

交接提供事实项、依据位置和交付边界；写作者直接读取 skill 与模板，再重新组织句子。版本与来源单独定位。材料整理完成的条件是每项变化均能说明实际对象怎样改变，以及依据或相关缺项是什么。

从材料中选出解释最终方案、取舍、证据可信度或合并后果的事实。修改经过仅在解释这些事实或满足明确审计要求时进入正文；保留已发布问题的实际影响、相关验证失败和重要覆盖缺口。更新已有 PR 时围绕最终 diff 重新组织正文。

## 2. 合成标题

从提纲选出核心变化、具体对象和前后结果，先确定标题的完整宾语，再选择动作并合成单一动宾短语。一个主要动作支配一个完整对象；对象中可以包含辨认变化所需的条件、场景和结果。次要变化进入正文，不将多条完整规则压入标题。

标题必须遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。以下规则补充项目类型选择和中文表达要求。

格式为 `<type>(<scope>): <description>`。type 从 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 中按主要目的选择。scope 选填，省略时一并省略括号，采用项目已有英文范围名称；冒号后一个空格，中文描述末尾不加句号。

标题的宾语采用需求与最终 diff 共同指向的对象，保留材料给出的名称与种类；描述写出该对象在修改前后的差异，修改目的放在正文。type 表示改动性质。描述不含开发过程编号或临时标记，不用 `+`、`/`、`、` 串联不同动作。

## 3. 按审阅顺序组织段落

同一 PR 经过多轮实施或评审后，由未接触开发讨论的子 Agent 或独立会话重新生成标题和正文。执行者直接读取本 skill 和正文模板，只接收用户需求、实际 PR base/head、完整最终 diff、已核实的事实项及验证记录、项目指令。

使用[正文模板](assets/pr-body.md)，先写各主题的加粗短标签和结论句：按主要变化排列 Summary 的结论，为每项结论安排对应的 Evidence 结果，再写 Merge Danger 的影响和恢复条件。提纲能单独说明改动、验证发现与合并后果后，才补解释、证据和条件。展开时只使用已筛选事实，不从原始讨论重新摘抄。

每个主题用加粗短标签和完整结论句引出，再按内容关系选择结构：

- 有先后顺序的操作或推导步骤，用编号列表，每步单独换行。
- 同层且可分别核对的规则、结果或条件，用 Markdown 项目列表，每项单独换行。
- 解释、因果或递进关系，用连贯自然段；一句能清楚表达的简短枚举无需拆成列表。

列表前留空行，每项保留自身的条件和例外，不用逗号或分号把多项独立要点挤在同一段。同一主题可以包含引导段和列表，标签只放在主题开头，列表项不必重复加粗。Summary 和 Evidence 中对应变化使用可相互辨认的主题标签；Merge Danger 使用影响范围和可逆性定位后果与恢复条件。

**Summary** 首段交代原问题和最终变化，后续段落解释方案及必要取舍。小改动可用一段完成。

方案包含同一输入到多项输出的对应、组件职责分工或步骤依赖时，用关系图说明，并紧邻整体方案放置。纯文本关系图使用标记为 `text` 的 Markdown 代码块，节点分行，以缩进、分支线和箭头区分并列对应与先后依赖。节点写明实际对象，连线表达已核实的关系；已有图仍符合最终方案时，保留必要节点和呈现结构，按最终事实校正文字。局部代码差异适合用短 diff 展示。

**Evidence** 逐项对应 Summary 中的变化，每项说明验证对象、输入条件、观察结果、来源和未验证范围。比较不同版本或方法时，先说明各自角色及共用输入，再保留 **修改前 / 修改后** 的对应结果；分项或表格保留影响结论的条件与例外。没有执行记录时注明文档或源码依据及缺少的运行结果。一次检查支持多项变化时，集中交代覆盖范围；未覆盖的变化明确列出。

**Merge Danger** 先说明采用后的实际影响，再列出材料中已明确的回退对象与恢复动作。逐个核对对象是否会随代码或文档回退恢复，需单独处理的对象及条件分别保留；条件未知时指出缺项。风险已在 Evidence 说明时，此处只补合并决策或恢复所需的信息。

采用[项目文风规范](../mower-prose-standard/SKILL.md)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)。每段说明一个审阅问题。先确定实际主体及其动作，再将对象、条件和结果组成完整句子，用普通动词说明具体行为或要求。版本、材料类别和比较方法在来源或方法说明中定位。相邻句子按实际的因果、条件、递进或并列关系衔接，需要时补足主语和连接词。

首次引入的对象交代它在方案中的用途和本次变化，指代词对应前文已说明的对象。另一个对象的变化单独成段，并说明它与已述方案的关系。

## 4. 核验证据和依据

按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)区分程序检查、行为观察及语义评审。对照必须使用同一场景并定位两侧依据；只有旧版源码或文档时，明确其来源。说明示例、给定材料和本次实际执行结果分别归属，旧结果只支持它实际验证过的版本与结论。

先逐项关联 Summary 的主要变化与证据：行为变化对应已执行的验证对象、条件及结果，文档要求的变化对应两版原文的具体差异，尚无验证的变化对应其具体缺项。一次检查支持多项变化时，说明实际覆盖的对象，再集中记录方法。

将工具结果翻译为具体事实：什么通过、什么未通过、原因及影响。正文保留判断结论所需的比较版本、方法和代表性差异；完整草稿、逐项日志和文件摘要按需保存在独立记录中，正文引用结果或链接。没有独立记录时，在一处简短附注必要方法和版本。正文不以退出码、诊断码或整串参数充当结论。链接文字说明内容，版本放入链接目标。

验证结论写明实际通过或失败的检查，以及影响主要结论的待验证行为。同一缺口集中写一处；真实失败说明失败对象、原因和影响。缺少的材料、未测量的指标或未执行的项目仅在影响主要结论或属于明确审计要求时进入正文。

简短记录实际使用的指令版本，以及影响方案、验证或交付边界的要求，采用“来源 + 已发生的动作”。正文已有来源和证据时直接复用；尚未定位的依据可在末尾集中补充，不重复解释规则。临时要求保留核对结论所需的原文，规则变化时区分执行依据与交付版本。

## 5. 回读与交付

作者逐项核对完整正文：每项 Summary 变化均能定位到 Evidence 的具体结果、原文差异或缺项；首次出现的对象已解释用途与变化；每个回退对象已说明恢复动作和条件。通读自然段，核对主语、指代和句间关系，确认旧行为、文档要求及检查结果已写出具体内容。

发现概括性表述、对象用途不明或对应事实遗漏时，重新核实相关事实项并重写该段，再按相同场景复核。交付条件是具体内容、证据对应和恢复条件均已落实到成稿。

再单独读标题、标签和结论句，检查对象和结果能否定位到正文。并列要点逐项核对，有序步骤核对先后关系；核对每个首次出现对象的用途、取舍和恢复条件，更新数量、链接及证据版本，清除模板提示。

发布前将仓库路径转为实际提交的可访问链接。按已有授权发布后，回读远端标题、正文和最新提交，核对成稿一致并检查当前 CI 与评审状态；草稿请求以交付标题和正文结束。

[评估用例](evals/evals.json)用于同一请求、相同材料下的独立对照。执行者只获得请求和必要输入，期望结果留给后续评估。程序检查格式、数量与路径；语义评审核对主要动宾结构、具体对象、标签定位、结论句、段落与列表的选择、证据对应和恢复条件；用户判断中文文风。分别记录这些结果，不用格式通过替代写作效果。
