# Mower PR

本 skill 在 Arknights Mower 仓库内使用，文档链接按仓库布局解析。

输入是需求、最终 diff、已有 PR 和验证记录，输出是中文标题与正文。执行范围和发布授权沿用[项目工作流](../../AGENTS.md#1-task-selection)。正文使用 Summary、Evidence、Merge Danger 三个栏目组织审阅事实；需要进入更新日志时，将简短的 Changelog 段作为 Summary 第一段。

## 1. 提取最终事实

确认实际 base/head 或工作区范围，读取完整 diff、已有 PR 和相关子树指令。已有 PR 的改动范围以实际 base/head 为准；评审修复或写作演练使用的版本只定位各自的验证结果。按[根指令](../../../AGENTS.md)、[Arknights Mower 项目编码规范](../../../CODING_STANDARDS.md)及用户要求核对材料；项目编码规范规定共享行为规则、并发与资源要求和验证要求。区分已有 commit 与尚未创建 commit 的修改。

按[交接模板](assets/pr-handoff.md)记录整体范围、scope 选择和主要事实项，包含实际对象、前后变化、方案理由、验证结果及原始依据。同时记录既有产物与本次交付状态，分别确定影响范围与恢复对象。

筛选前从原始材料确认审阅必需的事实：触发条件与现场后果、失败原因、相关版本各自的行为、同输入对照，以及已有状态或数据的影响与恢复条件。只保留与本次判断有关的项目；未提供的关键材料标为缺项。未进入 Git diff 的本地数据修复或外部产物，也按其实际影响判断是否需要交接。

对照文档时，读取两版原文，确认与本次变化有关的具体规定，以及本次补充了哪些原文未规定的要素。文档和工程改动说明使用或维护方式的变化。

文档要求展开为具体格式、内容或操作。格式说明给出实际格式，流程说明给出动作及顺序；原文只提出名称或方向时，记录与本次变化有关的未规定内容。材料只有概括时先补读原文，缺少必要原文时记录缺少的依据。事实项只写核实后的具体内容，概括性原句留在原文中作为来源。

交接前筛选事实，只保留最终变化、必要设计理由、实际验证及重要缺口、真实影响与恢复条件，以及核对这些事实必需的来源。每项说明审阅者据此判断什么；没有审阅用途的工作记录留在聊天或工作区。再从必需事实反向核对交接，确认精简后仍能判断问题、方案、证据和恢复条件。方案关系另列节点、连线及含义，已有图作为核对来源。

负责写作的 Agent 直接读取 skill 与模板，再重新组织句子。版本与来源单独定位。材料整理完成的条件是每项变化均能说明实际对象怎样改变，以及依据或相关缺项是什么。

操作经过仅在影响最终方案、证据可信度、实际后果、恢复责任或满足用户明确审计要求时进入交接与正文。判断同样适用于 rebase、冲突数量、改稿轮次、代理分工、临时环境排障、工作树使用和要求落实自述。保留已发布问题造成的数据遗漏或损失、失败后恢复所需的条件与责任，以及真实验证失败和重要覆盖缺口。缺少材料时报告具体缺项，不编造操作或过程合规。更新已有 PR 时围绕最终 diff 重新组织正文。

## 2. 合成标题

读取 mower-commit 主文件中的[共享标题规则](../mower-commit/SKILL.md#title-rules)。从整个 PR 的需求、最终 diff 和已筛选事实形成独立范围陈述，区分主线与支撑措施，再生成标题。该陈述及范围核对属于写作交接，不进入正式正文。标题概括整个 PR 的主要变化，正文说明具体措施和完整范围；一次 commit 的标题只依据该次 commit。

## 3. 按审阅顺序组织段落

同一 PR 经过多轮实施或评审后，由未参与开发讨论的子 Agent 或新会话中的 Agent 重新生成标题和正文。该 Agent 直接读取本 skill、正文模板及指定版本的共享文风与术语来源，接收自然任务请求及用户明确的格式、语言和称呼偏好、实际 PR base/head、完整最终 diff、独立范围陈述、已筛选事实及其必要来源。完整 diff 用于核对范围，不能把原始讨论或未经筛选的日志作为写作交接。缺少隔离能力时说明限制。

使用[正文模板](assets/pr-body.md)，先写各主题的加粗短标签和结论句：按主要变化排列 Summary 的结论，为每项结论安排对应的 Evidence 结果，再写 Merge Danger 的影响和恢复条件。提纲能单独说明改动、验证发现与合并后果后，才补解释、证据和条件。展开时只使用已筛选事实，不从原始讨论重新摘抄。

按 mower-commit 主文件中的[Changelog 写作规则](../mower-commit/SKILL.md#changelog-rules)，写一个脱离标题和正文仍能说明本次具体变化的简短 `Changelog:` 段，作为 Summary 第一段，后面留空行。后文承接摘要解释问题、原因、方案和详细使用条件，恢复操作与验证记录放在对应审阅主题中。更新 PR 时也按当前最终 diff 重写这一段。

每个主题用加粗短标签和完整结论句引出，再按内容关系选择结构：

- 有先后顺序的操作或推导步骤，用编号列表，每步单独换行。
- 同层且可分别核对的规则、结果或条件，用 Markdown 项目列表，每项单独换行。
- 解释、因果或递进关系，用连贯自然段；一句能清楚表达的简短枚举无需拆成列表。

列表前留空行，每项保留自身的条件和例外，不用逗号或分号把多项独立要点挤在同一段。同一主题可以包含引导段和列表，标签只放在主题开头，列表项不必重复加粗。Summary 和 Evidence 中对应变化使用可相互辨认的主题标签；Merge Danger 使用影响范围和可逆性定位后果与恢复条件。

**Summary** 首段说明本次主要变化，需要发布说明时使用 `Changelog:` 标记；后续段落解释问题、方案、使用条件及必要取舍。篇幅取决于审阅问题、证据和后果的复杂度；这些内容简单时可用一段完成。

方案包含同一输入到多项输出的对应、组件职责分工或步骤依赖时，用关系图说明，并紧邻整体方案放置。纯文本关系图使用标记为 `text` 的 Markdown 代码块，节点分行，以缩进、分支线和箭头区分并列对应与先后依赖。节点写明实际对象，连线表达已核实的关系；已有图仍符合最终方案时，保留必要节点和呈现结构，按最终事实校正文字。先确定要解释的关系，再选择最小展示：步骤依赖用关系图，局部代码变化用短 diff，同输入结果比较用对照表。正文仍需解释的职责或依赖关系由关系图呈现，局部 diff 和结果表分别说明变化与证据。

关系图的展示方式参考 HumanLayer 的 [show-me](https://github.com/humanlayer/skills/blob/main/plugins/show-me/skills/show-me/SKILL.md)。

**Evidence** 逐项对应 Summary 中的变化，每项说明验证对象、输入条件、观察结果、来源和未验证范围。比较不同版本或方法时，先说明各自角色及共用输入，再保留 **修改前 / 修改后** 的对应结果；分项或表格保留影响结论的条件与例外。没有执行记录时注明文档或源码依据及缺少的运行结果。一次检查支持多项变化时，集中交代覆盖范围；未覆盖的变化明确列出。

**Merge Danger** 先按方案采用后的状态说明实际影响，确定代码或文档、已有状态及方案产生的产物各自的恢复对象，再依据材料列出回退与独立恢复动作。交付边界只有影响采用或恢复条件时才进入正文。

逐个核对对象是否会随代码或文档回退恢复，需单独处理的对象及条件分别保留；条件未知时指出缺项。风险已在 Evidence 说明时，此处只补合并决策或恢复所需的信息。

按[项目文风规范的中文表达方法](../mower-prose-standard/SKILL.md#chinese-prose)和[术语来源](../mower-prose-standard/references/mower-terminology-guide.md)复核成稿。每段说明一个审阅问题。

栏目和步骤直接写出名称。模型负责的操作以 Agent 为主语，需要区分职责时说明负责写作、复核或评估的 Agent。版本、材料类别和比较方法在来源或方法说明中定位。

首次引入的对象交代它在方案中的用途和本次变化。另一个对象的变化单独成段，并说明它与已述方案的关系。

## 4. 核验证据和依据

按[验证与报告规则](../../AGENTS.md#4-verification-and-reporting)区分程序检查、行为观察及语义评审。对照必须使用同一场景并定位两侧依据；只有旧版源码或文档时，明确其来源。说明示例、给定材料和本次实际执行结果分别归属，旧结果只支持它实际验证过的版本与结论。

先逐项关联 Summary 的主要变化与证据：行为变化对应已执行的验证对象、条件及结果，文档要求的变化对应两版原文的具体差异，尚无验证的变化对应其具体缺项。一次检查支持多项变化时，说明实际覆盖的对象，再集中记录方法。

将工具结果翻译为具体事实：什么通过、什么未通过、原因及影响。正文保留判断结论所需的比较版本、方法和代表性差异；完整草稿、逐项日志和文件摘要按需保存在独立记录中，正文引用结果或链接。没有独立记录时，在一处简短附注必要方法和版本。正文不以退出码、诊断码或整串参数充当结论。链接文字说明内容，版本放入链接目标。

验证结论写明实际通过或失败的检查，以及影响主要结论的待验证行为。同一缺口集中写一处；真实失败说明失败对象、原因和影响。缺少的材料、未测量的指标或未执行的项目仅在影响主要结论或属于明确审计要求时进入正文。

规范依据仅在解释方案、证据或恢复条件确有必要，或用户明确要求审计时出现。引用与结论有关的具体要求及来源，正文已有事实时直接复用。指令版本、工作流程选择和落实自述不是默认输出项。规则本身发生变化时，以两版原文定位变化；这不要求附上执行日志。

## 5. 回读与交付

负责最终复核的 Agent 直接回读原始依据：确认正文事实有依据，再将必需事实逐项定位到正文，填写交接表中的落点。复核包含未进入交接或 diff、但影响审阅的事实；省略项须确认不影响方案、证据或恢复判断。交接表保存在工作区。

每项 Summary 变化均能定位到 Evidence 的具体结果、原文差异或缺项；首次出现的对象已解释用途与变化；每个回退对象已说明恢复动作和条件。按第 3 步的条件核对方案关系及其展示，确认所需关系图、局部 diff 或对照结果已经进入成稿。按共享中文表达方法通读成稿，确认旧行为、文档要求及检查结果已写出具体内容。

发现无法辨认实际变化的概括性表述、对象用途不明或对应事实遗漏时，重新核实相关事实项并重写该段，再按相同场景复核。交付条件是具体内容、证据对应和恢复条件均已落实到成稿。

先按共享规则脱离正文检查标题能否直接说明主线，再对照需求与完整最终 diff 核实对象、变化及不可省略的条件，避免误述范围。单独阅读 Changelog 并对照两版事实，确认它保留同一主要变化及决定含义的信息，能辨认本次改动而非只描述改后流程；按共享规则取舍细节，具体措施在 Summary 后文展开。再读标签和结论句，核对 scope、并列要点、步骤先后、首次文档名称与用途、恢复条件、数量、链接和证据版本，清除模板提示。

发布前将仓库路径转为实际审阅 commit 的可访问链接，按[正式文本检查入口](../../../scripts/README.md#formal-text-checks)检查完整成稿；每次编辑 PR 元数据同样执行。程序检查标题格式、栏目、模板残留和术语，事实覆盖、scope 适用性与展示选择由上述复核确认。用户要求开 PR 时默认发布为可审阅状态，明确要求 Draft PR 时才使用 Draft。发布后回读标题、正文和最新 commit，重新执行同一检查，核对成稿一致及当前 CI、评审状态；只要求文案草稿时交付文本。

[评估用例](evals/evals.json)用于同一请求、相同原始材料下的独立对照。各版本按自己的流程筛选和交接，旧版不使用新版筛选后的材料。隔离执行者只获得自然任务请求、共同输入和指定版本的 skill 及依赖，作者分析、预期标题和评分标准留给评估方。程序检查格式、扫描与路径；生成观察记录实际事实保留、遗漏和标题范围；用户判断文案质量。分别报告这些结果、可获得的统计及缺口，有限对照不代表所有输入或模型。

验证整理、独立写作、最终复核及发布回读的连贯执行时，按[完整交接评估](evals/README.md)运行。
