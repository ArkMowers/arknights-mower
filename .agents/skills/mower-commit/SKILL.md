# Mower Commit

输入是用户需求、目标范围的完整 diff 和已有检查记录，输出是中文提交标题、必要正文及已授权提交的结果。[Arknights Mower Agent 工作流程](../../AGENTS.md#1-task-selection)规定任务范围与完成条件；[项目文风规范](../mower-prose-standard/SKILL.md)规定表达和术语核对方法。

## 1. 确认提交范围

1. 读取工作区状态、工作区 diff 和暂存 diff，选择本次文件或代码片段。核对已有暂存内容的归属，保留其他修改原有的暂存状态。
2. 历史提交或比较范围使用对应两版及完整 diff。分别定位目标、基线和背景；相邻提交、当前 HEAD 和旧提交说明只用于定位背景。
3. 核实实际对象、操作、触发条件、修改前后的行为及来源。用[Arknights Mower 项目术语表](../../../CONTEXT.md)及其[中文版](../../../CONTEXT.zh.md)确认概念，再从对应版本的调用者、界面和子系统说明定位具体场景；术语表未收录的对象也按这些来源定位。
4. 区分本次新增和基线已有能力，保留重要配置、失败处理和兼容条件。因果和后果分别核对调用者、测试或现场记录，区分实际观察、源码行为和待验证推断。
5. 写出独立范围陈述：谁使用或维护什么、修改前后有什么具体差异。按[标题规则](#title-rules)判断主次，需要拆分提交时分别确定范围；文件数、行数和材料顺序不决定主线。该陈述属于工作材料。

## 2. 隔离撰写

由未参与本次开发和改稿讨论的子 Agent 或新会话中的 Agent 撰写。启动时关闭工作上下文继承，只交接自然任务请求、已核实的范围陈述、业务对象与事件及其来源、对应两版及完整 diff、实际检查记录；开发讨论、已有草稿和预期标题留在工作材料中。

写作 Agent 直接读取本 skill、项目文风规范及其关联的中英文术语来源，按下面的标题、正文和发布说明规则完成成稿。事实或范围需要修正时，交给新的隔离 Agent 按修正后的材料重新撰写；缺少隔离能力时说明限制，并依据已核实材料完成说明。

<a id="title-rules"></a>
## 3. 标题规则

本节供提交与 `mower-pr` 共用：提交标题依据一次提交的完整 diff，PR 标题依据整个 PR 的最终 diff。PR 写作只复用本节和发布说明规则，执行范围由 `mower-pr` 确定。

标题面向了解 Mower、但未参与本次开发的维护者。先从需求和两版事实确定主要动作，中文描述优先用动宾结构写清动作及对象，再补理解变化所必需的条件和结果，最后选择 type 和 scope；所有类型都按同一标准确认实际变化，类型名称不代替中文描述中的对象、动作和结果。

- 修复说明项目中的实际操作、触发条件和错误表现，区分外部组件的响应与项目对该响应的处理。新增能力说明现在支持什么操作及必要条件；行为调整说明处理方式怎样改变。工程、文档和 skill 改动同样写出操作、检查或使用要求的具体差异；规则归属和文件位置的变化按其实际维护用途说明，不能代替同时发生的内容变化。
- 使用来源已核实的具体名称和操作，保留辨认变化所需的对象与情境；概括时仍写明具体分支、页面、服务、数据或检查规则。生成、转换或提取先区分产物、来源对象和采用的具体内容，再写清它们的关系；内容选择顺序改变时，标题保留本次改变的优先或回退关系。保留辨认产物和内容所需的标记或设置名称。skill 名称、正式文档名称和代码标识保留原名，不能仅凭函数名或通用类别推定业务对象。
- 按需求和实际影响核对主次。多项措施共同构成同一具体结果时，概括该结果并保留实际对象和场景，参数及实现步骤进入正文。另行改变使用、维护规则或产物结果的内容分别判断，不能只因服务于同一宽泛目的或放在同一文件而省略。多个对象的动作不同时写清各自归属；另一项主要变化仍需说明或拆分，不能靠正文补足标题范围。
- 错误名称、内部状态、流程或职能标签先按调用者、界面和源码展开为“谁在做什么、在哪一步遇到什么问题”的事实，再用读者能辨认的业务操作、条件和具体表现组织标题。配置变化写明实际设置项控制的量。已核实的具体场景可以说明问题发生在哪里，适用范围另按源码和证据核对，不把该场景写成唯一适用条件，也不把预期收益写成已验证效果。

采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 格式 `<type>(<scope>): <description>`，冒号后一个空格，中文描述末尾不加句号。type 按主要目的从 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 选择；源码是否改变或改动大小不能单独决定类型。

scope 按主要维护对象优先采用项目已有英文范围名称；多个对象属于同一维护范围时使用共同范围，没有合适范围时省略括号及 scope。描述不含追踪编号、开发过程标记或临时文件名，不用 `+`、`/`、`、` 串联不同动作；真实配置、接口和文件名称按辨认变化的需要保留。

确定主要变化后，核对项目已有 scope 是否能准确标明该范围；有明确对应时使用，跨范围且无合适名称时可省略。scope 补充英文归属，中文描述仍须说明对象及结果，选择依据保留在写作交接或提交工作材料中。

复核时，对照完整 diff 和独立范围陈述，逐项指出标题怎样覆盖主要对象及具体差异；省略项重新核实主次，正文已有说明不能代替范围判断。去掉格式前缀，按[共享中文表达方法](../mower-prose-standard/SKILL.md#chinese-prose)脱离正文读出描述，确认读者能复述对象、操作、必要条件和实际变化。读者仍需追问具体内容、状态或失败指什么时，回到来源重写。逐项回到对应版本的来源确认对象、事件、因果、结果及新旧能力的归属，再核对格式与类型。不能以存在点击、取消或重试调用代替其最终结果的证据；格式通过或字数更少不证明语义清楚。

## 4. 必要正文

标题之外没有理解变化或判断后果必需的信息时，只交付标题。需要正文时，补充具体问题与原因、主要取舍、重要使用或兼容条件，承接标题展开，篇幅由信息决定，不逐项复述完整 diff 或 PR 正文。

验证只使用真实执行记录，区分历史记录与本次执行。常规检查、测试数量和开发经过放在交付记录或 PR 中；实际失败或未验证范围影响理解改动或判断后果时才写入正文，并保留影响结论的条件。正文首次出现的简称、类别和指代说明其对象，共同范围只覆盖实际共用规则的步骤。

<a id="changelog-rules"></a>
## 5. 发布说明规则

发布说明供使用者和维护者独立阅读，默认用一句话交代最主要的具体变化，保留辨认对象、触发条件和结果所必需的信息。新增能力说明支持的操作及决定其可用性的启用条件或限制。数据补录、运行环境、迁移与恢复操作和验证详情分别进入 PR 的对应正文；直接提交需要这些说明时，放在摘要之后的必要正文。工程、文档和 skill 改动同样说明具体使用或维护方式的变化；性能、因果和效果分别核对证据。

- 通过 PR 合入，包括普通 merge、squash 和 rebase merge，需要进入更新日志时，将一个以 `Changelog: ` 开头的说明段作为 Summary 第一段，标记与文字写在同一行，后面留空行。依据整个 PR 的最终 diff 写说明；每个提交只说明自己的改动，PR 整体说明不复制到各提交。后文承接摘要解释问题与方案，不拼接中间提交记录或另写重复摘要。
- 没有 PR 的直接提交，标题足以作为发布说明时使用标题；需要独立说明时，将 `Changelog:` 摘要作为正文首段，后留空行。其后只补理解变化或判断后果必需的正文。普通提交不强制发布说明，PR 关联查询失败时仍按各提交自身的说明或标题兼容。
- 交付前确认这一句能独立说明主要变化及成立条件，并区分本次新增与已有能力。局部策略或合成测量不扩大为所有场景的实测性能结论。

[跨平台发布说明](../../../doc/release-platforms.md#发布说明)规定[更新日志生成器](../../../scripts/changelog_generator.py)的提取与兼容边界：优先读取实际合并 PR 的发布说明，再读取提交正文的保留说明，均无有效说明时使用去除格式前缀的提交标题。合并归并、回退抵消和已发布内容复用以该文档为准；只提取发布说明段，已有提交和更新日志保留原文。

## 6. 交付与提交核对

1. 只请求提交文案时，交付标题和必要正文。历史提交或多份草稿在文案之外标明来源；演练案例与当前目标分别展示。
2. 请求执行提交时，按已有授权暂存本次改动，读取实际使用的完整暂存 diff，重新核对标题、正文和范围。
3. 按[项目验证要求](../../AGENTS.md#4-verification-and-reporting)完成相关检查并记录实际结果。多行说明写入临时文件，通过 `git commit --file` 提交，保留原有换行。
4. 提交后回读生成的说明和 diff，确认内容符合范围、其他修改的暂存状态得到保留。交付实际提交、主要变化和检查结果；推送或发布 PR 沿用对应任务的授权。

[评估用例](evals/evals.json)在相同请求和原始材料下比较新旧版本。程序检查格式和指定术语，对照材料核验事实覆盖，用户判断文案是否清楚；分别报告结论。
