# Mower Commit

输入是用户需求、目标范围的完整 diff 和已有检查记录。普通提交输出中文标题、必要正文及已授权创建 commit 的结果；PR 合并直接执行[合并流程](#pr-merge)，保留平台默认说明。[Arknights Mower Agent 工作流程](../../AGENTS.md#1-task-selection)规定任务范围与完成条件；[项目文风规范](../mower-prose-standard/SKILL.md)规定表达和术语核对方法。

## 1. 确认 commit 范围

1. 读取工作区状态、工作区 diff 和暂存 diff，选择本次文件或代码片段。核对已有暂存内容的归属，保留其他修改原有的暂存状态。
2. 历史 commit 或比较范围使用对应两版及完整 diff。分别定位目标、基线和背景；相邻 commit、当前 HEAD 和旧 commit 说明只用于定位背景。
3. 核实实际对象、操作、触发条件、修改前后的行为及来源。按[共享业务用语查找方法](../mower-prose-standard/references/mower-terminology-guide.md#business-wording)确认对象和事件的已有称呼及适用含义，保留原始来源与版本供交接。
4. 区分本次新增和基线已有能力，保留重要配置、失败处理和兼容条件。因果和后果分别核对调用者、测试或现场记录，区分实际观察、源码行为和待验证推断。
5. 写出独立范围陈述：谁使用或维护什么、修改前后有什么具体差异。按[标题规则](#title-rules)判断主次，需要拆分 commit 时分别确定范围；文件数、行数和材料顺序不决定主线。该陈述属于工作材料。

用户或仓库上下文将安全问题标为敏感、需暂缓披露或不宜公开时，在拟定分支名和 commit 文案前执行[公开安全元数据规则](../mower-prose-standard/SKILL.md#public-security-metadata)。推送后的分支名、标题、正文和 Changelog 都是公开元数据；即使用户只要求 PR 文案省略敏感事实，这些位置也沿用同一披露边界。使用真实但不暴露弱点的维护对象、行为边界或验证结果概括完整 diff，不写漏洞类别、严重程度、可识别弱点的位置、攻击条件、利用过程、载荷、概念验证、秘密值或确认缺少某项控制的文字。

## 2. 隔离撰写

由未参与本次开发和改稿讨论的子 Agent 或新会话中的 Agent 撰写。启动时关闭工作上下文继承，交接自然任务请求及用户明确的格式、语言和称呼偏好、已核实的范围陈述、scope 及其来源、业务对象与事件、已核实的业务用语及适用含义和来源、对应两版及完整 diff、实际检查记录；开发讨论、已有草稿和预期标题留在工作材料中。

写作 Agent 直接读取本 skill、项目文风规范及其关联的中英文术语来源，按下面的标题、正文和发布说明规则完成成稿。事实或范围需要修正时，交给新的隔离 Agent 按修正后的材料重新撰写；缺少隔离能力时说明限制，并依据已核实材料完成说明。

<a id="title-rules"></a>
## 3. 标题规则

本节规范 Agent 撰写的普通 commit 标题，并供 `mower-pr` 共用：commit 标题依据一次 commit 的完整 diff，PR 标题依据整个 PR 的最终 diff。PR 写作只复用本节和发布说明规则，执行范围由 `mower-pr` 确定。

标题供维护者在 commit 历史或 PR 列表中辨认主要改动。先从需求和两版事实确定主要动作及其直接支配的宾语，中文描述用这一动宾结构起笔，再补足辨认变化所需的内容，选择 type 和 scope。仅引出后续动作的变化提示不能代替主要动作。所有类型都按同一标准确认实际变化，类型名称不代替中文描述。

- 修复说明实际使用或产物中出现的问题，按已核实的因果关系保留理解问题所需的原因和后果；新增能力说明支持什么操作，行为调整说明处理方式怎样改变。工程、文档和 skill 改动区分被维护对象与它生成或约束的内容，通过归属或因果关系交代该对象与变化的联系，不把条款或流程的调整动作当作必须写出的主线。scope 不代替对象关系，具体条款、执行步骤和文件位置在正文展开。
- 使用来源已核实的名称，保留辨认变化所需的对象与情境。生成、转换或提取写清产物和主要内容来源，选择顺序改变时表明优先关系；具体格式、标记和设置只有影响主线含义时才进入标题。对象称呼、正式名称和代码标识按[共享中文表达方法](../mower-prose-standard/SKILL.md#chinese-prose)处理，不能仅凭函数名或通用类别推定业务对象。
- 按需求和实际影响选择主线，用准确的整体变化统领相关措施。完整 diff 用于核对概括是否准确，标题不逐项列出实现方法、检查和配套规则；正文负责说明完整改动。只有无法由同一具体主线概括的独立变化才考虑并列或拆分，不能用空泛目的掩盖不同对象的变化。
- 错误名称、内部状态、流程或职能标签先按调用者、界面和源码展开为“谁在做什么、在哪一步遇到什么问题”的事实，再用读者能辨认的业务操作、条件和具体表现组织标题。配置变化写明实际设置项控制的量。已核实的具体场景可以说明问题发生在哪里，适用范围另按源码和证据核对，不把该场景写成唯一适用条件，也不把预期收益写成已验证效果。

采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) 格式 `<type>(<scope>): <description>`，冒号后一个空格，中文描述末尾不加句号。type 按主要目的从 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 选择；源码是否改变或改动大小不能单独决定类型。

scope 按主要维护对象优先采用项目已有英文范围名称；多个对象属于同一维护范围时使用共同范围，没有合适范围时省略括号及 scope。描述不含追踪编号、开发过程标记或临时文件名，不用 `+`、`/`、`、` 串联不同动作；真实配置、接口和文件名称按辨认变化的需要保留。

确定主要变化后，从项目配置、相关路径历史或已有 PR 核对可用的 scope；有明确对应时使用，跨范围且无合适名称时可省略。scope 补充英文归属，中文描述仍须说明对象及结果。交接提供已核实的名称、来源及选择或省略依据；缺少来源时先补查，不能据此认定没有合适的 scope。更新已有标题时同样核对并保留仍适用的 scope。

复核时，去掉格式前缀，按[共享中文表达方法](../mower-prose-standard/SKILL.md#chinese-prose)脱离正文通读，分别指出开头的主要动词、它支配的宾语、实际被改变的功能或维护对象，再对照完整 diff 和独立范围陈述核实三者及其关系。宾语只说明处理方式，或产物与维护对象混淆时，重组动宾关系。需要读者自行拼合多个局部动作才能理解主线时，重新概括；需要精简时先取舍信息，保留自然完整的中文，不靠删连接词或堆叠名词缩短句子。因果、结果及新旧能力各自回到来源确认；按[共享用语回读方法](../mower-prose-standard/references/mower-terminology-guide.md#business-wording)核对已交接的称呼及其成稿用法，格式通过不证明语义清楚。

<a id="commit-body"></a>
## 4. 必要正文

标题之外没有理解变化或判断后果必需的信息时，只交付标题。需要正文时，补充具体问题与原因、主要取舍、重要使用或兼容条件，承接标题展开，篇幅由信息决定，不逐项复述完整 diff 或 PR 正文。用户明确要求自定义 PR 合并说明时，按整个 PR 的最终 diff 编写；默认合并使用[平台说明](#pr-merge)。

验证只使用真实执行记录，区分历史记录与本次执行。常规检查、测试数量和开发经过放在交付记录或 PR 中；实际失败或未验证范围影响理解改动或判断后果时才写入正文，并保留影响结论的条件。正文首次出现的简称、类别和指代说明其对象，共同范围只覆盖实际共用规则的步骤。

<a id="changelog-rules"></a>
## 5. 发布说明规则

Changelog 面向使用或维护改动对象的读者。先完成必要正文及其事实核对，再从需求、对应两版差异和已核实内容中选择能统领主要改动的一条主线，最后用一句自然、完整、简短的话提炼核心变化。正文按自身用途取舍，不以摘要是否已经覆盖为删减依据。type 用于归类，句子本身须写出具体变化，脱离标题和正文也能读懂。

从实际变化确定主要动作及其直接宾语，以这一动宾结构起笔，让核心能力、行为差异或实际问题成为句子的主干。核实新增与已有能力、维护对象与产物的区别，保留辨认变化所需的具体名称和对象关系。维护性改动说明实际维护内容的变化，不把预期收益写成已验证效果。

修复类说明修改前实际发生的具体错误，保留辨认问题所需的触发条件和必要后果，不能以修复手段或流程调整代替问题本身。原有错误及其后果须由对应版本的源码与调用路径、测试或现场记录支持，不能从补救措施反推症状。依据不足时先补查，仍无法确认的后果不写成事实。

标题与 Changelog 按各自用途组织，可以共享关键对象和核心变化，不为避免重复而删去必要事实，也不机械复制标题。精简与语句组织按[共享中文表达方法](../mower-prose-standard/SKILL.md#chinese-prose)执行；实现细节、兼容条件、验证方法与恢复操作放在正文，只有会改变读者对核心变化或适用范围理解的条件才进入 Changelog。性能、因果和效果分别核对证据，局部策略或合成测量不扩大为所有场景的实测性能结论。

- 通过 PR 合入，包括普通 merge、squash 和 rebase merge，需要进入更新日志时，将一个以 `Changelog: ` 开头的说明段作为 Summary 第一段，标记与文字写在同一行，后面留空行。依据整个 PR 的最终 diff 写说明；每个 commit 只说明自己的改动，PR 整体说明不复制到各 commit。不拼接中间 commit 记录或另写重复摘要。
- 没有 PR 的直接 commit，按需要提供独立的 `Changelog:` 摘要，放在正文首段并留空行；不需要独立摘要时只写标题与必要正文。普通 commit 不强制 Changelog，生成器在没有有效说明时使用 commit 标题的兼容行为保持不变。
- 交付前脱离标题、正文和 diff 回读这一句，确认动宾主干、对象关系、核心差异及必要条件，再逐项回到两版原始依据核实。核心变化已完整时，删去不影响理解的附加流程和重复解释；需要借助正文拼合局部措施才能理解时，重选主线。逗号或顿号串联多项信息时先检查信息取舍，按句意保留必要标点，不以删标点压缩句子。修复类另确认原有错误已经写出。

[跨平台发布说明](../../../doc/release-platforms.md#发布说明)规定[更新日志生成器](../../../scripts/changelog_generator.py)的提取与兼容边界：优先读取实际合并 PR 的发布说明，再读取 commit 正文的保留说明，均无有效说明时使用去除格式前缀的 commit 标题。合并归并、回退抵消和已发布内容复用以该文档为准；只提取发布说明段，已有 commit 和更新日志保留原文。

## 6. 交付与 commit 核对

1. 只请求 commit 文案时，交付标题和必要正文。历史 commit 或多份草稿在文案之外标明来源；演练案例与当前目标分别展示。
2. 请求创建 commit 时，按已有授权暂存本次改动，读取实际使用的完整暂存 diff，重新核对标题、正文和范围。
3. 按[项目验证要求](../../AGENTS.md#4-verification-and-reporting)完成相关检查并记录实际结果。创建普通 commit 前，回读将实际写入的标题和完整正文，按[必要正文](#commit-body)核对信息取舍；格式与术语检查不能替代这一步。多行说明写入临时文件，通过 `git commit --file` 显式传入，保留原有换行。PR 合并另按[合并流程](#pr-merge)执行。
4. 创建 commit 后回读生成的说明和 diff，确认内容符合范围、其他修改的暂存状态得到保留。交付实际 commit、主要变化和检查结果；推送或发布 PR 沿用对应任务的授权。

涉及敏感安全问题时，创建或推送前还须把分支名、commit 标题、正文、Changelog 及将引用它们的公开链接作为整体回读，确认没有直接或组合泄露被省略的事实。中性 commit 文案不能隐藏公开 Git diff；如果公开分支或 commit 本身会越过用户接受的披露边界，停止发布并建议使用私密安全公告或暂缓披露协作。默认合并说明也须服从这一发布边界。

<a id="pr-merge"></a>
## 7. PR 合并

1. 沿用用户已有的合并授权，核对目标 PR、最终 diff 和当前 head。当前 head 的必要检查全部成功，并完成未解决评审的核对后，再执行合并；检查尚未完成或失败时保留具体状态。
2. 使用 GitHub 按仓库配置生成的默认合并标题和正文，保留平台附带的 PR 关联编号。普通 commit 的中文写作、编号限制和隔离撰写流程不用于重写平台默认合并说明；只有用户明确要求自定义说明时才另行撰写。
3. 使用默认说明合并时，CLI/API 省略说明覆盖参数：不传 `--subject`、`--body`、`--body-file`，REST 请求省略 `commit_title` 和 `commit_message`，也不以空字符串替代省略。合并方式沿用用户选择或仓库要求，并用 head SHA 固定本次已核验的提交。
4. 合并后回读 PR 状态、合并提交 SHA 及实际标题正文，报告实际结果。平台默认说明的核对不要求重新生成说明，也不改写历史提交。

[评估用例](evals/evals.json)在相同请求和原始材料下比较新旧版本。程序检查格式和指定术语，对照材料核验事实覆盖，用户判断文案是否清楚；分别报告结论。
