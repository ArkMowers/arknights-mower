# 中文标题规则

本文件由 mower-commit 维护，供 Git 提交标题和 PR 标题共用。调用方先确定实际改动范围：提交标题依据本次提交的完整 diff，PR 标题依据整个 PR 的最终 diff。

先对照需求和已确定范围的完整 diff，列出实际对象及可核实的前后变化，再确定主要变化或共同维护对象，最后选择动作并合成标题。业务改动写具体功能、流程或配置；工程、文档和 skill 改动写实际维护对象及其职责、格式或使用方式的变化。

多项变化共同实现同一结果时，概括这个有事实依据的结果；变化相互独立时，按需求和方案确定主次。文件数、行数、测试数量、材料顺序及命名难易均不能决定主线。检查被省略的变化是否仍属于标题所述范围，避免用一个局部动作代表整个改动，也避免虚构空泛的共同对象。

一个主要动作支配完整对象；保留对象的名称与种类，以及辨认变化所需的条件、场景和结果。次要细节进入正文，标题长度由识别变化所需的信息决定。

标题必须遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。以下规则补充项目类型选择和中文表达要求。

格式为 `<type>(<scope>): <description>`。type 从 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert` 中按主要目的选择。scope 选填，省略时一并省略括号，采用项目已有英文范围名称；冒号后一个空格，中文描述末尾不加句号。

标题的宾语采用需求与最终 diff 共同指向的对象，保留材料给出的名称与种类；描述写出该对象在修改前后的差异，修改目的放在正文。type 表示改动性质。描述不含开发过程编号或临时标记，不用 `+`、`/`、`、` 串联不同动作。

类型按实际主要目的选择：feat 表示新增功能，fix 表示修复问题，其他类型结合项目约定及实际目的判断。是否改动业务运行源码不能单独决定类型，chore 也不表示改动很小。

复核时先对照需求和完整 diff 检查范围与事实，再脱离正文检查标题能否让审阅者识别对象和变化，最后检查中文修饰关系、动宾结构、格式及类型。标题中的每项事实能定位到正文或 diff，只能说明有来源；还需确认标题概括了实际主要范围，并保留必要限定。
