# Recognition

Recognition consumes standard canvas frames and their crops. [Device Control](device-control.md#4-capture-frame-contract--storage) owns acquisition and screenshot storage; this subsystem owns model input preparation and OCR execution.

<a id="clue-access-records"></a>
## Clue Access Records

`Recognizer.get_scene` identifies the reception room's Access Records overlay as `CLUE_ACCESS_RECORD`, before navigation-bar and facility features visible behind the overlay. Recognition compares the complete title's binary foreground shape within its fixed search region, without depending on the orange header bar. The shipped title resource contains only the foreground silhouette; background texture, dates, visitor counts, credit amounts and the optional credit item do not participate. This scene does not initialize or call OCR. Standard-frame fixtures cover the original screenshot and the existing video example after normalization to 1920×1080.

The [Access Records recognition tests](../../arknights_mower/tests/clue_access_record_recognition_tests.py) verify scene classification, changed backgrounds, incomplete foreground rejection and navigation. The [credit workflow tests](../../arknights_mower/tests/clue_credit_tests.py) verify settlement dismissal and preservation of the current-week collection policy. These offline checks do not establish successful game collection.

## Network Adaptive Scene Waiting

`waiting_scene_network_adaptive` and `run_order_network_adaptive` are independent, default-off user selections. When either is enabled, [`BaseSolver.waiting_solver`](../../arknights_mower/utils/solver.py) records only continuous, explicitly recognized network waits: `CONNECTING`, or `LOGIN_LOADING` while its `login_connecting` text is actually visible. The latter supplies the logical evidence source `LOGIN_CONNECTING`; a publisher logo in the same scene supplies no evidence. Black screens, general `LOADING` and other local loading screens do not create network observations. The timer restarts whenever the explicit network source changes or disappears, including a source change within one scene enum. Separate short waits are never added together.

The instance records the raw duration when each explicit network wait ends or times out; collection has no fixed five- or ten-second filter and no half-base filter. Duration uses monotonic time. A timeout records only the observed lower bound, not a completed response time or an exemption from another use's qualification threshold. The bounded history retains at most 1024 observations for fifteen minutes. Normal game recovery preserves the history on the existing recognizer; restarting the Mower process does not restore this transient history.

Compensation qualification uses a fixed fraction of **one half**, independently for each purpose. For run orders, the base is the user's original Grandet confirmation buffer. For scene waiting, the base is the current scene's original screenshot interval multiplied by its configured wait count. A recorded duration qualifies when it is greater than or equal to that purpose's base divided by two. Comparison uses the uncapped recorded duration and the original base, never a previously adapted value. The fraction is not configurable. Raw observations remain shared even when they fail one purpose's threshold, so that purpose does not discard evidence needed by the other.

[`NetworkAdaptation`](../../arknights_mower/utils/network_adaptation.py) first selects the latest observation meeting the current purpose's half-base threshold, then checks whether that purpose has already consumed it. If it has, selection returns no allowance rather than falling back to an older observation. A new shorter observation that fails the threshold does not hide an earlier qualifying observation. Planning and failed qualification do not consume records. Run orders and scene waiting have separate consumption; each qualifying record supplies at most one allowance for each purpose. Eligible scene-wait recipients are `CONNECTING`, `LOADING` and `LOGIN_LOADING`, sharing one scene-wait consumption. General loading can receive compensation but cannot create or renew network evidence.

A qualifying observation adds its actual recorded duration, capped at 120 seconds, without an additional fixed five seconds. The cap is a maximum allowance, not a compulsory wait: a recovered page continues immediately. Both features preserve the saved base settings. For example, a nine-second observation raises a fifteen-second Grandet buffer to twenty-four seconds, but leaves an ordinary thirty-second scene timeout at thirty seconds because nine is below fifteen. A fifty-second Grandet buffer also remains fifty seconds because nine is below twenty-five. A timeout observation must pass the same comparison; its timeout flag does not bypass either purpose's threshold. [Run-order network adaptation](base-scheduler.md#run-order-network-adaptation) owns how the selected buffer affects confirmation and queue entry.

For a protected scene wait, the effective timeout is the user's base timeout plus the selected compensation. Capture intervals retain their configured values. A continuous waiting episode retains one base budget for each supported scene and one shared compensation budget; returning to a scene does not refill its base budget, and switching scenes does not consume another allowance. An absolute deadline bounds the episode by the initial base-budget sum plus its single compensation. This preserves a new loading scene's configured base timeout without permitting repeated transitions to extend waiting indefinitely. A new explicit network observation can protect a later episode. `UNKNOWN`, combat and ordinary business sleeps supply no network evidence. The protected deadline coordinates the recognizer's existing freeze checks, and timeout retains the caller's `restart_on_timeout` choice.

Within a running order, `CONNECTING` can inherit the already selected run-order compensation without meeting a second scene-wait threshold. All three supported recipients can also select existing scene-wait evidence using the current scene's original half-base threshold, even when the global scene-wait switch is off; this access is limited to that run's temporary scope and retains the separate scene-wait consumption. Concurrent run-order and scene-wait allowances use their maximum, not their sum. Outside this scope, a disabled scene-wait switch supplies no adaptive scene-wait allowance.

The [half-base qualification decision](../../.agents/notes/implemented/feature/2026-10-29-network-adaptive-half-budget.md) records why qualification is relative to each original base and why collection remains independent. [`network_adaptation_tests.py`](../../arknights_mower/tests/network_adaptation_tests.py) and [`waiting_network_adaptation_tests.py`](../../arknights_mower/tests/waiting_network_adaptation_tests.py) provide offline checks for threshold boundaries, observation expiry, independent consumption, source recognition, finite deadlines and recovery.

## OCR Models and Results

The production factory uses RapidOCR 3.10.0 with the bundled PP-OCRv6 tiny detection and recognition models. Direction classification uses the SDK's bundled legacy classifier. All three model paths are explicit and checked before engine construction; a missing file fails initialization rather than downloading a replacement. [Model provenance and licenses](../../arknights_mower/models/rapidocr/README.md) identify the shipped bytes. Desktop packaging collects the SDK configuration and classifier plus Mower's tiny models; it excludes the SDK's unused small models. Android and source deployments use the same factory and bundled tiny files.

The adapter retains the existing `(results, elapsed)` interface: full OCR returns box/text/confidence rows, recognition alone returns text/confidence pairs, detection alone returns boxes, and classification alone returns label/confidence pairs. Empty outputs return `(None, None)`. Each call explicitly resets detection, classification, recognition and threshold options so the SDK's mutable settings cannot carry into the next request. The existing detector bounds and local/shared execution policy below remain in effect.

Furniture names occupy a fixed region. The caller locates its complete white glyph span and rejects empty or horizontally clipped text before inference. It confirms the name with two recognition-only reads: an enlarged original-color line and a binary line. Each read requires confidence of at least 0.9 and permits one alternate full-line input only when that confidence check fails. Two reliable names must agree, allowing the existing paired-quote variants; a conflict remains an error. This avoids using a detector crop that can omit quotes or distort small superscript letters. Unknown names still require exact resource matching before dismantling can proceed.

Tiny prioritizes inference speed and model size. Fixed screenshot checks retain known character errors, including reading 白面鸮 as 白面鸽 and reading γ as y in recognition-only mode; the model choice does not establish general accuracy or equivalence to template matching. Existing source environments that retain their interpreter must follow the [OCR dependency migration procedure](../cookbook/source-dependency-migration.md).

## OCR Memory Bounds

[`rapidocr.py`](../../arknights_mower/utils/rapidocr.py) owns the production model factory. The detector input passes through two steps. RapidOCR first applies its own letterbox: when the width/height ratio exceeds 8 or the height is at most 30 pixels, it pads black bands above and below until the height is about twice the width divided by 8, so a 441×48 crop becomes 441×110. The bounded wrapper in `rapidocr.py` then scales that letterboxed image with two bounds: a long-edge cap at 1920 pixels and short-edge enlargement toward 736 pixels for small text, followed by alignment to the network's 32-pixel units. The tighter bound determines the scale, so above a letterboxed aspect ratio of 1920/736 (about 2.61) the long edge stays at 1920 pixels and the short edge follows that cap instead of enlarging toward 736 pixels; the same 441×48 crop reaches the detector as 1920×480, and a 1920×65 crop becomes 1920×479 after letterbox and 1920×480 after the wrapper. Wide crops therefore keep a bounded detector tensor instead of the wider input under the previous short-edge rule (2944×736 for these crops). This limit changes only the detector input size; result coordinates retain their existing meaning and recognition thresholds are unchanged.

Concurrent initialization publishes one engine per instance; failed construction leaves initialization retryable. The in-process engine constructs the model in the calling instance through the same factory with the library's default session threads. The shared service constructs the model in its worker through the same factory, with two intra-operation threads and one inter-operation thread per ONNX session, and an OpenCV thread limit of two. The shared path bounds each library's parallel work rather than reserving particular CPU cores. The input limit reduces inference allocations; it does not establish an application-wide resident-memory limit.

## Independent Shared OCR

**Independent Shared OCR** is the multi-instance OCR path: instances using the same installation and data root share one on-demand OCR model worker. The multi-instance manager remains a launcher; closing it or the first requesting instance does not stop recognition for other instances. Account, task and device state stays in each instance. Separate installations, data roots and network namespaces do not share this service.

[`ocr_shared.py`](../../arknights_mower/utils/ocr_shared.py) implements the callable client used by `initialize_ocr`. [`ocr_service.py`](../../arknights_mower/utils/ocr_service.py) runs an independent coordinator and its sole model worker. The shared worker and the in-process engine are the two production paths that construct an OCR engine. Source and frozen launches dispatch to the service entry before GUI or configuration initialization. A new service starts only when a caller needs OCR; it does not keep the manager or an instance alive.

`initialize_ocr` chooses the OCR path on every call. The default `MOWER_OCR_MODE=auto` publishes the shared client when at least two live Mower instance registrations use the same installation and data root, and publishes the in-process engine otherwise; `local` and `shared` force those paths, a blank value means `auto`, and any other value raises `ValueError`. The count reads the existing instance registrations, and only a desktop launch through the webview entry registers as a live instance: Flask and Android launches that start the web service directly do not register, so those deployments set `MOWER_OCR_MODE=shared` explicitly for cross-instance sharing. A mode change builds and publishes the new engine before releasing the old reference; a construction failure keeps the previous engine, and the next call evaluates again. The in-process path loads its model during this call, so a load failure surfaces as a task-initialization error rather than at the first recognition call, and it does not indicate a device problem. Engine choice is logged with its evidence.

```text
Instance A ─┐
Instance B ─┼─ small request headers → loopback listener (backlog 32)
Instance N ─┘                              │
                        one admitted image at a time
                                           ↓
                         one OCR model worker → caller's result
                                           ↑
                          independent deadline coordinator
```

Clients upload pixels only after admission. Each instance serializes its own calls; the service holds at most one admitted image. Each image side must be at most 8192 pixels and the array must contain at most 32 MiB of `uint8` pixels, so the per-edge and total-size limits apply together. Grayscale and one-, three- or four-channel arrays are accepted, including non-contiguous crops. A 10000×1000 image stays below 32 MiB yet exceeds the per-edge limit and is rejected as an invalid image shape. The JSON header is limited to 4096 bytes and JSON responses to 2 MiB. Socket data uses bounded JSON and raw arrays, not executable object serialization. A random secret authenticates the loopback endpoint. The OS listen backlog bounds waiting connections; this is not a throughput guarantee for eighteen simultaneous requests.

Protocol version 2 authenticates a connection before any JSON exchange. The client sends a fixed 69-byte preamble containing the magic value, the protocol version and the 64-byte token, and the server must receive and validate it within one second. A bad magic value, a different version and a wrong token each receive its own fixed refusal text: invalid request, protocol version mismatch or authentication failure. An unauthenticated peer never receives internal exception detail. After authentication the server answers `authenticated`, the client then sends the JSON header within a five-second budget, and the server answers `ready` only after it admits the request. A refusal or failure after authentication carries the server's error text, limited to 512 characters, and the client includes that text in its own error: a refusal appears as `共享 OCR 拒绝请求：` followed by the text, and an execution failure as `共享 OCR 执行失败：` followed by it.

The request's 60-second monotonic budget includes client serialization, cold startup, admission, upload, model execution and response; on the shared path a newly launched service has a ten-second sub-budget to publish its endpoint. The two execution paths have separate failure behavior. On the shared path, waiting clients receive no implied success, a sent request is never automatically replayed, and a failed call does not fall back to an in-process model; when the service cannot start, the caller receives a failed request instead of a result, and that error carries the tail of the service log, at most 2048 characters. In the shared path the coordinator writes its standard error to `service.log` in the shared OCR directory, and a new launch rotates a file of at least 64 KiB to `service.log.1`. The in-process path neither creates nor depends on the shared service; a failure on that path propagates from the in-process engine to the caller. Each call overrides the previous call's thresholds with the current request's values: `text_score` comes from `initialize_ocr(score)` (0.3 by default), `box_thresh` and `unclip_ratio` come from the request, and omitted values fall back to `rapidocr.DEFAULT_BOX_THRESH` (0.5) and `rapidocr.DEFAULT_UNCLIP_RATIO` (1.6), so one caller's options cannot change another caller's results; the score argument accepts only a number from 0 to 1.

The 60-second request budget and 60-second idle exit remain unchanged on the shared path, and the 256-request replacement threshold keeps its value. Measurements on the development host describe accepted trade-offs there rather than guarantees: eighteen concurrent clients using the real model completed a burst in 13.5 to 17.2 seconds, leaving about 71% to 77% of the request budget; at 2.8 seconds per inference on a slower host the same burst takes about 54 seconds and leaves about 10%; a cold start after idle exit adds 2.1 to 3.5 seconds; and replacing the worker after 256 requests adds about 4 seconds per cycle, about 16 milliseconds per request when amortized.

The request header's `options` object accepts exactly six keys. `use_det`, `use_cls` and `use_rec` accept a boolean or null, and null leaves the engine default for that stage. `text_score` accepts a finite number from 0 to 1 and defaults to `rapidocr.DEFAULT_TEXT_SCORE` (0.3). `box_thresh` accepts a finite number from 0 to 1 and `unclip_ratio` accepts a finite number from 0 to 10; both fall back to `rapidocr.DEFAULT_BOX_THRESH` (0.5) and `rapidocr.DEFAULT_UNCLIP_RATIO` (1.6) when omitted. Production callers pass only the three boolean switches; the client supplies its configured text score. Any other key or a value outside these ranges rejects the request. The in-process engine accepts the same six call options and applies the same defaults.

The coordinator terminates and joins its own worker on an execution deadline or update shutdown. Model failure closes that service generation; a subsequent new request can start a service. Only a request that reaches inference counts toward worker replacement; silent, invalid and unauthenticated connections neither end the service generation nor advance that count. After 256 inference requests, the coordinator confirms the old worker's exit before replacing it; the listener, secret and waiting connections remain available. This releases native allocations without requiring Python garbage collection to return them. After 60 seconds without an accepted connection, the worker and coordinator exit. The next request starts cold.

Startup, service and model lifetime locks prevent duplicate construction. A model lock left held by a surviving worker prevents a replacement from loading a second model after coordinator death. The portable parent-channel EOF watcher needs the GIL; an abruptly orphaned native call holding it cannot be guaranteed immediate cleanup on every platform. No foreign process is terminated to overcome that lock.

Endpoint metadata and lifetime locks live under `@app/tmp/shared-ocr/<service-hash>/`, with `space=""`; `MOWER_DATA_DIR` and macOS writable-data-root behavior match ordinary application paths. Service launches pass the caller's resolved absolute data root so a different working directory does not move service registration or update admission to another directory. The service hash includes the installation path and host name, plus the Linux network-namespace identity so containers sharing a data volume do not reuse an inaccessible loopback endpoint. Endpoint metadata records the protocol version, port, token, coordinator process id and worker process id. The client ignores an endpoint whose version or token is invalid and attempts a cold start; when the recorded coordinator process no longer exists, it deletes that endpoint first. While the recorded coordinator remains alive but its listener does not accept a connection, the client retries within the remaining request budget instead of starting a second coordinator. These are separate from the software-update cache. The coordinator and every model worker register as `ocr-service` and `ocr-worker` respectively, so [software updates](software-update.md#shared-ocr-update-lifecycle) can wait for both before replacing files; that section owns update shutdown, restart exclusion, submission-lock and backup-cleanup procedures. Recovery after an update does not eagerly relaunch either process; a resumed instance creates OCR on demand.

The [shared OCR decision](../../.agents/notes/implemented/architecture/2026-10-16-shared-ocr-service.md) records why service lifetime is independent of the launcher and why the first implementation uses one model worker.

## Offline Verification

[`shared_ocr_tests.py`](../../arknights_mower/tests/shared_ocr_tests.py) exercises eighteen concurrent clients, cold-start arbitration, preamble authentication and refusal text, deferred pixel upload, independent thresholds, input validation, real OCR equivalence, model failure, timeouts, stale-endpoint recovery, silent-connection tolerance, inference-only worker replacement, idle exit and software-update shutdown. A real source launch remains available after its originating client exits. Frozen entry routing is checked offline; eighteen real running emulators have not been measured here.

[`ocr_gate_tests.py`](../../arknights_mower/tests/ocr_gate_tests.py) verifies the engine choice without loading a model: single-instance local mode, two-instance shared mode, `auto`/`local`/`shared` overrides, blank and invalid values, per-call re-evaluation with switching and release of the previous engine, instance filtering by kind and data root, degraded local mode after a registration scan failure, score validation, retry after a failed construction, and the local engine's shared-client call options.

The shared OCR service has not run on an Android host or from a packaged Windows or macOS artifact. Its shared-directory identity reads `/proc/self/ns/net` on Linux-family hosts, its launch depends on `sys.executable` and detached child-process creation, and its model worker uses `multiprocessing` spawn.

[`shared_ocr_update_lifecycle_tests.py`](../../arknights_mower/tests/shared_ocr_update_lifecycle_tests.py) verifies that an orphaned model remains visible to update shutdown and that a worker starting after update admission cannot construct a model.

[`runtime_memory_tests.py`](../../arknights_mower/tests/runtime_memory_tests.py) verifies detector tensor bounds and concurrent client initialization. Furniture, mastery, clue, manufacturing, recycling and operation-drop fixtures verify the production model's expected names, counts, timing and rejection results. These offline checks do not establish long-running device memory stability or bound simulator memory.
