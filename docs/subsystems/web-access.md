# Web Access

## 1. Session Boundary

`webview_ui.run_desktop` binds the service to `127.0.0.1` when the Web UI token is empty. It generates a runtime credential for protected HTTP endpoints and AI WebSocket access. Configuring a Web UI token binds the service to `0.0.0.0` and requires that token for protected requests.

Browser launch URLs carry the session token without the client instance name. The embedded desktop window adds its instance name only to its own URL for title display; browser fallbacks use the original browser URL.

`GET /status` and its HEAD representation require the current instance token before reading operational state, including scheduling, recovery and deployment information. Browser polling uses the shared authenticated client. The process supervisor checks HTTP responsiveness without a token and treats this endpoint's 403 response as an available service; it does not read protected status data or persist the session token. Other HTTP errors retain the existing failed-probe behavior.

The profile, GUI preference and browser instance-management routes share HTTP credential checks in [`web_auth.py`](../../arknights_mower/utils/web_auth.py). Their OPTIONS preflight requests do not carry a token: the supplied Origin must match the current service, or the explicitly configured loopback development origin when the request itself is local and the instance has a token. The requested method must be registered on that path and cannot be OPTIONS. Preflight never parses operation inputs or reads instance state. The subsequent operation still requires the current token; profile and instance-management writes also retain their confirmation headers and permitted-Origin checks. Focused offline verification is in [`web_auth_tests.py`](../../arknights_mower/tests/web_auth_tests.py).

## 2. Log Read Interface

The local-only session accepts read-only log requests without a credential at `/log`, `/diagnostics/timeline`, `/diagnostics/errors`, and the diagnostic log and export routes. The request must arrive from a loopback address with a loopback Host. Browser origin and fetch metadata must identify the same local Web UI; the log WebSocket requires an Origin header. Cross-origin and remote requests fail. Sessions with a configured token require that credential.

AI chat at `/ws/chat`, AI analysis, diagnostic deletion, and other mutating endpoints do not receive the local log-read exemption. The source-snippet tool retains its file allowlist.

For authenticated `/log` subscriptions, the first frame carries the valid Web UI token within five seconds. This credential authorizes the log subscription independently of Origin, Host, scheme or port, including absent Origin and proxy-rewritten Host values. HTTPS termination and port forwarding require WebSocket upgrades to reach the backend; forwarded headers grant no tokenless access. Other routes retain their existing origin checks.

The process-local logging relay and frontend relay each retain at most 256 waiting messages. Producers evict the oldest waiting entry when full, including when no frontend consumer exists; shutdown sentinels also remain admissible. Each asynchronous message is limited to 16,384 characters with an explicit truncation marker. These limits apply to live delivery and console output; the separately attached runtime file handler receives the complete original record. Eviction can omit a live notification and its automatic screenshot archive trigger. Existing per-client subscription limits remain in force. Focused offline checks are in [`runtime_memory_tests.py`](../../arknights_mower/tests/runtime_memory_tests.py), [`log_tests.py`](../../arknights_mower/tests/log_tests.py) and [`log_stream_tests.py`](../../arknights_mower/tests/log_stream_tests.py).

## 4. Subsystem Invariants

- <a id="frontend-navigation-dispatch"></a>**Frontend Navigation Dispatch**: Known frontend page navigation resolves before API dispatch according to the [frontend navigation contract](#6-frontend-navigation).

- <a id="log-window-cohesion"></a>**Log Window Cohesion**: Displayed logs, screenshot navigation and export share one loaded time window or error archive; date drafts and superseded requests never replace that source, and failed source changes expose no stale evidence.

- <a id="local-log-read-boundary"></a>**Local Log Read Boundary**: A WebView session without a configured token permits read-only log requests from loopback with valid browser origin metadata; remote and cross-origin requests are rejected, and AI chat and mutating endpoints retain their credential checks.
- <a id="credentialed-log-forwarding"></a>**Credentialed Log Forwarding**: Log WebSockets with a valid first-frame token are authorized independently of Origin, Host and forwarded headers; tokenless access remains restricted to the local log-read boundary.
- <a id="managed-instance-admission"></a>**Managed Instance Admission**: Individual and bulk manager launches use the same stopped-process, selected-directory, update and port checks. Startup reservations prevent another launch before runtime registration appears.
- <a id="stopped-instance-configuration"></a>**Stopped Instance Configuration**: Manager edits require the instance process to have exited, not merely stopped automation. Name, directory, deletion and connection settings share the backend guard; [batch settings](#batch-instance-settings) apply that guard before each file write and preserve unselected fields.

## 5. Desktop Startup

`webview_ui.run_desktop` evaluates `start_automatically` once per process, in foreground and background modes. It claims startup ownership before exposing the HTTP service. `/status.desktop_startup_handled` and the existing `/status.auto_start_handled` remain true throughout that desktop process, including while stopped and when automatic tasks are disabled. The desktop flag also identifies process-owned resource automation; update restarts on other hosts do not claim that ownership. Browser refresh, closing and reopening the window, tray browser actions, and importing configuration do not schedule another automatic start. Manual task controls remain available.

The startup worker waits for the active software update operation to finish. When resource checking and automatic installation are enabled, it checks and completes installation before admitting automatic tasks. Resource installation uses a credentialed POST context; ordinary task startup uses a separate credentialed GET context for `/start/<mode>`, without requesting temporary device preparation. Resource check or installation failure preserves the existing resource fallback and still permits task startup. Stop or application shutdown cancels pending automatic admission, including during the resource step. Resource automation also runs when task autostart is disabled. The frontend observes tracked resource jobs and retains manual resource installation.

Software update restarts preserve the recorded task-run state independently of `start_automatically`: running tasks resume in mode `0`, while stopped tasks remain stopped, including after source Git updates and background restarts. [Task-run intent and startup modes](process-recovery.md#dispatch-recovery) define recovery and replacement-job handling. `MOWER_RESUME_MODE` values `0` and `1` select that task mode explicitly. Ordinary process-operation restarts set `MOWER_RESUME_MODE=preserve`: `MOWER_RESUME_RUN=1` starts mode `2`, while a previously stopped task stays stopped regardless of the saved autostart option. A legacy update restart without an explicit mode also uses mode `2` when `MOWER_RESUME_RUN=1`. Other hosts that do not claim desktop startup ownership retain their existing frontend fallback; this change does not alter the separate Android launcher.

The [desktop startup decision](../../.agents/notes/implemented/bug-fix/2026-10-11-desktop-process-autostart.md) records the cause and verification.

## 6. Frontend Navigation

For GET and HEAD requests, an explicit positive `text/html` Accept entry and a missing, `document` or `iframe` Sec-Fetch-Dest identify page navigation. At process startup, known pages load from the distribution's `frontend-routes.json`, falling back to the source manifest when absent. Request matching uses this immutable set without reading the manifest and ignores case and trailing slashes. Navigation to these pages returns `index.html` before API dispatch, including `/mastery-recommendation`, which shares its URL with a JSON endpoint. Both representations declare `Vary: Accept, Sec-Fetch-Dest`.

JSON clients, wildcard Accept requests and non-read methods retain API dispatch and credential checks. Documentation files and directories retain their static responses. Unknown APIs and missing assets retain 404 responses; unknown extensionless page navigation outside API and resource prefixes retains Vue's missing-page display.

The [navigation dispatch decision](../../.agents/notes/implemented/bug-fix/2026-10-12-frontend-navigation-dispatch.md) records the defect and focused verification.

### Build Asset Caching

GET and HEAD requests for bundled frontend files remain public without a Web UI token. These files contain the distributed application and public assets; API requests retain their existing credential checks.

Successful and not-modified static responses under `/assets/` use `public, max-age=31536000, immutable` when a script, stylesheet, image or font filename ends with the build's eight-character content hash. HTML, filenames without that suffix, resource-package overlays and error responses retain their existing cache policies. A new build changes asset URLs when their content changes, while the HTML entry continues to revalidate.

Precompressed assets declare `Vary: Accept-Encoding` for both identity and gzip responses, including 304 responses. An identity ETag does not validate gzip bytes; gzip responses retain date-based validation without reusing that ETag. Focused offline checks exercise the Flask request paths in [`web_routing_tests.py`](../../arknights_mower/tests/web_routing_tests.py).

### Frontend Session Navigation

Internal page links include the current session token in their rendered `href`, before any click. An explicit destination token takes precedence. Navigation preserves the destination's query parameters and fragment when inheriting the session query.

In a desktop WebView, primary and middle-button clicks on internal page links navigate in the current window, including clicks carrying modifier keys. Links recognize the initial `window_shell=1` URL marker before the Python bridge is injected and continue to recognize an available bridge without that marker. Browser sessions retain native modified-click behavior with a credentialed destination. External links retain their configured targets.

Focused offline verification: [`router.test.js`](../../ui/src/router.test.js) and [`SessionLink.test.js`](../../ui/src/components/SessionLink.test.js) cover session inheritance, rendered links and desktop click handling. These checks do not establish native Windows input delivery.

### Sidebar Preferences

[`sidebarPreferences.js`](../../ui/src/composables/sidebarPreferences.js) owns the current sidebar layout. Browser, Windows, macOS and Linux clients load and save that layout through the current instance's `config/gui.yml`, separately from saved profiles. `localStorage` is read only as a migration source when the backend has no sidebar layout. A failed initial read leaves editing disabled; a failed save keeps the current changes in memory and exposes an explicit retry. Accepted edits are saved in order, with later pending changes replacing superseded pending snapshots.

`GET /gui/sidebar` returns `{sidebar: object | null}`. Missing layouts, unsupported versions and invalid version 3 layouts return `null`; version 1 and version 2 layouts remain readable, and frontend initialization upgrades them to version 3. `PUT /gui/sidebar` accepts `{sidebar: object}` and returns the saved object in the same response shape. Both routes retain the instance credential checks. Sidebar writes share the configuration backup lock but do not require a saved-profile generation, so switching profiles cannot reject an independent GUI save. Invalid writes return 400, requests larger than 1 MiB return 413, and storage or lock failures return 503 without replacing the saved file.

Version 3 contains `groups`, `placements` and `knownKeys`. A group has a unique `key`, a nonempty `title` of at most 80 characters and a Boolean `collapsed` value; there may be zero to 20 named groups. A placement has a unique `id`, a catalog `key`, a `group` and Boolean `visible` and `pinned` values. Placement groups reference a named group or the reserved `ungrouped` and `footer` areas; `pinned` is also reserved and cannot name a group. Keys and placement IDs use 1 to 100 ASCII letters, digits, underscores or hyphens. The API accepts at most 100 distinct `knownKeys` and 2200 placements.

The fixed catalog in [`navigation.js`](../../ui/src/navigation.js) supplies editable pages and canonical external links; unknown catalog keys and former user-added links are discarded during frontend normalization. Normalization restores the fixed footer entries and returns ordinary pages previously placed there to their default group, or the ungrouped area when that group is absent. External links open a new tab without opener access. A catalog key identifies a page, while a placement ID identifies one independent copy. Each named group, the ungrouped area and the pinned area accept at most one copy of a page. Moves, pin changes and removal act on the placement ID; an occupied target rejects the move while other copies remain unchanged. `knownKeys` prevents a page removed from every area from reappearing after reload. Newly introduced catalog pages join their default group when it exists, otherwise the ungrouped area. When adding 任务配置 with no default group and exactly one unpinned 运行日志 copy, normalization instead places it directly after that copy in the same group or ungrouped area. The default `daily` group is labelled 常用 and may be renamed or dissolved like any other group. Dissolving a group moves its pages outside groups, deduplicates pages already present there and preserves copies in other groups and pinned pages.

[`gui.py`](../../arknights_mower/utils/config/gui.py) merges each preference change with the latest file under a process-local lock and the shared `gui.yml.lock` OS lock. Windows uses `msvcrt` and macOS/Linux use `flock`; lock acquisition has a three-second monotonic budget. The lock file remains in place across atomic replacements and process exits. Configuration export omits it, and import or profile activation preserves the existing lock file even if an older archive includes one. Window ratio, window mode, launch mode, close preference and unknown saved fields survive sidebar saves, and subsequent window saves preserve the sidebar. [`gui_sidebar_tests.py`](../../arknights_mower/tests/gui_sidebar_tests.py) checks authenticated requests, validation, migration reads, failed writes and actual cross-process interleaving with isolated files. [`config_backup_tests.py`](../../arknights_mower/tests/config_backup_tests.py) and [`config_profiles_tests.py`](../../arknights_mower/tests/config_profiles_tests.py) verify that import and profile activation keep the same lock file while it is held.

<a id="settings-search"></a>**Settings Search**: [`settingsSearch.js`](../../ui/src/utils/settingsSearch.js) normalizes both searches and indexed text with NFKC and lowercase conversion. Query whitespace separates keywords; every keyword must match. Whitespace within indexed text does not prevent a match. The shared aliases map 深色 to 暗色, 浅色 to 亮色, 公招 to 公开招募, 肉鸽 to 集成战略 and 触摸 to 触控. Other punctuation remains significant; pinyin and approximate spelling are not supported.

[`SettingsLayout`](../../ui/src/components/SettingsLayout.vue) collects card titles, field labels, rendered option labels, descriptions and explicit search metadata from all mounted categories, including inactive categories. The index excludes user-entered configuration values such as accounts and API keys. Each search reads the current fields, and DOM changes refresh an active query after asynchronous content arrives. Results prefer individual fields over category or card matches. Components declare metadata for conditional fields such as SMTP settings or custom model endpoints, so these searches can locate the owning card before that mode is selected. Selecting a result clears the query, activates its category and then scrolls to and highlights the target. It does not enable a mode, expand a conditional configuration or write a setting.

The display theme preference defaults to `light` and accepts `light`, `dark` or `system`. Explicit light and dark selections retain their appearance when the operating system changes. `system` follows the current system color preference through [`useResolvedTheme`](../../ui/src/composables/theme.js), which exposes the effective light or dark appearance without rewriting the saved preference and releases its media-query listener when its owning scope is disposed. Providers, teleported editors, navigation, charts and the embedded guide use that effective appearance. ## 7. Instance Manager

Windows directory browsing in the manager and instance desktop windows uses the native `IFileDialog` folder picker through [`folder_dialog.py`](../../arknights_mower/utils/folder_dialog.py), rather than pywebview's legacy tree picker. It runs on the owning WinForms UI thread, selects one existing filesystem directory, accepts Unicode paths, and releases COM references and allocated path memory on selection, cancellation or failure. The system owns the resizable Explorer-style layout and saved dialog size. Cancellation does not change the saved directory; the manager retains its post-dialog identity and stopped-process checks. File selection and other platforms' existing dialogs remain unchanged, including the manager's macOS directory-creation support.

[`manager.py`](../../manager.py) exposes the manager bridge; [`InstanceController`](../../arknights_mower/utils/manager_instances.py) owns lifecycle admission and offline configuration writes. Instance names and directories remain in `instances.json`. The manager reads current runtime registrations with a strict, single-attempt scan and combines them with persisted launch reservations. Unreadable state blocks operations rather than authorizing another process or configuration overwrite. Resolved, case-normalized data directories identify instances, including directory aliases. A reservation remains active while its child process is alive, across manager window recreation; verified process exit releases it. Starting successfully means that process creation succeeded, not that HTTP startup is ready.

The main desktop window also exposes these same manager methods through `attach_instance_controls`. Its custom title bar lists instances and delegates individual and bulk operations to the existing manager component, including its confirmations and stopped-process edit restrictions. Browser sessions use the authenticated HTTP adapter described below. Each attached controller reloads the shared list under the existing admission lock; opening a window defers that read so an unreadable list is reported on menu use without preventing the window from opening. Folder dialogs belong to their attached window. New launches discard the parent instance's supervision and recovery environment before establishing their own launch identity.

When the main window requests bulk close, it dispatches exit requests to other configured instances before the current instance, keeping the calling window alive until those requests have been sent. The standalone manager retains instance-list order.

Individual row actions carry the captured `{name, path}`; under the admission lock, the backend rejects a changed or missing target before editing the list, launching or stopping a process, or opening a folder dialog. Folder selection validates that same identity again before saving.

The UI shows stopped, starting, running and stopping process states. Starting and running managed instances expose Stop, which sends the existing instance-specific graceful exit request, including before registration completes. It stops the entire instance and its automation, not just the automation thread. Stopping does not permit editing or restarting until process exit. Non-managed instances sharing a directory block launch and edits but must be exited from their own application. The manager does not kill unrelated processes or force termination after a stop request.

Manager list and configuration mutations run under a shared admission lock and recheck live processes. Folder selection releases that lock while the dialog is open, then verifies the original row and both directories before saving. The UI disables configuration controls while a process is live and closes stale edit dialogs; the backend remains authoritative. Bulk open and close each require a confirmation dialog. Bulk open checks each row's eligibility immediately before dispatch, silently skips ineligible rows and retains the individual startup checks. Actual startup failures remain warnings and do not prevent other eligible rows from being processed. Repeated registration scans and port probes add overhead with many instances. Deletion requires a separate confirmation naming the instance; it removes only the manager entry, not the saved files. Status refresh cancels a pending deletion if the selected row changes or becomes non-editable. Ordinary frontend bridge calls have a fifteen-second response budget; that deadline only ends the frontend wait and does not cancel Python work. Native directory selection waits for the user's confirmation or cancellation without that deadline and retains the UI's busy state until the call returns or fails, followed by a bounded state refresh. State refresh failures disable actions until a complete snapshot is available again.

Connection settings use each instance's `config/conf.yml`, under `webview.token` and `webview.port`, rather than a second copy in `instances.json`. A blank port saves as `0` and requests a random port. Managed launches honor an explicit port from 1 through 65535 regardless of whether a token is configured. Existing token binding rules in [Session Boundary](#1-session-boundary) remain unchanged. Standalone desktop launches retain their token-dependent fixed-port selection, with `0` also resolving to a random usable port. Active fixed ports and pending launches reserve their port during admission, and the final HTTP bind remains authoritative if an external process takes that port after the check. The same stopped-instance dialog edits [assistant authorization](ai-assistant.md#managed-assistant-authorization); model-provider configuration stays in Mower settings.

Connection settings are drafts until Save. Writes preserve other YAML fields, including unknown private settings, and use atomic replacement. If only legacy `conf.yml` exists, the manager copies its complete mapping into the current path with the selected connection fields; normal startup retains responsibility for other configuration migrations. Invalid or unreadable configuration is not replaced with defaults. Failed configuration or instance-list writes retain the previous saved data. These changes preserve existing domain-concept definitions and require no glossary changes.

The same individual dialog and batch table expose Allow Updates through the [managed update authorization](software-update.md#managed-update-authorization) stored in each instance's configuration. Update All On and All Off change eligible rows' drafts independently of AI authorization. Ordinary connection edits do not submit an untouched update choice, including when another administrator changes that saved choice while the dialog is open.

Single-instance editing captures the row's name, directory and assistant choice when the dialog opens. A refresh closes the editor if that target changes or becomes non-editable, including after risk acknowledgement. Save compares the assistant draft with its opening choice rather than the latest status, so editing Token or port does not restore an externally changed authorization. The UI sends the captured `{name, path}` as the third argument to `update_settings(idx, settings, target)`. Under the shared lock, the backend reloads the instance list and rejects a missing or changed target before writing. Legacy two-argument callers retain their existing stopped-process checks without target comparison; the current UI always supplies the target.

### Browser Instance Management

Desktop and browser menus reuse [`MowerManager.vue`](../../ui/manager/MowerManager.vue) and its existing confirmations, stopped-process guards and draft handling. [`instanceManagement.js`](../../ui/src/utils/instanceManagement.js) uses the desktop bridge when available; browser sessions use the page's credentialed Axios client and [`instances.py`](../../arknights_mower/views/instances.py), which calls the same `InstanceController` without importing a GUI backend. Loading or refreshing the list does not launch or stop an instance. An unavailable or older backend exposes an error and an explicit retry rather than hiding the menu.

`GET /instances` returns the current manager rows. `POST /instances/actions` accepts `{action, args}` for the published manager operations. Both routes require the current session credential. Writes additionally require `X-Mower-Settings: 1` and reject a supplied foreign Origin; the explicitly configured loopback development origin remains available to authenticated local requests. Responses disable caching. The shared instance list is independent of saved configuration profiles, so profile-generation checks do not reject these operations; the existing configuration and manager locks remain effective.

Individual HTTP actions require the captured `{name, path}`. Add, bulk start and bulk stop additionally submit the accepted list's names, paths and order, which the controller checks under the admission lock before dispatch. Batch settings retain their existing captured-list check. Invalid requests return 400, unauthorized requests 403, changed targets or a busy manager lock 409, oversized requests 413, and unavailable storage or runtime scans 503; failure responses include a user-facing `message`. These results do not authorize automatic replay of a process operation.

Browser directory editing accepts an absolute path on the computer running Mower, independently of the browser's local filesystem. A directory need not exist yet; existing configuration and startup code retain responsibility for creating its files. Saving a path rechecks the captured identity and the stopped-process status of both the previous and proposed directories. Desktop sessions retain their native folder picker. Bulk stop sends the calling instance's exit request after the other configured instances.

Focused HTTP tests are in [`instances_http_tests.py`](../../arknights_mower/tests/instances_http_tests.py); frontend transport, directory editing, menu availability and stale-response checks are in [`instanceManagement.test.js`](../../ui/src/utils/instanceManagement.test.js), [`MowerManager.test.js`](../../ui/manager/MowerManager.test.js) and [`App.test.js`](../../ui/src/App.test.js).

### Batch Instance Settings

The manager's batch settings dialog is an editable table: instance names occupy the fixed left column, and Token, port and assistant choices occupy the other columns. Cells initially display each instance's existing values; different rows can use different settings. Names and storage directories remain unchanged. Running or otherwise non-editable rows are read-only. Only cells changed from the opening snapshot are submitted; restoring an original value removes that change. Clearing Token saves an empty value, and clearing port saves random selection (`0`). Fixed ports must be integers from 1 through 65535. Port occupancy remains authoritative at launch rather than being reserved by a configuration edit. Narrow windows scroll the table horizontally while retaining the instance-name column and column headings.

`update_all_settings(changes, targets)` accepts a list of `{idx, settings}` entries with partial per-row settings. It validates every index, rejects duplicate indices and invalid field values before any write, and checks the dialog's captured names, paths and order against the current instance list under the existing shared admission lock. A changed list rejects the whole request before writing; a frontend refresh also closes that obsolete editor and reading notice. Process state changes do not expand the target list. The backend rechecks registrations before each changed row and skips live processes, software-operation guards, missing directories and directory aliases already handled in this request. An incomplete initial scan prevents all writes; a later scan failure stops all remaining writes and reports them as failed.

Writes share the individual settings validator and atomic YAML replacement. Each file commits independently, not as a cross-directory transaction: a failed file retains its previous bytes, successful files remain committed, and later valid files can still succeed. Results report each row as `updated`, `skipped` or `failed`, with the UI showing counts and skipped or failed reasons. `ok=true` means result collection completed, not that every row changed successfully. Existing files already matching every selected value are not rewritten. Unknown private YAML fields remain intact, and unreadable mappings are not replaced by defaults.

The batch starts a ten-second monotonic dispatch budget before scanning; it checks the budget before each row and before each new file write. Exhaustion marks the remaining rows failed without starting more writes. This budget does not cancel an already executing filesystem operation. The ordinary bridge deadline still bounds frontend waiting and does not roll back completed files or cancel Python work. No operation is automatically retried. After checking the results, an administrator can retry; already matching files are not rewritten, allowing remaining writes to progress. Manager termination likewise preserves completed file replacements without storing drafts or pretending that the entire batch committed.

The AI All On and All Off commands change the eligible rows' drafts together. The first attempt to enable an AI cell or use All On requires one acknowledged, five-second notice covering the captured list, as defined in [Managed Assistant Authorization](ai-assistant.md#managed-assistant-authorization). That acknowledgement is shared by subsequent AI edits within the same table session; cancelling or reopening the table discards it. Confirmation changes only the requested cell or rows, and Save Changes commits the edited cells. Disabling requires no reading notice. Running rows remain unchanged; a previously edited row that starts before saving is reported as skipped by the backend.

Focused offline verification: `pytest arknights_mower/tests/manager_tests.py arknights_mower/tests/manager_instance_controls_tests.py`; from `ui/`, `npm test -- manager/bridge.test.js manager/MowerManager.test.js`. These tests cover partial field preservation, stopped-process guards, range validation, aliases, stale target lists, per-file failure, scan failure, budget exhaustion and progress on an explicit retry. Desktop lifecycle and registration regressions live in `webview_ui_tests.py`, `desktop_lifecycle_tests.py` and `update_runtime_tests.py` under `arknights_mower/tests/`. No live device or game operation is needed for these checks.
