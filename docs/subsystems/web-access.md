# Web Access

## 1. Session Boundary

`webview_ui.run_desktop` binds the service to `127.0.0.1` when the Web UI token is empty. It generates a runtime credential for protected HTTP endpoints and AI WebSocket access. Configuring a Web UI token binds the service to `0.0.0.0` and requires that token for protected requests.

Browser and embedded desktop launch URLs carry the session token without an instance name. After the page loads, it reads the current process registration through the protected process-control information endpoint and uses its registered name in the document title and app menu. An invalid token or unavailable registration leaves the ordinary title and default app-menu name unchanged. The process-control information endpoint returns the current registration's name only after the instance token check succeeds.

The desktop HTTP server writes 4xx and 5xx status codes at DEBUG through the shared logger. It omits the expected 403 response to the supervisor's marked, tokenless loopback GET probe of `/status`. Access and protocol-error records omit request URLs, query parameters and client addresses, including for malformed requests. Credentials still reach the application unchanged. [Desktop HTTP logging tests](../../arknights_mower/tests/desktop_http_log_tests.py) exercise the real server and supervisor probe with synthetic credentials and bounded local connections.

`/latest-screenshot`, `/screenshot/latest` and `/screenshots/<path>` require the current instance token for GET and HEAD before reading screenshot or archive files. The file route can also resolve archived log files, so knowing a path grants no access. The log schedule page reads images through the authenticated client, cancels obsolete requests and releases replaced object URLs. These routes have no tokenless local exception; the separately protected diagnostic log and export routes retain their existing local log-read boundary.

`GET /status` and its HEAD representation require the current instance token before reading operational state, including scheduling, recovery and deployment information. Browser polling uses the shared authenticated client. The process supervisor checks HTTP responsiveness without a token and treats this endpoint's 403 response as an available service; it does not read protected status data or persist the session token. Other HTTP errors retain the existing failed-probe behavior.

`GET /daily-status` requires the same current instance token before reading the game-day completion records and activity facts described in [Worker Status](base-scheduler.md#29-worker-status). It reads existing state without changing configuration, the scheduler, task dispatch or persisted data. A failure in this route leaves `/status`, and therefore the Start and Stop controls, unaffected.

PUT and DELETE `/stop-after-round` require the same current instance token before reading or changing the pending [Stop After Round](base-scheduler.md#stop-after-round) request. The log toolbar retains immediate Stop and offers cancellation while the request is pending; status polling restores that display after navigation or browser refresh.

The profile and GUI preference routes share HTTP credential checks in [`web_auth.py`](../../arknights_mower/utils/web_auth.py). Their OPTIONS preflight requests do not carry a token: the supplied Origin must match the current service, or the explicitly configured loopback development origin when the request itself is local and the instance has a token. The requested method must be registered on that path and cannot be OPTIONS. Preflight never parses operation inputs or reads instance state. The subsequent operation still requires the current token; profile writes also retain their confirmation headers and the [credentialed forwarding boundary](#credentialed-web-forwarding). Instance credentials do not grant [global instance-management access](#browser-instance-management). Focused offline verification is in [`web_auth_tests.py`](../../arknights_mower/tests/web_auth_tests.py).

### Credentialed Web Forwarding

<a id="credentialed-web-forwarding"></a>
Protected HTTP operations carrying the current nonempty Web UI token accept proxy-rewritten Host values, HTTPS termination and forwarded ports independently of Origin. The shared `check_request_origin` guard checks credentials before granting this allowance; without a configured nonempty token it retains the direct-origin check. The allowance covers software updates, shared network settings and connection tests, process control, configuration backup and profiles, database maintenance, diagnostic deletion and AI error analysis. Operation-specific headers, configuration generations, manager permissions and input limits still apply. Forwarded headers are not credentials and do not change the perceived request origin.

Log and AI chat WebSockets use the same first-frame credential check, with a five-second deadline and a 4096-character frame limit, independently of Origin and Host. AI chat additionally requires the instance's assistant permission. The local tokenless log-read exception remains restricted to its loopback Host, peer and browser metadata conditions. Tokenless CORS preflight retains the session-boundary restrictions above; a forwarded page and its APIs share their public browser origin and do not need a new cross-origin allowance.

The temporary software-update progress service applies the same credentialed forwarding behavior to status and cancellation using registered token hashes. Its static progress shell remains public; cancellation still requires update permission and the update header. Proxies must route HTTP requests and WebSocket upgrades to the instance and retain explicit credential and operation headers. Hosting beneath a rewritten URL path prefix is not provided by this boundary. Focused offline verification is in [`web_forwarding_tests.py`](../../arknights_mower/tests/web_forwarding_tests.py), [`ai_security_tests.py`](../../arknights_mower/tests/ai_security_tests.py), [`log_access_tests.py`](../../arknights_mower/tests/log_access_tests.py) and [`software_update_progress_tests.py`](../../arknights_mower/tests/software_update_progress_tests.py).

## 2. Log Read Interface

The local-only session accepts read-only log requests without a credential at `/log`, `/diagnostics/timeline`, `/diagnostics/errors`, and the diagnostic log and export routes. The request must arrive from a loopback address with a loopback Host. Browser origin and fetch metadata must identify the same local Web UI; the log WebSocket requires an Origin header. Cross-origin and remote requests fail. Sessions with a configured token require that credential.

AI chat at `/ws/chat`, AI analysis, diagnostic deletion, and other mutating endpoints do not receive the local log-read exemption. The source-snippet tool retains its file allowlist.

For authenticated `/log` subscriptions, the first frame carries the valid Web UI token within five seconds. This credential authorizes the log subscription independently of Origin, Host, scheme or port, including absent Origin and proxy-rewritten Host values. HTTPS termination and port forwarding require WebSocket upgrades to reach the backend; forwarded headers grant no tokenless access. Other protected operations follow [Credentialed Web Forwarding](#credentialed-web-forwarding).

The process-local logging relay and frontend relay each retain at most 256 waiting messages. Producers evict the oldest waiting entry when full, including when no frontend consumer exists; shutdown sentinels also remain admissible. Each asynchronous message is limited to 16,384 characters with an explicit truncation marker. These limits apply to live delivery and console output; the separately attached runtime file handler receives the complete original record. Eviction can omit a live notification and its automatic screenshot archive trigger. Existing per-client subscription limits remain in force. Focused offline checks are in [`runtime_memory_tests.py`](../../arknights_mower/tests/runtime_memory_tests.py), [`log_tests.py`](../../arknights_mower/tests/log_tests.py) and [`log_stream_tests.py`](../../arknights_mower/tests/log_stream_tests.py).

### Live Log Records

A full live queue reports a rate-limited WARNING with group `runtime-log`, displayed as 日志显示, when it discards an ordinary INFO-or-higher record. The message explains that some earlier records were skipped to display the latest content and directs the reader to `runtime.log`. Discarding DEBUG or NOTSET records, shutdown sentinels or this notice itself does not produce a user warning. Inserting a shutdown sentinel also suppresses the warning so that a new notice cannot displace the sentinel. Queue eviction counters remain available for diagnostics; the message does not present them as a count of missing business records. This group belongs to this subsystem; it does not inherit a neighbouring HTTP or business heading. The file handler remains independent of the live queues.

The run entry has no file-wide business fallback: startup and configuration-space notices have no business group, while actual scheduling notices set `base-scheduler` explicitly. OCR initialization uses `recognition`. [Startup checks](../../arknights_mower/tests/startup_log_groups_tests.py) exercise the entry path without preparing a device. The WebUI displays `maa-integration` as MAA日常; the transport value stays unchanged.

Mixed business modules set `log_group` on the specific log call. Public recruitment notices use `recruitment`, warehouse scan notices use `depot-recognition`, native daily tasks use `local-operation`, and MAA task progress uses `maa-integration`. MAA engine loading, connection and release use `maa-runtime`; navigation resource updates use `software-update`. Shared inventory-based stage selection uses `weekly-plan-editor`, and post-scan mastery planning uses `growth-planning`. Base reports, trust rotation and the common end-of-round rest forecast remain `base-scheduler`. Clue collection, receipt, placement, gifting and exchange timing use the `clue` business group, owned by [Clue Collection & Exchange](base-scheduler.md#clue-collection-exchange). Credit-shop records use the `credit-shop` business group, displayed as 信用商店购物, even when reached from the clue workflow. Their retained-failure and ordinary recovery notices use the same shopping group. These overrides retain the message, severity, source location and screenshot options, and do not propagate to calls made by device or recognition modules.

Each `/log` log message is a JSON object with `"type": "log"`. `records` holds structured records and `data` holds the same lines as `t level msg` text. A live broadcast carries one record; the history snapshot sent on subscribe carries every retained entry in both shapes. Legacy text arrives with its unchanged text in `msg` and the stream sequence in `seq`. Older senders may provide `data` alone. The frontend relay receives shared-logger records at INFO and above; DEBUG lines reach only the console and the runtime file.

Shared-logger records have `t` (the asctime string), `level` and `msg`. `msg` is the message text with any archive notice; when it is truncated for live delivery, the truncation marker and the archive notice stay at its end. A call site adds optional fields through `extra`: `log_group`, `log_room`, `log_agents`, `log_duration_ms` and `log_error_code` arrive as `group`, `room` (an internal room identifier such as `room_1_1`), `agents` (a list of operator names), `duration_ms` and `error_code`. `group` identifies the business displayed for the line. It normally uses the owning subsystem description filename without `.md`, such as `base-scheduler`. A finer business group retains its existing subsystem owner through `BUSINESS_GROUP_OWNERS` in `log_groups.py`; `clue` and `credit-shop` belong to `base-scheduler` and display as 线索 and 信用商店购物. `_build_log_record` uses an explicit `log_group` first; otherwise it derives the value from the record's source module through the ordered prefix table in [`utils/log_groups.py`](../../arknights_mower/utils/log_groups.py). A module outside that table produces no `group`. Call sites set the remaining fields only when they need them, and consumers accept a record without any of them. The runtime file handler keeps its text format and ignores these fields. `ui/src/stores/mower.js` reads `records` and falls back to `data` when an older message has no nonempty record array. Focused offline checks are in [`log_tests.py`](../../arknights_mower/tests/log_tests.py), [`log_stream_tests.py`](../../arknights_mower/tests/log_stream_tests.py) and [`mower.test.js`](../../ui/src/stores/mower.test.js).

Structured records produced by the shared logger also carry `at`, the record creation time in Unix milliseconds. The frontend uses a finite numeric `at` for elapsed-time calculations, so different client and server time zones do not change scene-wait timing. Older records without this field retain the existing `t` parsing fallback; `t` remains the display and text-export representation.

Additional display snapshots preserve their source text. `log_event`, delivered as `event`, accepts the event shapes below. `log_inventory`, delivered as `inventory`, contains an ordered `items` array of `{name, count}` entries: 1–512 items, nonblank names of at most 256 characters and nonnegative integer counts within JavaScript’s safe integer range. These snapshots share the existing 16,384-character live budget with the message, task, recruitment and backup fields. Invalid or oversized metadata is omitted as a whole; the original message follows the existing text fallback. The enqueue handler copies these fields before returning to the producer, and the relay retains independent snapshots for history. Display fields do not participate in execution.

`log_parent`, delivered as `parent`, explicitly associates a source record with an operation. A rescue task uses `{type: "rescue-staffing", id, room?, attempt?}`. IDs and the optional room and attempt strings are nonblank and at most 128 characters. The room and attempt appear together; an attempt identifies one existing facility-arrangement lifecycle. A root-level task diagnostic may omit both. Ordinary facility attempts, staffing attempts during Fiammetta charging and both staffing changes of a trade order run use `{type: "facility-arrangement", id, room}` with the same ID and room as the corresponding arrangement event. The temporary staffing and original-roster restoration each use their own ID. Order collection stays outside these staffing scopes. The rescue reference takes precedence when the attempt belongs to a rescue task. A recruitment slot uses `{type: "recruitment-slot", id, slot}`, where `slot` is an integer from one to four. Its event shares those fields and optionally adds `phase`. A `started` event anchors the first concrete operation for that slot. A matching `completed`, `failed` or `stopped` event updates the same summary. Older events without a phase establish grouping only. The producer binds this context when creating each record, before queue transfer, restores it on every exit and keeps independent threads and asynchronous contexts separate. Explicit record metadata takes precedence. Unknown fields are discarded, invalid references are omitted, and the retained reference shares the existing live budget and queue/history snapshot isolation. The reference does not grant access: the [local log-read boundary](#local-log-read-boundary) and [credentialed forwarding](#credentialed-log-forwarding) remain unchanged.

Warehouse scans, product and trade-strategy switches, order reads, manufacturing observations and real-time mood calculations associate ordinary records through `{type, id}` with the same type and ID as the operation event. The producer attaches the reference during the actual work that owns the record. The frontend matches that reference to the operation’s start record. Records without a matching start remain readable at their own positions.

[Rescue payload tests](../../arknights_mower/tests/rescue_staffing_payload_tests.py) cover source-context isolation, cancellation cleanup, malformed references, queue/history snapshots and the shared live budget. [Log access tests](../../arknights_mower/tests/log_access_tests.py) retain coverage of local access and credentialed forwarding.

Names are nonblank strings of at most 256 characters; counts are positive integers within JavaScript’s safe integer range. The frontend displays every item with its icon and count.

The nonblank date is at most 32 characters; 1–64 ordered items each contain `name`, `value`, `unit` and `item`. Names and item-icon names are nonblank strings of at most 256 characters, and units are nonblank strings of at most 32 characters. Each known value has one space before its actual unit; unread values say 未读出 without a unit, while zero remains a numeric reading. The display label 合成玉订单数 leaves the stored field name unchanged. Material icons and every reported item remain visible without collapse controls.

The nonblank code is at most 64 characters; `drops` contains at most 64 nonblank material names of at most 256 characters. Hovering, focusing or clicking the stage shows those principal drops with icons. The materials that satisfy the configured limit are described in the message and need not be the stage’s principal drops. An empty drop list indicates unavailable drop information.

Principal drops come from stage data rather than the material bound to a ratio rule. Selection does not start an execution animation or alter the stage-selection algorithm.

Codes are strings of at most 64 characters, nonblank except for the empty code meaning 上次作战; labels are nonblank strings of at most 64 characters. Ordinary labels equal their codes. `Annihilation` displays 当期剿灭, and the empty code displays 上次作战; both virtual stages have an empty drop list. Each ordinary stage has at most 64 nonblank principal-drop names of at most 256 characters. Nonempty results use 接下来计划依次刷取 followed by the ordered labels joined with ` → `; the frontend validates this complete suffix and decorates only the corresponding ordinary-stage spans. The result describes this calculation rather than promising an entire round's execution or stopping automation. Existing no-rule and disabled early returns retain their logging behavior.
- `{type: "training-selection", positions}` describes the actual pending selection in the training room. One or two ordered entries each contain a nonblank `agent` name of at most 256 characters and a unique integer `index`: zero is the support position and one is the training position. The frontend indents this action beneath the facility context; selection alone does not confirm staffing completion.
- `{type: "facility-arrangement", id, phase, room, label, agents}` records one facility arrangement. The nonblank ID, room and facility label are at most 128 characters each; `agents` contains at most five nonblank names of at most 256 characters. Optional `anchor` is a boolean. A `started` record with `anchor: true` names the facility after actual entry and establishes its progress heading. An optional single-line `summary` of at most 1,024 characters matches the source message and supplies the wording for the heading. Trade order staffing names the incoming order operators. When an explicit Fiammetta task names a target and the dormitory plan matches the charging positions, the start heading names the charging operator and target. Confirmation requires reliable position readback. Protection skips and failures before entry do not announce an arrangement start. Subsequent `completed` or `failed` records also carry `anchor: false` and the same ID; completion follows confirmation and room-exit cleanup, while failure ends the attempt without declaring its arrangement complete. A later `updated` record cannot reopen a completed or failed attempt. An empty name list does not establish that a facility is being emptied. The frontend updates only the explicitly anchored heading for the same ID, room and label, stops its animation when execution stops, and retains each source record for copying in its original position. Older records without an anchor field, and updates whose anchor is outside the loaded window, retain their ordinary source-text presentation. The first measured operation emits `started` with `anchor: true`. The matching `completed` or `failed` record reports the outcome and total duration at the original heading. Older `updated` records remain readable. Each `summary` is a single line of at most 1,024 characters and matches `msg`. Plain calculation details carry a `{type: "mood-calculation", id}` parent that references the same batch. The retained log keeps the source records together. A record without its original heading remains readable as source text.

The ID is nonblank and at most 128 characters. The phase is `started`, `updated`, `completed`, `failed` or `stopped`. Only `started` has `anchor: true`. The single-line summary matches `msg` and has at most 1,024 characters. Completion follows the successful warehouse writes and reports the number of distinct item quantities confirmed by the scan. ID, room and label are nonblank strings of at most 128 characters; `facility` is `manufacture` or `trade`; `product` and optional `previous` are nonblank display names of at most 256 characters. Actual survey establishes the original heading; later matching records update that heading with the current phase. For historical records without an explicit parent reference, the event detail remains readable under the heading. Completion follows target readback and required production-queue verification. - `{type: "order-read", id, phase, anchor, after_switch, rooms, detail?}` records actual order-countdown reading. The nonblank ID is at most 128 characters; `phase` is `started`, `updated`, `completed` or `failed`; `anchor` and `after_switch` are required booleans. Only `started` has `anchor: true`. One to 32 ordered, unique room entries contain nonblank `room` and `label` strings of at most 128 characters and a `status` of `pending`, `read` or `paused`. Started and updated events retain at least one pending room; completed events retain none. Optional nonblank `detail` is at most 2,048 characters and belongs only to a failed attempt. A cohort after product switching includes only the actual new or reused order-refresh tasks, identified by object identity; unrelated reads do not inherit its completion prefix. The first actual read establishes its heading after the order page is ready, rather than when refresh work is queued. Every room is resolved from its own countdown result or confirmed paused-order observation; one successful room and task removal do not establish that the whole cohort was read. Failed, invalidated or abandoned display attempts end without consuming unread scheduler work. Display contexts retain at most 32 cohorts and do not introduce tasks, timers or dispatch dependencies. These records retain the existing log-read authorization, source-copy, snapshot and shared capacity boundaries.

Training-room arrangement events may also carry `positions` in the training-selection shape above. Each named operator must belong to the event’s `agents` list. The snapshot preserves support and training roles when the selected roster or order changes before completion. All display events retain the existing shared capacity limit and independent queue/history snapshots; malformed metadata falls back to its original text.

Task forecasts add optional `log_task`, delivered as `task`. Its `header` is the waiting and next-task message, `title` describes the task, `rooms` contains ordered `{id, label, agents}` entries, `backups` contains `{name, active}` changes, `targets` contains `{id, label}` entries for tasks without a staffing plan, and `wait_seconds` retains the waiting duration at the time of the record. Optional `actions` contains `{kind, subject, action}` entries, where `kind` distinguishes `group` and `operator`, and `action` is 上班, 下班, 休息 or 转为空闲 under the [task-presentation rules](base-scheduler.md#task-presentation). Group entries also carry optional `members`, an ordered list of operator names; older snapshots without either field remain readable. The producer copies this JSON snapshot before enqueueing; the relay also preserves the published snapshot for history. `msg` retains the complete readable arrangement for the runtime file and older clients. The message text and compact task JSON share the 16,384-character live budget. An invalid or oversized task snapshot is omitted as a whole, leaving the existing text fallback and truncation behavior; individual staffing positions are not trimmed to fit.

Recruitment messages add optional `log_recruitment`, delivered as `recruitment`, with `event` (`tags`, `start` or `rare`) and `rarity` (null or an integer from one to six). Single-group records carry `tags`, one to five nonblank strings of at most 32 characters each. A multi-group `rare` record instead carries `combinations`, one to 25 `{tags, rarity}` entries; each entry has one to three tags under the same string limit and an integer rarity from one to six, as does the notice's top-level rarity. A record cannot carry both top-level `tags` and `combinations`. The producer copies only these fields, including nested tag lists, before enqueueing. The compact JSON is limited to 4,096 characters and shares the existing live budget with `msg` and any retained task snapshot. Invalid or oversized metadata is omitted; the text remains the fallback. This display metadata retains the existing [local log-read](#local-log-read-boundary) and [credentialed forwarding](#credentialed-log-forwarding) boundaries. [Recruitment transport tests](../../arknights_mower/tests/log_recruitment_tests.py) cover snapshot isolation, shape validation and shared capacity limits.

Completed backup switches add optional `log_backups`, delivered as `backups`: one to 128 `{name, active}` entries with nonblank names of at most 128 characters and Boolean activation states. The producer copies only these fields before enqueueing and counts the complete snapshot with the message, task and recruitment metadata under the shared live budget. Invalid or oversized snapshots are omitted without changing the text. The frontend highlights captured full names before operator or group matches; later configuration changes do not rename historical switches. [Backup field tests](../../arknights_mower/tests/log_backup_fields_tests.py) verify isolation, validation and shared capacity limits.

Authenticated `GET /task` and its HEAD representation read the current queue without preparing or dispatching work. Existing task fields remain available. An item with a readable staffing plan adds `presentation` with `title`, `rooms`, `backups`, `targets` and `actions` in the same shapes as the forecast. An item with a malformed staffing plan retains its original fields and omits `presentation`, so other items remain readable. The shared instance-token guard runs before scheduler access for GET, HEAD and POST. The [task presentation rules](base-scheduler.md#task-presentation) own the meaning and sources of these fields. Focused checks are in [`task_presentation_route_tests.py`](../../arknights_mower/tests/task_presentation_route_tests.py).

### Retained Log Window

The live log retains at most 100 top-level entries. An operation, its matching lifecycle updates and explicitly associated details occupy one entry; an unassociated record occupies its own entry. A valid explicit parent reference reserves that entry when details precede the operation’s start record. Only a matching start record establishes a summary heading; retaining early details does not invent one. Line wrapping, concise mode and opening details do not change this count. The backend owns retention so live delivery and history replay use the same window.

Each operation retains its most recent 50 ordinary detail records in addition to the evidence needed to render its summary and state. The retained source window also has hard limits of 2,000 records and 4 MiB for the complete serialized history message, including both `records` and legacy `data`. Original anchors, lifecycle state, recruitment results and scene transitions are retained together; when protected evidence cannot fit, the oldest complete entry is removed. Removing a scene transition must not restore an earlier scene as an active wait. These bounds may leave fewer than 100 entries. Source records keep their original order and text. Expanding or copying a retained entry includes only its remaining source records; the runtime log file retains the complete records under its existing retention policy.

Log messages carry a `stream_id`, a Boolean `snapshot` and structured `records` with positive integer `seq` values. A subscription starts with `snapshot: true`; the frontend replaces its window atomically and keeps record identity stable for the same stream and sequence. Live messages use `snapshot: false` and an `evicted` array of removed sequence values, including an incoming record if it exceeds the retention budget. Replayed sequence values do not append duplicate records. Clearing the stream changes its ID and sends an empty snapshot. Legacy text remains available in `data` and appears as `{msg, seq}` in `records`. For older backends without this protocol, the first log message on each connection replaces the frontend's retained window. Later log messages append to that window, bounded to the latest 2,000 source records and 4 MiB of serialized JSON.

This changes no log-read authorization or scheduler state. Focused checks exercise retention and live/history equivalence through [`log_stream.py`](../../arknights_mower/utils/log_stream.py), [`log_history_tests.py`](../../arknights_mower/tests/log_history_tests.py) and the real WebSocket consumer in [`mower.test.js`](../../ui/src/stores/mower.test.js).

## 5. Desktop Startup

`webview_ui.run_desktop` evaluates `start_automatically` once per process, in foreground and background modes. Browser refresh, closing and reopening the window, tray browser actions, and importing configuration do not schedule another automatic start. Manual task controls remain available.

The startup worker waits for the active software update operation to finish. When resource checking and automatic installation are enabled, it checks and completes installation before admitting automatic tasks. Pending task startup also waits for existing MAA core, MAA resource and Mower resource update workers to exit, including failed updates. It releases configuration and maintenance locks while waiting and rechecks maintenance under the shared admission lock before starting tasks with the original startup mode. Stop, application shutdown or a configuration-profile change cancels this wait. Resource check or installation failure preserves the existing resource fallback and still permits task startup. Stop or application shutdown cancels pending automatic admission, including during the resource step. Resource automation also runs when task autostart is disabled. The frontend observes tracked resource jobs and retains manual resource installation.

Configuration, mastery plans and database records remain intact. Older update workers do not send the new flag and retain their original startup behavior. Ordinary process-operation restarts set `MOWER_RESUME_MODE=preserve`: `MOWER_RESUME_RUN=1` starts mode `2`, while a previously stopped task stays stopped regardless of the saved autostart option. Other hosts that do not claim desktop startup ownership retain their existing frontend fallback; this change does not alter the separate Android launcher.

#### Recorded Order Candles

## 7. Instance Manager

Windows directory browsing in the manager and instance desktop windows uses the native `IFileDialog` folder picker through [`folder_dialog.py`](../../arknights_mower/utils/folder_dialog.py), rather than pywebview's legacy tree picker. It runs on the owning WinForms UI thread, selects one existing filesystem directory, accepts Unicode paths, and releases COM references and allocated path memory on selection, cancellation or failure. The system owns the resizable Explorer-style layout and saved dialog size. Cancellation does not change the saved directory; the manager retains its post-dialog identity and stopped-process checks. File selection and other platforms' existing dialogs remain unchanged, including the manager's macOS directory-creation support.

[`manager.py`](../../manager.py) exposes the manager bridge; [`InstanceController`](../../arknights_mower/utils/manager_instances.py) owns lifecycle admission and offline configuration writes. Instance names and directories remain in `instances.json`. The manager reads current runtime registrations with a strict, single-attempt scan and combines them with persisted launch reservations. Unreadable state blocks operations rather than authorizing another process or configuration overwrite. Resolved, case-normalized data directories identify instances, including directory aliases. A reservation remains active while its child process is alive, across manager window recreation; verified process exit releases it. Starting successfully means that process creation succeeded, not that HTTP startup is ready.

New manager launches discard inherited supervision and recovery environment before establishing their own launch identity. Folder dialogs belong to the standalone manager window.

The manager HTML displays startup status before Vue loads. Failure to load or execute the page entry module displays an error and instructions to reopen the manager and report the message; a browser without module-script support displays a compatibility message. These messages require the native browser to load the HTML and do not diagnose native browser initialization failures.

Before the first instance list arrives, the manager displays loading status rather than a zero-instance count. A failed initial load displays the error, marks the list as not loaded and provides a visible 重新加载 button. Retrying reads the list again; only a successfully loaded list supplies the instance count. A loading failure does not establish that the saved list is empty.

Individual row actions carry the captured `{name, path}`; under the admission lock, the backend rejects a changed or missing target before editing the list, launching or stopping a process, or opening a folder dialog. Folder selection validates that same identity again before saving.

The UI shows stopped, starting, running and stopping process states. Starting and running managed instances expose Stop, which sends the existing instance-specific graceful exit request, including before registration completes. It stops the entire instance and its automation, not just the automation thread. Ready managed instances also expose Open Window. Starting an already ready managed instance sends a show request instead of launching another process; a closed WebView is recreated, and an existing window is shown and restored. Starting or stopping instances cannot be reopened this way. Stopping does not permit editing or restarting until process exit. Non-managed instances sharing a directory block launch and edits but must be exited from their own application. The manager does not kill unrelated processes or force termination after a stop request.

Closing the manager leaves managed instances running. A newly opened standalone manager reloads the saved instance list and scans shared runtime registrations and startup reservations, so it can recover starting/running/stopping state, open a ready instance in its browser, stop it and start it again after exit. Matching uses the normalized instance storage directory and live managed registration, rather than the saved port or the former manager's in-memory process handles. Live independent launches block duplicate startup and editing but grant no stop or browser control. [`manager_reopen_tests.py`](../../arknights_mower/tests/manager_reopen_tests.py) covers an exited manager process and surviving offline registered processes; native tray reconstruction remains a separate platform check.

Manager list and configuration mutations run under a shared admission lock and recheck live processes. Folder selection releases that lock while the dialog is open, then verifies the original row and both directories before saving. The UI disables configuration controls while a process is live and closes stale edit dialogs; the backend remains authoritative. Bulk open and close each require a confirmation dialog. Bulk open checks each row's eligibility immediately before dispatch, silently skips ineligible rows and retains the individual startup checks. Actual startup failures remain warnings and do not prevent other eligible rows from being processed. Repeated registration scans and port probes add overhead with many instances. Deletion requires a separate confirmation naming the instance; it removes only the manager entry, not the saved files. Status refresh cancels a pending deletion if the selected row changes or becomes non-editable. Ordinary frontend bridge calls have a fifteen-second response budget; that deadline only ends the frontend wait and does not cancel Python work. Native directory selection waits for the user's confirmation or cancellation without that deadline and retains the UI's busy state until the call returns or fails, followed by a bounded state refresh. State refresh failures disable actions until a complete snapshot is available again.

Connection settings use each instance's `config/conf.yml`, under `webview.token` and `webview.port`, rather than a second copy in `instances.json`. A blank port saves as `0` and requests a random port. Managed launches honor an explicit port from 1 through 65535 regardless of whether a token is configured. Existing token binding rules in [Session Boundary](#1-session-boundary) remain unchanged. Standalone desktop launches retain their token-dependent fixed-port selection, with `0` also resolving to a random usable port. Active fixed ports and pending launches reserve their port during admission, and the final HTTP bind remains authoritative if an external process takes that port after the check. The same stopped-instance dialog edits [assistant authorization](ai-assistant.md#managed-assistant-authorization); model-provider configuration stays in 全部设置.

Connection settings are drafts until Save. Writes preserve other YAML fields, including unknown private settings, and use atomic replacement. If only legacy `conf.yml` exists, the manager copies its complete mapping into the current path with the selected connection fields; normal startup retains responsibility for other configuration migrations. Invalid or unreadable configuration is not replaced with defaults. Failed configuration or instance-list writes retain the previous saved data. These changes preserve existing domain-concept definitions and require no glossary changes.

The same individual dialog and batch table expose 更新与维护 through the [managed update authorization](software-update.md#managed-update-authorization) stored in each instance's configuration. Its header checkbox changes eligible rows' drafts independently of AI authorization. Ordinary connection edits do not submit an untouched maintenance choice, including when another administrator changes that saved choice while the dialog is open.

Single-instance editing captures the row's name, directory and assistant choice when the dialog opens. A refresh closes the editor if that target changes or becomes non-editable, including after risk acknowledgement. Save compares the assistant draft with its opening choice rather than the latest status, so editing Token or port does not restore an externally changed authorization. The UI sends the captured `{name, path}` as the third argument to `update_settings(idx, settings, target)`. Under the shared lock, the backend reloads the instance list and rejects a missing or changed target before writing. Legacy two-argument callers retain their existing stopped-process checks without target comparison; the current UI always supplies the target.

The managed MAA 核心 panel retains only the restore-theme option and its target theme. MAA directory, connection, touch and connection-test controls are hidden; `MaaBasic` does not start connection discovery merely by mounting in a managed instance. The manager owns the MAA directory and retains its common path setting and maintenance tools. Standalone launches retain the complete connection and theme panel. MAA update controls use the [network and update section](software-update.md#7-maa-resource-updates).

The standalone manager's per-instance 连接与启动 editor reads effective saved/shared settings, offers native path selection and bounded device discovery, and saves explicitly changed fields through the existing `Conf.updated` validation and atomic YAML replacement. Discovery and candidate selection do not persist configuration or start a simulator. Instance UUID and topology fingerprint are hidden from manual editing; changes to these recorded identity values must match a freshly detected simulator instance, while target edits retain automatic identity clearing. Saves require a captured instance name and directory, a matching original settings snapshot, a stopped process and no active software operation. Target changes retain the existing endpoint and identity reset rules. Unknown private configuration fields remain intact. Shared connection parameters apply at the next managed launch unless the instance uses 独立配置.

The editor distinguishes instance discovery results from connection-test results. Instance choices use their discovery key and verified binding; BlueStacks Air connection-test choices display the observed ADB serial and state, retain repair guidance, and require an explicit address selection. The selected Air preset and validated application/ADB paths accompany the address; a failed test does not confirm a game package or connection readiness. For Air, manual MuMu Pro without a topology fingerprint and the manual presets, an explicitly selected or reentered serial survives accompanying target edits during detection and on Save, including when it equals the previous target's address. Editing a target invalidates the preceding address confirmation; without an explicit address submission the ordinary endpoint-clearing rules apply. Runtime still validates the selected endpoint at the next launch.

Instance windows expose no native instance-management, device-editor, common-settings or maintenance bridge. These capabilities have no HTTP fallback. Protected `/conf` writes reject changed manager-owned device settings, MAA location, managed automatic-start preferences, instance port and token, and currently protected maintenance settings with HTTP 403 before persistent changes. Legacy full-form echoes of unchanged values remain accepted. Managed processes reject device discovery/start, performance-test writes, custom screenshot and boss-key tests, and MAA connection tests even when invoked directly over HTTP. MAA update actions and policy edits follow [Managed Update Authorization](software-update.md#managed-update-authorization). Read-only status remains available. Existing Web UI token checks run before the manager-ownership refusal, request parsing and device actions; valid instance credentials do not grant manager configuration authority.

Instance configuration imports and profile creation, switching or imports preserve manager-owned device and runtime settings, MAA directory, automatic-start preferences, the unified maintenance and AI permissions, effective common values and saved per-instance overrides. Hidden network/maintenance settings retain their current values, while the shared network document keeps its existing protection. Instance port, token and tray settings retain their existing preservation rules. The global `manager-common.json` file is excluded from instance exports, and imports neither create, replace nor remove it; shared `network.json` retains its existing import protection. Exporting an instance does not rewrite either the instance or manager configuration. Profile operations retain their existing clearing of prior task-run and recovery intent without changing the saved manager automatic-start choice.

Focused offline evidence lives in `manager_instance_controls_tests.py`, `manager_instance_overrides_tests.py`, `managed_http_boundary_tests.py`, `device_settings_route_tests.py`, `config_backup_tests.py`, `config_profiles_tests.py` and the manager/device frontend tests. ### Batch Instance Settings

The manager's 配置管理 dialog contains an editable table: instance names occupy the fixed left column, and Token, port and assistant choices occupy the other columns. Cells initially display each instance's existing values; different rows can use different settings. Names and storage directories remain unchanged. Running or otherwise non-editable rows are read-only. Only cells changed from the opening snapshot are submitted; restoring an original value removes that change. Clearing Token saves an empty value, and clearing port saves random selection (`0`). Fixed ports must be integers from 1 through 65535. Port occupancy remains authoritative at launch rather than being reserved by a configuration edit. Narrow windows scroll the table horizontally while retaining the instance-name column and column headings.

`update_all_settings(changes, targets)` accepts a list of `{idx, settings}` entries with partial per-row settings. It validates every index, rejects duplicate indices and invalid field values before any write, and checks the dialog's captured names, paths and order against the current instance list under the existing shared admission lock. A changed list rejects the whole request before writing; a frontend refresh also closes that obsolete editor and reading notice. Process state changes do not expand the target list. The backend rechecks registrations before each changed row and skips live processes, software-operation guards, missing directories and directory aliases already handled in this request. An incomplete initial scan prevents all writes; a later scan failure stops all remaining writes and reports them as failed.

Writes share the individual settings validator and atomic YAML replacement. Each file commits independently, not as a cross-directory transaction: a failed file retains its previous bytes, successful files remain committed, and later valid files can still succeed. Results report each row as `updated`, `skipped` or `failed`, with the UI showing counts and skipped or failed reasons. `ok=true` means result collection completed, not that every row changed successfully. Existing files already matching every selected value are not rewritten. Unknown private YAML fields remain intact, and unreadable mappings are not replaced by defaults.

The batch starts a ten-second monotonic dispatch budget before scanning; it checks the budget before each row and before each new file write. Exhaustion marks the remaining rows failed without starting more writes. This budget does not cancel an already executing filesystem operation. The ordinary bridge deadline still bounds frontend waiting and does not roll back completed files or cancel Python work. No operation is automatically retried. After checking the results, an administrator can retry; already matching files are not rewritten, allowing remaining writes to progress. Manager termination likewise preserves completed file replacements without storing drafts or pretending that the entire batch committed.

Each boolean column has a header checkbox that changes only editable rows in the current draft. Its checked and indeterminate states follow those editable rows; running or missing-directory rows do not contribute. An empty editable set disables the header. Individual row checkboxes update the same aggregate state. The first attempt to enable an AI cell or check its column header requires one acknowledged, five-second notice covering the captured list, as defined in [Managed Assistant Authorization](ai-assistant.md#managed-assistant-authorization). That acknowledgement is shared by subsequent AI edits within the same table session; cancelling or reopening the table discards it. Confirmation changes only the requested cell or rows, and Save Changes commits the edited cells. Disabling requires no reading notice. Running rows remain unchanged; a previously edited row that starts before saving is reported as skipped by the backend.

### Manager Common Settings

The 通用设置 area appears above the batch instance table. It stores shared connection parameters once in `@app/config/manager-common.json`, outside instance spaces, together with each normalized instance-directory path's 独立配置 policy. Connection parameters are shared by default and use ordinary field labels; they cannot be unchecked individually. Only optional common fields have sharing checkboxes. An instance can opt out as a whole through 独立配置 in its manager-owned connection editor. The other five fields—MAA location, screenshot saving, screenshot archive limit, startup mode and page-opening mode—allow individual instance overrides. An explicit instance value takes priority over the selected common value; without an override, the instance inherits the common value when selected. Changing common values does not overwrite saved instance values. For the three Conf fields, ordinary saves and configuration/profile imports retain the stored local values while the running process continues to use its launch snapshot. Selecting 使用本实例值 later restores that stored value. The launch records which fields it actually inherits, so a later common edit cannot change that persistence rule for a live process. Inherited screenshot controls stay read-only even when extra maintenance settings are visible; `/conf` exposes their source as read-only `manager_inherited_settings` metadata. The manager groups simulator templates, paths, connection backends, performance, recovery, game startup, runtime timing and instance startup in one expanded 连接与启动 block with continuous subheadings.

The common editor and the manager-owned independent instance editor show one idle-action selector: no action, return home, exit game or close simulator. Selecting an action writes mutually exclusive legacy flags; opening an old configuration preserves its values and displays the scheduler’s close, exit, then home priority. Closing and exiting still require more than five minutes of idle time. Physical-device presets disable closing the simulator. The MuMu 12 ADB-disconnection option appears only with that preset and the close action. Custom screenshot commands, DroidCast rotation, tap coordinates, custom game-launch commands and boss-key delay appear only when their corresponding backend, launch method or boss key is selected; hiding a field retains its draft value. New custom screenshot defaults omit a fixed ADB serial and use the selected instance through the existing command validation. Explicit saved commands remain unchanged and an explicit serial must match the selected instance.

Shared connection parameters include the simulator preset and installation/manager/configuration paths, ADB executable, screenshot/touch backends and commands, recovery budgets, capture/selection timings, the six-row scene-waiting table, game launch method and idle actions, and performance settings. The native manager's 实例配置 dialog provides the 连接与启动 entry. Shared mode exposes only the simulator instance number, instance name and game package as manual inputs. Other connection fields use the common template; an edit cannot override them. The ADB endpoint remains specific to the selected instance, is not shared between instances and is not manually editable in shared mode. Target edits retain endpoint clearing and bounded discovery; manually specifying an endpoint requires 独立配置. UUID and topology fingerprint remain detection-verified identity fields rather than manual inputs. Discovery cannot replace the shared preset or paths with another template. Manager permissions remain separately owned by the manager. Switching to independent mode begins with the effective inherited values and exposes the connection and runtime parameters, including all six waiting rows, for that instance. Switching back uses the current shared parameters at the next managed launch.

The versioned document accepts the former flat common-settings mapping. On first manager access, migration takes the first coherent configuration expressible by the shared field schema as its baseline, or uses the application defaults when none qualifies, while retaining selected old shared values. Existing instances with different simulator templates, explicitly different connection parameters, values outside the shared form limits or incompatible inherited combinations retain independent settings without changing their effective values. Template comparison includes formerly effective defaults: an omitted path that meant automatic discovery must not inherit a different installation during migration. Ordinary migration leaves instance files unchanged. Old flat installation and manager paths remain in the common template; if an instance becomes independent because of other differences, migration materializes its formerly effective binding and synchronized legacy identity fields in that instance. An earlier versioned document without the four simulator-template fields or scene-waiting table receives the missing fields during migration. Previously independent instances stay independent; previously shared instances with different simulator templates or waiting tables become independent while retaining the connection, performance and waiting values that were effective before the upgrade. All affected files are prepared before writes; a write failure restores their original bytes, and an incomplete restoration reports an error. Policy and common defaults commit in one atomic document replacement; later policy edits also compare the opening common values, instance values and policy snapshot, and roll back a preceding instance-file replacement if the policy write fails. Saved policies follow storage directories rather than row indices, and instance backups and profiles cannot create or replace them.

Version 2 adds `instance_overrides[normalized_path]` containing `local_keys` for the three instance-Conf fields and `manager_values` for startup/page-opening modes. Conf values remain only in the instance configuration; manager-only modes remain outside it. Flat and version 1 documents remain readable, and saving an override upgrades the document to version 2. Retired sender fields are filtered only while reading old documents; new submissions reject them. A complete versioned document is cleaned on the next successful manager write rather than a read. Existing instance SMTP settings are neither cleared nor migrated.

A managed process applies a snapshot after loading its own configuration at startup, including update restarts. Independent instances skip the shared connection subset; the other selected common fields apply only when the instance has not selected its own value. Saving common settings does not rewrite instance configuration or change live sessions. Direct standalone launches do not read this file and retain their full settings editors. Invalid or unreadable common data fails explicitly instead of replacing the file with defaults.

The effective `startup_mode` controls each manager launch, including individual rows within a bulk launch: the instance override takes priority over the common selection. Absent or `window` retains ordinary startup with an embedded window; `background` passes the existing `MOWER_BACKGROUND=1` launch setting and creates neither an instance splash nor an initial embedded window. The help beside Startup Mode explains background access and its next-launch effect. This manager-owned value is not applied to `Conf` or written into instance configuration. Changing it leaves running processes untouched, while update and recovery restarts retain their existing startup rules. Automatic task admission remains governed by [Desktop Startup](#5-desktop-startup).

Each instance row places 打开实例页面 beside its name. It is enabled only for a ready, manager-controlled instance without a pending shutdown. Without an explicit request mode, page opening resolves the instance override before the common `instance_page_mode`. A ready instance with no resolved mode returns `needs_mode` without writing or dispatching. The manager then offers 外部默认浏览器 (initially selected) and 内置 WebView. The 记住我的选择 checkbox starts unchecked. Cancelling does nothing; confirming validates the target again and dispatches the command. The explicit selection controls this request. With the checkbox checked, it atomically saves only the global manager preference and preserves all instance overrides; otherwise the selection applies to this request and a later request without a resolved choice asks again. Subsequent requests again give instance overrides priority. The 配置管理 dialog can change the remembered choice later. This preference is stored outside instance configuration and affects explicit page opening independently of startup mode.

The local `open_instance_page(idx, target, mode=None, remember=False)` bridge operation checks the captured name and directory against the current list and rechecks registrations and shutdown state under the manager lock before dispatching `browser` or `show`. The compatibility `open_browser` operation continues to dispatch `browser` without changing the remembered choice. Stopped, starting, stopping, unmanaged, changed and unreadable targets return an error without dispatch. The instance uses its own actual port and session credential for browser opening, or creates/restores its own WebView for `show`; the manager neither constructs a URL from saved configuration nor returns a credential in this result. A successful bridge result confirms dispatch, not that a page or window has appeared. Opening does not change existing automation. These actions use only the local bridge and have no manager HTTP route.

The top-level 一键开启页面 action calls `open_instance_pages(targets, mode=None, remember=False)` with the captured complete instance list. It validates the list under the manager lock and rechecks each instance before dispatch. When all ready instances resolve a mode, each uses its own effective mode without a prompt. If a ready instance has no resolved mode, the batch asks once; that explicit request choice applies to all ready instances in the request, and remembering it changes only the global default. Non-ready or unmanaged instances are skipped; per-instance results distinguish dispatched, skipped and failed commands. A ten-second monotonic budget bounds starting further commands; scan failures stop the remaining dispatches. No request is retried automatically. If no instance can open, the operation neither asks for a choice nor saves a preference. List changes while the choice dialog is open cancel that pending request.

Device changes use `Conf.updated`, retaining instance identity and applying endpoint and identity-verification reset only when that instance’s binding changes. Native capture remains preset-specific; incompatible capture selections fail configuration validation rather than changing the target device. Screenshot and touch selections retain MuMu IPC coupling. No emulator, network request or connection test runs while saving common settings.

Common edits use an optional third argument to `update_all_settings`: `{values, original}`. The bridge validates an explicit field allowlist, types, numeric bounds and backend pairing before writing, compares the original common snapshot and captured instance list under the existing manager lock, and rejects stale edits. The common file commits atomically before any selected per-instance edits; `common_saved` reports this independent commit even when individual rows are skipped or fail. A failure before that commit leaves both common and instance data unchanged. Common-only saves may have an empty instance list and empty changes list. The current software-operation guard and initial registration scan still apply.

Common reads, saves and native path selection use only the local pywebview manager bridge. They are not exposed as Flask, Bottle or WebSocket configuration routes; the manager's HTTP application continues to serve static assets only. Browser-accessible instance APIs retain their existing authentication boundaries. Instance SMTP credentials remain local configuration secrets; removing manager sharing does not isolate users who can access host files.
