# Base Infrastructure & Scheduling Subsystem Specification

Authoritative specification of the Base Infrastructure & Scheduling Subsystem, governing operator assignments, mood mechanics, dormitory allocation, shift transitions, and facility automation.

## Manual Queue Tasks

The task dialog admits a configured daily run, recruitment, Skland signing, credit shopping, mail collection, base reports, friend visits, daily and weekly rewards, the current stage plan, and each supported long task. A single selection runs once using its current parameters and selected runner without requiring its automatic-enable switch. The combined daily selection includes enabled daily work and stage plans, excludes long tasks, and retains its remaining steps across device recovery and dependency waits. Manual selections do not change saved automation settings.

The task category menu has one daily-work entry. Its second selector defaults to all configured daily work and offers each individual daily action. Stage plans and long tasks retain separate category entries. The daily sub-selection determines the queued task type; switching to another category ignores it, and clearing the form restores the combined daily selection.

Manual tasks carry no room arrangement or caller-supplied metadata. Adding one requires the existing Web UI token and wakes the scheduler. Execution requires a five-minute margin before the next dispatchable task, excluding the current manual task. MAA daily work yields at that margin, MAA long work yields thirty seconds before the next task, and local stage work uses its existing operation deadline. Each manual dispatch also has a fixed twenty-four-hour execution limit when no earlier task exists. Dependency waits retain the original task, timestamp and remaining steps; unchanged dispatch and elapsed time do not release a wait. Completion or rearrangement of the blocking task, or a configuration change, permits reconsideration without a polling task. Manual MAA execution returns to the queue without entering the automatic idle-sleep path or starting another configured long task.

[`manual_tasks.py`](../../arknights_mower/solvers/manual_tasks.py) owns selection and remaining steps; [`manual_task_tests.py`](../../arknights_mower/tests/manual_task_tests.py) verifies queue dispatch, authentication, runner selection and unchanged-dependency retention offline. Existing scheduling and configuration concepts retain their meanings.

## Manual Maintenance Windows

The task dialog also admits flash updates and server downtime with a selected start and an integer duration, defaulting to ten minutes. Flash updates allow 1–10080 minutes and offer preparation followed by pause, or direct pause. Preparation reuses the existing maintenance Drone Acceleration and mastery support handoff scheduling. Direct pause does not advance either operation for that window. Server downtime allows 0–10080 minutes: a positive duration schedules a later start, while zero closes the Mower process without a scheduled start. Server downtime uses preparation and supplies the existing major-maintenance condition, so applicable maintenance backups activate before stopping at their own lead times; creating a task does not force an immediate backup transition.

The queue owns these windows and preserves their start, duration and mode through saved-state recovery and software-update replanning. Adding a window requires the existing Web UI token, clears caller-supplied room arrangements and metadata, and wakes maintenance evaluation. A zero-duration server task also requires the instance's existing process-control permission when manager-owned settings are hidden. Manual flash updates pause dispatch until their exact end, with no announced flash probe or half-hour early login. At the selected start, manual server downtime first checks the applicable maintenance backup through the existing selection and preparation flow. It waits for queued advance runs, original-roster restoration and actual backup arrangement tasks to finish before saving the task state and stopping the automation worker. The stop task keeps its original timestamp while preparation is pending, remains active beyond its nominal end, and is excluded from dispatch so its own prerequisites can execute. A retained preparation failure keeps the stop pending while unrelated tasks remain dispatchable; elapsed time alone does not authorize a retry or shutdown. After device cleanup, a positive-duration task reuses the server's scheduled-start timer to continue the saved queue at the selected start plus duration. The stopped state and countdown appear through the existing status and scheduled-start controls. Cancelling the reservation prevents automatic startup; an explicit stop during the handoff also cancels it. Timers remain process-local, so closing the application cancels the reservation. A zero-duration task is consumed before saving the remaining queue and requests the existing process shutdown lifecycle, without creating a timer. The desktop launcher exits through that lifecycle; an external WSGI host remains responsible for terminating its hosting process. If saving the task state fails, the worker stops without closing the process or scheduling a restart and reports that manual recovery is required.

Startup during manual server downtime returns to the stopped state before OCR or device initialization: a positive duration schedules only the remaining time, and zero requests process shutdown. This startup boundary does not log in to perform a fresh backup arrangement during downtime; backup preparation must complete while the scheduler is running before it stops. A flash wait yields at an overlapping manual server downtime's start instead of delaying the stop until the flash ends. Official announcements retain their existing handling, including the client-update stop. A nearer manual flash does not hide a later major update's preparation threshold or its scheduled wakeup. Expired manual windows leave the queue without deleting other pending tasks. These are operational additions to existing scheduling concepts; glossary definitions remain unchanged.

[`scheduled_start_tests.py`](../../arknights_mower/tests/scheduled_start_tests.py) verifies stopped status, countdown, saved-queue startup and cancellation. ## 2. Core Concepts & Functional Contracts

### 2.1 Scheduling Plan (`Scheduling Plan`)

The shared roster precheck checks training-slot eligibility in main and backup assignments, every binding replacement, and explicit backup staffing tasks. The [training-slot validation decision](../../.agents/notes/implemented/bug-fix/2026-10-09-training-slot-validation.md) defines cache, synchronization and exemption behavior. The [inventory synchronization contract](growth-planning.md#inventory-synchronization-and-mastery-payments) owns material calibration and refresh entry points.
Income snapshot validation uses the same native checker with detached configuration and roster-mode exceptions defined in [Income Image Export](plan-editor.md#income-export). Manual saved-plan and startup validation retain their existing roster refresh policy.

- Running-plan restoration restores the baseline, backups and advanced settings captured at scheduler startup. The advanced-settings snapshot comes from the actual global configuration rather than editable plan metadata. The endpoint preserves unrelated global settings, rejects missing or invalid snapshots before writing, and compensates either file-write failure with the original models and file bytes. The frontend pauses and drains autosave, reloads configuration and plan after success, and keeps autosave paused until a page refresh if either read fails. The [restore-cohesion decision](../../.agents/notes/implemented/simplification/2026-10-06-running-plan-restore-cohesion.md) records the regression coverage.
- Manual and startup validation check the baseline once, then check each distinct effective schedule from possible backup activation combinations with `Operators.init_and_validate`, the same merged-plan checker used by runtime `Operators.swap_plan(..., refresh=True)`. Successful results are reused only within that validation call, keyed by ordered facilities and slots, all bindings, products, every merged configuration field and maintenance primary slots. Checks retain declaration-order overrides and whole-slot `Current` inheritance, including replacements. Independent operator models preserve actual occupancy and active conditions; failures identify the active backups. Reported counts include baseline validation and distinct merged-schedule checks. The manual endpoint delegates baseline validation to this checker, and the UI permits only one in-flight manual request. The [validation reuse decision](../../.agents/notes/implemented/simplification/2026-10-11-zero-mood-validation-reuse.md) defines verification.
- Static trigger analysis shares known operator working/resting states, room string comparisons, same-room facility-product comparisons and clue-party null checks through supported Boolean logic. Unsupported, missing, time-dependent and state-mutating conditions retain independent activation choices. The validator excludes only logically impossible combinations, admits at most 16384 distinct activation combinations and analyzes at most 262144 symbolic states. Results distinguish `passed`, `failed` and `incomplete`; only `passed` has `success: true`. Startup condition analysis and combination checks share a five-second monotonic deadline after ownership and baseline validation. Manual validation has no elapsed-time limit. Checkpoints stop after the current synchronous parse, sort or merged-plan check; ownership synchronization and baseline validation remain outside the time budget. The [startup deadline decision](../../.agents/notes/implemented/feature/2026-10-06-backup-validation-deadline.md) defines verification. Exceeding any budget returns `incomplete`: manual validation displays a warning and startup logs the warning and continues. Ownership and baseline errors, confirmed merged-plan conflicts and unexpected validation exceptions remain blocking. Runtime checks still validate active combinations before changing operators. The [budget warning decision](../../.agents/notes/implemented/feature/2026-10-02-backup-validation-warning.md) defines these caller contracts. There is no fixed backup-count limit: 14 independent conditions fit the combination budget, and shared or mutually exclusive conditions permit more backups. Static validation does not prove future dynamic convergence. The [validation decision](../../.agents/notes/implemented/bug-fix/2026-10-02-backup-validation-coverage.md) records the regression.
- Configures assigned primary operators, operator groups, replacements, products, and resting rules across all base facilities. Working primaries configured in `workaholic` may omit ordinary replacements when ungrouped or when every member of that binding is configured for zero-mood work. Entirely zero-mood working groups require no bed capacity or replacement for an omitted candidate list; supplied ordinary candidate lists retain unique matching; mixed groups require replacements for every member. Multiple bindings are checked independently, including shared followers. Supplied replacement names, dormitory group constraints and Fiammetta charging targets retain their validation rules; a measured mood of zero alone grants no exemption.
- Working-cover admission exempts names in the effective merged `workaholic` configuration from personal mood-floor rejection and exhaustion-based priority demotion. It also admits a slot's only configured ordinary cover at its mood floor. The ordinary set excludes `Free` and trade order agents and, for shared primaries, intersects all resting bindings before counting candidates. Occupied or reserved alternatives remain part of the configured set; filtering a multiple-candidate list down to one available name grants no sole-cover exemption. Ordinary shifts, exhausted-shift coordination, correction, backup transitions and rescue handoff use the same admission rule. Occupancy, reservations, unique matching, mastery protection, full-recovery locks and shared-binding compatibility remain binding; crafting and mastery retain their specialized mood checks. The [zero-mood decision](../../.agents/notes/implemented/simplification/2026-10-11-zero-mood-validation-reuse.md) records rationale and verification.
- Manages the baseline master plan (`plan1`) and condition-triggered backup plans (`backup_plans`).
- Condition triggers monitor facility state, clue party status (`party_time`), and operator exhaustion. After backup conditions converge, ordinary planning reuses an existing dispatchable default-state empty task due no later than the requested wake, excluding the current task; specialized tasks and later deadlines remain unchanged, and physical arrangement completion retains its planning responsibility.
- Optional automatic rescue evaluates initialization observations against individual rescue lines and shared native rotation projection. Unknown observations and incomplete projections do not establish recovery blockage. Cached startup still checks actual staffing before planning temporary assignments.
- Each automatic rescue episode persists unfinished local staffing, uses an independently configured rescue schedule for ordinary working facilities, and freezes normal backup transitions and ordinary working shifts. Fiammetta, crafting and mastery retain specialized temporary swaps; explicit rescue trade order agents stay reserved for normally eligible order runs without suppressing ordinary order and product collection during ordinary observations or dormitory rotation. Collection shares existing scheduler and dormitory-rotation wakeups and retains the ordinary collection cooldown.
- Every automatic rescue tick reconciles personal mood-limit release deadlines through the existing strict-release planner, reusing unchanged tasks and their reserved operation starts, after due room observations and before bed reservations; ordinary working shifts remain frozen. Automatic rescue retains configured operator identities and personal limits while manager positions provide episode-local recovery capacity, including the configured Fiammetta position when primaries await beds. Pending strict releases reserve their occupants and original beds; completed personal-limit recovery outside dormitory retention cannot re-enter emergency beds or manager positions. Completion markers and predicted mood do not establish measured rescue targets. Strict releases read departing mood before selection even when idle recovery is disabled. Predicted idle targets lose only their unverified timestamp and release marker so bed planning can obtain a real reading. Trade order and Fiammetta compensation preserves explicit vacant slots from observed temporary staffing, while `Free` remains a filling request. The [specialized boundary decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-specialized-boundaries.md) and [measured-handoff decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-measured-handoff.md) define verification.
- Correction, backup transitions and handoff suppress completed personal-limit residents outside dormitory retention from vacant dormitory positions while applying the rescue bed priority to Fiammetta and preserving unfinished recovery primaries during manager restoration. Started trade order retries retain compensation snapshots and original-worker reservations; occupied workers remain at their other working facilities until release. Staffing arrangements preserve unfinished group positions and yield before strict release operation windows; failed handoff reopens beds and restores deadlines only for matching actual occupants. The [rescue admission and dispatch decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-admission-dispatch.md) defines regression coverage.
- History-derived targets use compatible measured segments and native recovery opportunities. Insufficient history uses the normal shift-off threshold. Eligible normal standby operators instead use their personal rescue thresholds; full-recovery requirements retain personal mood caps. Actual observations confirm each primary's recovery target and permit reserved standby; automatic rescue restores ready groups at final handoff when complete normal replacements and available beds from the normal schedule cover unfinished resting groups; manager positions temporarily opened by rescue do not increase normal bed capacity. Handoff and final readback verify current coverage without forecasting the next rotation; unknown recovery times or depletion rates do not independently block exit. Restarts reconcile actual staffing and retain only unfinished arrangements.
- Automatic rescue room readback invalidates measured mood timestamps for unexpectedly absent occupants. During an explicit recovery-target release, complete readback matching the final dormitory arrangement preserves the departing member's measured mood and timestamp only when that member is absent and the measured target is met; standby stops the former recovery-rate projection. Partial or mismatched readback, unknown mood and predicted mood do not establish completion. The handoff arrangement uses a dedicated ordinary `SchedulerTask`; its `finally` boundary restores the prior task before room readback and final scheduling, including after deferral and errors. The [observation and handoff decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-observation-handoff.md) records the original absence-invalidation and task-context rationale.
- Automatic rescue opens configured manager positions as recovery capacity, including the configured Fiammetta position when primaries await beds, and uses shared dormitory recovery priorities. As recovery demand falls, each dormitory restores one group-recovery manager, followed by one single-target manager if beds remain, without displacing unfinished recovery primaries. Collection and room reads use the strict-release operation allowance and persist unread rooms before yielding. Final readback confirms native feasibility and pending specialized restoration before exit. The [handoff fill cancellation decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-handoff-fill-cancellation.md) defines removal of obsolete episode filling before return. The [startup progress lifecycle decision](../../.agents/notes/implemented/bug-fix/2026-10-02-rescue-startup-progress-lifecycle.md) defines disabled-setting continuation and completed-snapshot invalidation. The [startup release window decision](../../.agents/notes/implemented/bug-fix/2026-10-02-rescue-startup-release-windows.md) defines initialization progress without a rescue episode. The [measured release and compensation decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-measured-release-compensation.md) defines room-level replanning and expired-order restoration. The [rescue observation budget decision](../../.agents/notes/implemented/bug-fix/2026-10-02-emergency-observation-budget.md) defines regression coverage.
- Automatic rescue freezes the normal schedule and applies the effective rescue roster to all ordinary workstations before planning dormitory filling. Rescue backups use the shared condition evaluator at entry and overlay the rescue main plan in configured order. Their `Current` slots inherit the preceding rescue roster. Missing rooms, duplicate workers and incorrect slot counts defer entry with a concrete configuration warning. Primaries explicitly assigned to rescue work receive a startup overlap warning and stay outside the episode recovery targets. Partial arrangements resume only outstanding rooms. Measured-ready recovery primaries leave dormitories into reserved standby until final restoration.
- The [configured rescue schedule decision](../../.agents/notes/implemented/simplification/2026-10-04-configured-rescue-schedule.md) defines limits, observation cadence, and handoff.
- The maintenance condition edits as one row with an advance-hour value, defaulting to 0.5 hours. Existing `op_data.major_maintenance_remaining_hours() <= hours` conditions retain their saved thresholds, including nested combinations. The scheduler queues one threshold check. The condition is false at and after announced downtime start, including while the announcement remains cached; unknown maintenance and flash updates also do not activate it. Major downtime saves state and stops the automation thread. After the client update and task restart, the first normal backup check exits the maintenance backup; no exit shift runs during downtime.
- Entry with effective trade order primaries first runs any other trade order agents in those primaries' effective replacement lists, once per affected trading post, using Drone Acceleration. These immediate adjusted RUN_ORDER tasks use the final merged slots even when the previous schedule has no order task for that room; Orundum trading posts remain excluded. The batch preserves pending tasks and original-roster restoration through repeated checks and queue recovery, suppresses new ordinary orders, and finishes before maintenance primaries activate. Without such replacements, entry switches directly. Activation cancels ordinary RUN_ORDER and order-time refresh tasks across all trading posts, including previously advanced and future tasks. Existing original-roster restoration remains mandatory and unrelated tasks remain queued. Final active backup precedence applies: Current preserves maintenance-primary permission and replacements, while a later explicit assignment replaces them. Entry without effective trade order primaries reuses the existing pre-maintenance order window and Drone Acceleration, retains retry delays and completes roster restoration before switching; new order creation pauses during this batch, and other queued orders are not pulled into it.
- Room arrangement and confirmation use RUN_ORDER task identity for temporary trade-order staffing and countdown calibration. Adjusted orders retain the advanced deadline and confirm without ordinary order waiting before Drone Acceleration. Maintenance primary arrangements use ordinary staffing confirmation.
- An active backup containing this condition permits Proviso, Tequila, Pepe, and Closure in its explicit primary slots, with ordinary replacements still required. Any retained trade order primary pauses every trading post's order tasks and order-time refresh tasks. Later explicit overrides replace this permission; `Current` inherits it. Exit or removal of all such primaries resumes order creation. A maintenance backup without trade order primaries keeps normal order runs.
- Decision records: [Maintenance backup ordering](../../.agents/notes/implemented/feature/2026-09-30-maintenance-backup-ordering.md) and [Maintenance cutoff and condition evaluation](../../.agents/notes/implemented/bug-fix/2026-09-30-maintenance-cutoff-condition-evaluation.md).

### Backup product and replacement transitions

When a slot retains its primary, facility type and ordered group bindings, product or replacement-list changes prefer to preserve its primary's shift state, recovery bed and deadline. Working primaries remain at their slots; unobserved slots retain initialization correction. Matching maximizes available covers across affected slots before recalling eligible primaries early for the remaining shortages. Current valid covers have priority. Cover selection and recalls respect mastery protection, task and product reservations, occupied recovery beds and unrelated working assignments. Ordinary return tasks are derived schedules and are rebuilt after a recall; locked product shifts remain protected. Infeasible arrangements defer the transition and retain active backup conditions and queued staffing tasks. Product observation and switching retain their existing execution boundary. Binding changes outside the off-duty admission rule below retain their existing behavior; explicit entry staffing tasks retain precedence. Same-primary relocations between ordinary workstations of the same facility type preserve resting primaries through cover matching; working primaries move to their new posts. Exit restoration uses covers instead of forcing resting primaries to work, including unchanged slots touched only by a deactivated staffing task. Dormitory group slots follow the group state; primaries without recovery retain task-exit restoration. Required dorm layout changes retain recovery ownership and require fresh deadlines for moved residents; normal dorm priority handling remains active after the transition. The [relocation decision](../../.agents/notes/implemented/simplification/2026-10-06-backup-relocation-rest-state.md) records regression coverage. Normal backup checks and full shift projections share this rule. The [product rest state decision](../../.agents/notes/implemented/simplification/2026-10-06-backup-product-rest-state.md) records verification; the [replacement transition decision](../../.agents/notes/implemented/simplification/2026-10-06-backup-replacement-state.md) defines the shared transition boundary.

An off-duty ordinary working primary newly assigned to an already resting group follows that group's rest state when it was absent from the previous effective roster or belonged to another group. Restoring its primary identity and arranging off-shift recovery converge in the same final arrangement, with the matched cover at the workstation. Backup transitions first match the slot's available covers. A member without a recovery bed needs a complete ordinary recovery arrangement unless its timestamped mood already reaches its personal upper limit while idle. Existing recovering members retain their beds; new admissions respect task and product reservations and training protection. Infeasible recovery preserves active conditions and queued tasks. Explicit entry staffing tasks retain precedence, and unavailable covers retain the constrained recall rules. Both ordinary backup checks and complete shift projections apply this rule.

### 2.1.1 Multiple Group Bindings

`Plans.group` and `Plans.replacement` retain the first column. `Plans.group_bindings` stores additional `{group, replacement}` columns and defaults to an empty list. Each operator owns one facility slot. Startup and manual validation require distinct group names, allowing one empty binding, and replacements for every binding under the existing zero-mood exemptions. Existing primary/replacement identity checks apply to every column.

A working shared primary with an empty binding can take individual shifts using that column's replacements and its own mood thresholds. Named resting bindings take precedence: their replacement lists intersect without the empty column, and individual returns cannot replace their covers. Group departures preserve an existing recovery bed and its individual return window instead of allocating a second bed. Once the final named group returns, a still-recovering primary uses its empty-column cover until its individual return; an idle primary can return normally. Empty bindings do not create a group state or make the shared primary a named group's shift anchor. Existing recovery tiers, standby admission and bed takeover, exhaustion, full-recovery and zero-mood settings remain binding. A standby shared primary can lose its bed to a higher-priority primary without recalling its named groups. Ordinary occupancy changes still refresh observed recovery deadlines. Configurations without an empty column retain group-following behavior. [Focused offline tests](../../arknights_mower/tests/multi_group_individual_rest_tests.py) cover individual shifts, named-cover precedence, preserved recovery, execution preparation and standby displacement.

`Operators.init_and_validate` requires at least one member accepted by `is_group_shift_anchor` in groups containing a non-workaholic working member, across primary and additional bindings and every effective backup combination. A qualifying member is a fixed working primary, neither a dormitory primary, a zero-mood worker, a shared primary nor an eligible standby. Groups whose working members all work at zero mood may validate without an anchor and still require complete replacement matching; dormitory-only groups remain invalid. Groups requiring an anchor fail without one even with sufficient beds. Exhausted-shift and full-recovery requirements retain their existing precedence over standby eligibility; ungrouped standby remains supported. The [protected-bed decision](../../.agents/notes/implemented/bug-fix/2026-10-09-protected-dorm-bed-tiers.md#group-validation-boundary) records the rationale and regressions.

Manual validation waits for pending Vue updates and successfully saves the current Scheduling Plan through its serialized save queue before requesting server validation. A save failure reports an error and stops that validation request. This applies to both normal and rescue Scheduling Plan pages.

Schedule membership and role queries collect the ordered union of all binding replacements. Ownership validation, mastery exclusions, workshop recommendations, resting priority, normal staffing identity during rescue, and trade order detection use that union within their existing table and facility scope. Mastery retains the training-room exception; workshop recommendations retain dormitory and workshop exceptions. Runtime group replacement matching retains its per-group lists and common-candidate intersection. The [complete membership decision](../../.agents/notes/implemented/bug-fix/2026-10-07-plan-binding-membership.md) records the consumer audit and verification.

Each group has an independent confirmed on/off-shift state. A group changes state after its arrangement targets are confirmed; planning, failed selection and skipped rooms leave that transition pending. Pending transitions and expected targets survive task serialization. Legacy runtime snapshots infer initial state from ordinary single-group anchors; followers, workaholics and fixed dormitory residents do not supply group state.

Before a state-changing ordinary work arrangement executes, the common group preparation boundary completes its single-binding member targets. Returns restore their fixed slots; incomplete departures use the existing replacement matching and bed planner on an isolated occupancy projection, preserving already named destinations. Both full convergence and fast paths use this boundary. Explicit backup staffing, standby membership and training protection retain their existing rules. A training-only adjustment does not expand into other facilities. A configured cover already at its exact target qualifies for ordinary matching; a cover at another occupied slot remains unavailable. Individual slot correction does not establish a group return or suppress the group's low-mood departure. A genuine group return retains same-cycle departure protection. The [explicit group-state decision](../../.agents/notes/implemented/simplification/2026-10-07-explicit-group-shifts.md) records the repair and focused evidence.

An unconfirmed started shift blocks arrangements sharing its group, affected shared-primary slot, named target slot or involved occupant. Other groups continue; different shared slots do not create dependencies through a third group. Conflicts enter the existing suspended queue with references to their predecessors, preserving the task and its timestamp. Confirmation releases them immediately after target revalidation, without a one-minute timer. Failed predecessors keep their dependents suspended. Task serialization preserves these references together with expected targets; removed predecessors require fresh target validation before admission. Independent started shifts contribute their pending group transitions together to occupancy and recovery correction. Incompatible shared replacements still wait for the blocking groups to return and complete matching to succeed. Shared replacement matching, return-task generation and predecessor checks receive the same protected-training exclusions as ordinary arrangements. Protected shared primaries neither request covers nor create cross-group dependencies; remaining ordinary targets retain their original time and confirmation requirements.

After cache-free occupancy observation, dormitory correction checks every resting binding of a shared primary, including explicit pending correction returns. The active binding column does not decide whether its fixed dormitory slot requires a replacement. Same-group working-primary replacements qualify through the dependent binding, while common-candidate matching, unavailable-candidate checks and final-dependent-group return remain binding. Correction does not commit group state or change Actual Occupancy. The [cold dormitory correction decision](../../.agents/notes/implemented/bug-fix/2026-10-11-cold-dorm-binding-correction.md) records the regression evidence.

Execution preparation applies legal dynamic-recovery cancellation and facility protection to both the remaining arrangement and its pending named confirmation targets. This synchronization runs again when live facility observations change protection. Reaching a personal mood cap or becoming excluded cancels the matching dynamic recovery target before dormitory selection; legal bed compaction relocates surviving targets with their named occupants. ### Group Recovery Completion

#### Working Replacement Checks

#### 2.5.2 Trade Order Countdown Admission

`get_run_order_time` accepts an order-page marker after opening the page, including pages without an acceleration button. A valid digit-template countdown returns the run time with the configured delay deducted; a measured zero remains valid. Only a failed countdown read invokes OCR to check for confirmed order acquisition pause. An unconfirmed failure raises `RecognizeError` instead of supplying the current time.

A confirmed pause returns `None` after navigating back to room details and reading Actual Occupancy and Operator Mood, clearing cached occupants absent from that observation. `plan_run_order` creates no order task from this result. Confirmed vacancies retain the room's existing refresh task, or create one missing refresh responsibility, with its original object and timestamp under [Runtime Task Failure](#211-runtime-task-failure). This empty-plan refresh reserves no operator or staffing slot and yields to ordinary correction and other work. Actual occupants, the effective staffing plan, facility type, product or run-order eligibility must change before another order read; elapsed time, repeated observations of the same vacancy and observation-counter or timestamp changes alone do not reopen it. Persistence retains this dependency. Losing run-order eligibility ends the waiting read responsibility. A fully staffed paused room retains ordinary planning without a vacancy correction. Ordinary correction retains existing replacements, projection and task priority boundaries under [Shift Transition Compensation](base-scheduler.md#shift-transition-compensation) and [Complete Shift Projection](base-scheduler.md#complete-shift-projection).

Once per scheduler startup, after saved state is restored, eligible run-order trade rooms are checked before ordinary initialization and rescue staffing when there is no `RUN_ORDER` task. Pending maintenance entry or a maintenance-replacement run skips this check. Each visited room supplies strict readings of Actual Occupancy and Operator Mood, followed by its order countdown in the same visit. Multiple rooms' countdowns may be compared in a temporary task set and separated with the existing Drone Acceleration adjustment. Only orders whose adjusted execution time is already due or falls within the next `max(10, 2 × run_order_delay)` minutes enter the real queue as `RUN_ORDER` tasks. Other countdowns are discarded after the check; distant, paused or unreadable startup observations create no `REFRESH_TIME` task. An existing failed refresh retains its failure handling. Recoverable observation failures return to the infrastructure page and allow initialization to continue; device recovery and exit exceptions propagate. Executable critical operations starting within one minute take precedence over further startup reads or Drone Acceleration adjustments.

The subsequent initialization reuses only trade-room mood observations actually obtained during this startup check, while their observed occupant positions and mood-sample timestamps remain unchanged. It continues to observe all other required rooms. Initial selection-page estimates do not overwrite those actual room readings. This reuse is limited to the current startup and does not treat a recent reading from a previous run as a completed initialization observation.

Ordinary arrangements perform no countdown read or refresh-task creation after individual rooms. After the entire arrangement succeeds, they request missing order reads once and read countdowns using the completed staffing, prioritizing the last staffed room. Existing order predictions retain their configured refresh-operator rules. A critical task whose operation starts within one minute takes precedence over each final read; unread refreshes remain queued. A confirmed pause retains the existing admission behavior. A failed final read retains its independent refresh object, timestamp and failure dependency, and returns to the infrastructure page without repeating completed staffing. Run-order insertion, Fiammetta exchanges and original-roster restoration retain their existing executor.

Before the next room, ordinary arrangements compare its estimated operation time and the existing admission margin with executable run-order deadlines, enabled mastery handoffs and reserved strict personal mood-limit release starts: fifteen seconds for work rooms and one minute for dormitories. Pending original-roster restoration is compensation rather than a new run-order deadline, even when its saved task retains room metadata; it does not trigger this yield or interrupt final refresh reads. Work that exactly fits its work-room budget may continue; using the complete dormitory margin yields, matching ordinary queue admission. An arrangement that cannot finish that room in time yields with the same task object, original timestamp, remaining rooms and transition metadata. Dispatch executes the critical task before resuming the retained arrangement; completed rooms are not reconstructed or repeated. This introduces no retry timer. Configured refresh-operator movements invalidate affected unstarted ordinary order predictions, including already-due predictions, and request another countdown observation. Active insertions, retained execution, original-roster compensation and maintenance-specific batches remain protected.

#### Credit Shop Value Settings

`credit_shop_by_value` defaults to false. The UI offers three decimal places beside the on-demand credit option. With Mower shopping selected but Mower friend visits disabled, both checkboxes remain visible and disabled with an explanatory tooltip.

When value shopping is selected and both Mower runners are enabled, the threshold becomes editable and the existing credit-overflow radio group becomes disabled. Priority purchases and the blacklist remain editable. Disabling the option or selecting another runner restores the overflow controls without overwriting any saved selections.

The active value-shopping branch first selects the cheapest remaining priority card using the observed sale price, independently of the configured priority-list order, discount percentage and value threshold. Equal prices retain shop order. A priority selection takes precedence over the blacklist, as in the existing purchase flow. Each confirmed purchase is followed by another reading of the balance and unsold cards. Balance equal to price permits purchase. If the cheapest priority card is unaffordable, the shop run ends without buying ordinary or overflow goods.

After all priority cards are sold, ordinary purchases exclude the blacklist and use the current user's saved material valuation through `growth_value.price_catalog()`. Each shop run reads one catalog snapshot when first needed; the next run reads saved prices again. The selector matches the observed name, discount percentage and sale price against the 25 known pack specifications in [credit_shop.py](../../arknights_mower/utils/credit_shop.py). Pack metadata contains item IDs, base prices and quantities, without a separate copy of material values. Total sanity value is the saved unit value times the full pack quantity. Unknown or inconsistent specifications and missing or invalid values are logged and skipped; zero-value ordinary goods are excluded. Quantity recognition on the game image is not added.

Ordinary goods are ordered by total sanity value divided by observed sale price. The best remaining ratio must be strictly greater than the threshold; if that item is unaffordable, shopping ends without selecting a cheaper lower-ranked item. Once no raw ratio exceeds the threshold, a balance above 300 permits another selection using effective cost `max(sale price - (balance - 300), 0)`. A positive-value item with zero effective cost has infinite effective ratio. The highest effective ratio must still exceed the threshold. Each purchase pays the full sale price and triggers a new balance observation and ranking. Equal raw ratios retain shop order; equal effective ratios retain raw-ratio order. The blacklist remains excluded even when the saved legacy overflow option permits blacklisted purchases.

When both options apply, an unaffordable selection reports `credit_deficit` as the total sale price of remaining target goods minus the observed balance, bounded below by zero. Target goods include every priority card regardless of value or blacklist, plus non-priority, non-blacklisted cards whose raw ratio strictly exceeds the threshold. Each card counts once. The calculation reuses the shop run's valuation snapshot and excludes goods qualifying only through overflow adjustment. The existing on-demand caller uses this total to decide whether to wait for Clue Party income or collect board credit. After the previous-week phase, a newly sufficient future 210 reward defers the current-week phase; actual income must arrive before it can fund purchases. Unconfirmed purchase rejections cannot report a shortage or trigger board collection.

Without on-demand collection, value shopping only spends the observed shop balance and does not evaluate future Clue Party income or request board credit. Daily shop credit becomes spendable after collection and a fresh balance reading. Existing clue-workflow board collection outside shopping remains unchanged. Inactive value-shopping configurations retain the original purchase code and shortage calculation, including affordable-item fallback, shop-order traversal, balance comparison and overflow rules. [Priority shopping tests](../../arknights_mower/tests/credit_shop_priority_tests.py), [value-shopping tests](../../arknights_mower/tests/credit_shop_value_tests.py) and [on-demand value-shopping tests](../../arknights_mower/tests/credit_shop_on_demand_tests.py) exercise the real shop loop and scheduler shopping entry, saved valuation imports, target filtering, both board phases, Clue Party timing and configuration isolation with simulated screen observations.

### Stop After Round

The log toolbar's 本轮结束后停止 requests a stop at the next normal round-end boundary in `rest_until_next_task`. A round includes the current base operations and the subsequent enabled daily or MAA work until that boundary; it is not one row in the pending queue. The request does not interrupt active operations. Due work still prevents normal rest. An empty queue at this boundary also permits the requested stop. A request received during normal task-between rest stops within the existing one-second idle checks, before device wakeup or the next dispatch. Scheduling waits, announced maintenance waits and MAA-error waits do not fulfill it.

The request belongs to the current worker run, survives browser refresh and is exposed as `/status.stop_after_round`. It is not stored in `conf.yml`; cancellation, immediate Stop, worker exit and a new Start clear it. Process restart does not carry it to another run. PUT and DELETE `/stop-after-round` require the current instance token. PUT requires a live automation worker that is not stopping, closing or being replaced; performance tests cannot accept it. DELETE cancels only a pending request and is idempotent after exit. Cancellation and completion serialize; a stop already committed at the round boundary cannot be undone by cancellation.

Before committing the stop, the worker saves the current queue, operator state and round count, records stopped task-run intent and cancels automatic recovery through the existing [recovery boundary](process-recovery.md#dispatch-recovery). A failed snapshot keeps the request pending and reports failure through the existing execution path. The final notification says 本轮任务结束，已按要求停止 instead of promising another start; delivery failure does not resume work. The worker then leaves through ordinary device cleanup without joining itself. Immediate Stop remains available while waiting, including during recovery or long-running tasks. [Focused offline tests](../../arknights_mower/tests/round_stop_tests.py) cover admission, authentication, normal and unrelated waits, cancellation, cleanup state and SQLite snapshot restoration.
