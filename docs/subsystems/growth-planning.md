# Operator Growth Planning

## 1. Interfaces

The existing recommendation route lists owned operators of every rarity, including unpromoted and completed operators. Resource capabilities determine which level, promotion, basic-skill, mastery and module controls appear. Unsupported mastery and modules remain absent. Mastery-capable skills expose target-specific costs for levels one through three. Module targets include opening and upgrades to levels one, two or three, default to the available maximum, and retain already-opened modules with unfinished upgrades.

Each operator exposes `level_goals` entries containing `id`, `elite`, `level`, `label` and `summary`. One- and two-star operators have `level_max` at elite zero level 30. Three-star operators retain `elite1` at elite one level 1 as an internal basic-skill prerequisite and `level_max` at elite one level 55 as the visible full-growth target. Four- through six-star operators retain `elite2`, `elite2_module` and `elite2_max`, respectively elite two level 1, the module threshold 40/50/60 and maximum level 70/80/90. The level slider is the sole level-target control: one- through three-star operators show only unplanned and full-growth nodes; four- through six-star operators show unplanned and their three supported elite-two targets. Dragging changes a local draft, releasing saves it automatically, and node clicks or keyboard changes also save. There is no separate apply or full-growth button, and arbitrary level targets are absent. Clearing an explicit target never removes a minimum prerequisite required by a selected skill or module. Explicit level choices remain mutually exclusive, and the highest selected prerequisite is counted once.

Skill and module selections automatically show their minimum unsatisfied level prerequisite; a higher explicit target remains selected. The independent `skill7` goal permits supported basic-skill upgrades without a mastery plan; its resource-defined unlock requirement includes elite one level 1 when necessary and shares promotion costs with explicit goals. Level/promotion, basic skills one through seven, mastery and module upgrade costs render separately, while the aggregate budget still deduplicates prerequisites. Crafting fees appear independently from direct upgrade costs and enter the total LMD requirement once. EXP uses the warehouse EXP image. Modules display expanded. Planning can precede readiness, but mastery dispatch requires elite two and basic skill level seven. A terminal mastery stage never switches to a halving assistant for a later stage.

`/growth-plan` stores valid level, promotion, independent basic-skill and module selections. `/mastery-t3-summary` combines them with skill plans and counts promotion, level and basic-skill prerequisites once per operator. Confirmed paid training stages are excluded. Unknown prerequisite data returns a visible error. Module goals persist their selected target level and charge only unfinished stages.

`/mastery-plan/start` verifies the selected skill target against confirmed local finished-material stock; craftable ingredients do not satisfy immediate execution readiness. It requires elite two, basic skill level seven, enabled mastery automation, a running scheduler, and no conflicting scheduled operator or occupied mastery queue. It inserts one start task keyed by the database plan id and wakes the scheduler. Repeated requests for the same queued plan return its existing queue status. Other active training, pending mastery work or a different unfinished plan waiting for materials receives an explicit blocking reason. The executor still verifies the training room before starting. Only an observed inserted or existing queue task receives a success response; an active training plan, missing materials and unavailable execution remain distinct responses.

The locally authenticated `GET /growth-crafting-order` returns `planning_items`, `items`, `prepared_items` and `custom`. `planning_items` contains all selected skills and goals, including pure leveling, in the saved order. `items` is the crafting-only projection. Each planning row carries its stable key, operator identity, target label, status, lock flag and `crafting_required`; skill rows carry `plan_id` and goal rows carry `module_id` for existing removal APIs. Pure-level goals retain their actual target level and report that no crafting is required. `PUT` accepts `{order: [key, ...]}` containing every planning item exactly once and retaining the complete locked prefix. It saves the single `growth_crafting_order` list and assigns mastery priorities from its skill subsequence; duplicate database rows for the same skill share that priority. Validation or persistence failure preserves the previous order. General `/conf` writes cannot overwrite this order from older settings snapshots. `DELETE` restores skill-first ordering while preserving the current relative training priorities. User-requested mastery deletion checks active training protection inside the same database transaction as deletion; a plan that starts after the dialog was opened cannot be removed from that stale draft.

`GrowthCraftingOrder.vue` provides the sole “养成计划” entry and dialog. One avatar list supports mixed skill and goal dragging, search, profession arrangement, removal, cancellation and saving. Search disables dragging; locked training items cannot move, be crossed or be removed by bulk clearing. Dragging and removal edit a local draft; saving applies removals through existing APIs and then submits the remaining complete order. A partial save failure reports the completed mutations and reloads the actual server state while keeping the dialog open. Canceling writes nothing. Failed mastery plans and their failure reasons remain visible below the sortable list, can be removed through the same draft save, and do not enter the executable order. Plan changes refresh server state without reading Skland. The leading reminder is the sole display for materials-ready unfinished manual goals: those keys are excluded from the draggable list but remain in the full saved plan. Reordering the remaining rows preserves those hidden keys and their positions; the reminder supports draft removal and disappears after synchronization confirms completion. Pure-level reminders still reserve resources after crafting demand; their display position creates neither a recipe nor a higher leveling-resource reservation. The [unified plan decision](../../.agents/notes/implemented/simplification/2026-10-08-unified-growth-plan-order.md) defines the removal of duplicate editing surfaces.

## 2. Materials and Farming

Only the plan material overview starts collapsed. Level, basic-skill, mastery and module material details are displayed directly without a collapse control. Material headers retain readiness. The overview header remains present with no selected goals, so selecting the first goal does not insert a new block above the operator list. Expanding details is a local display choice and does not alter plans.

Workshop execution shares transient game-rejected recipe records across admission and worker handoff. Unchanged relevant stock and configuration keep a rejected recipe suspended; changed ingredients, output or crafting LMD, a new configuration generation, or a newer relevant inventory observation allow retries. Rereading an old warehouse snapshot does not release the suspension. Color checks never overwrite ingredient counts with zero. Worker mood and Nine-Colored Deer phase selection remain local restrictions, and processing exceptions stop consecutive handoffs and restore borrowed staff. See the [decision record](../../.agents/notes/implemented/bug-fix/2026-10-08-workshop-rejected-recipes.md).

Workshop execution reads persisted inventory without refreshing Skland; confirmed recipe deltas update it after each batch. The crafting projection of the unified plan contains one project per selected mastery skill, module, unfinished explicit promotion target or independent basic-skill target. A level goal contributes only its unfinished promotion portion; raising levels within the current elite phase adds no crafting project. Implicit prerequisites remain inside their owning project rather than appearing as separate queue rows. Its default order follows mastery plan priority before other goals. Arranging, training, waiting-collect and confirmed-training material-wait plans retain a fixed leading order. A saved custom order applies to all other projects; new projects append after its existing keys. Quick-added skills preserve this saved sequence before immediate dispatch; profession alternation applies only without a saved custom order. Saving this order also updates relative skill training priority; automatic material admission itself does not mutate plan priorities.

`growth_order.prepare_project_materials` admits projects against one cumulative budget in queue order, including direct LMD, crafting fees and protected stock. An unstarted project that cannot be fully supplied remains visible and sortable with a shortage reason, reserves no stock, and emits no partial recipes. Later projects can use the remaining stock. A protected training shortage pauses later preparation. Unfinished promotion or basic skills do not prevent material preparation when the complete material demand is supplied; the project reports that only materials are being prepared, and actual training retains its readiness checks.

Each admitted project first contributes its minimum unsatisfied promotion and basic-skill prerequisites, then its own remaining costs. Shared prerequisites count once across the operator's admitted projects. Crafting preparation stops a promotion target at level one of its destination elite phase. Module preparation includes promotion through elite two level one; the additional LMD and EXP for the module's level 40/50/60 threshold do not enter crafting admission or reservations. Actual module readiness still requires that full threshold, and the material overview retains its complete leveling costs. A separately selected maximum-level goal does not enlarge an earlier skill's minimum elite-two level-one prerequisite. The workshop request selects the next missing recipe of the earliest admitted project, bounds output by its shortage and affordable batches, and recalculates after each confirmed batch using local inventory. Preparation continues through later recipes, projects and available workers; a worker lacking mood for even one recipe batch does not enter the workshop. Output upper limits are current inventory plus the affordable outstanding quantity; lower limits remain reserved inventory thresholds. It adds no unrelated stockpiling or fodder. Nine-Colored Deer requires separate fodder and is excluded from missing-only allocation. New fodder groups reserve 20 units of each child material by default; existing explicit limits remain unchanged. A recipe change queues continuation with remaining mood; ordinary first-time dispatch retains its normal mood gate. Existing manual backup, generation and material protection contracts remain binding. Shared inventory retains confirmed crafting changes across delayed cloud requests: pending per-item baselines and change directions survive restart. For an item changed only by production, cloud counts at or above the predicted inventory can reconcile; for consumption alone, counts at or below the prediction can reconcile. An item both produced and consumed requires exact equality with predicted inventory, or a newer actual warehouse observation covering that item. Unknown directions from migrated records also require exact equality. A missing item in a partial scan is not an observed zero. HTTP request time alone is insufficient evidence of fresh stock.

Chips never become workshop recipes. Each missing dual chip adds two same-profession chip packs and one catalyst to the displayed manual requirements. Each missing catalyst adds ninety purchase certificates. Existing dual chips and catalysts reduce derived requirements before certificates are counted. These are final products and their manual ingredients, not independent additional uses. A missing dual chip is craftable when its same-profession chip packs are sufficient and existing catalysts plus whole catalysts exchangeable with certificates cover the shared catalyst requirement. This manual readiness changes neither owned counts nor immediate availability. The cumulative project budget reserves those ingredients and certificates once, including any direct demand for them.

`/growth-chip-farming` updates the active MAA weekly plan only: outstanding small-chip and chip-pack requirements bind the corresponding PR stage; purchase certificates bind AP-5. Target stock is total remaining need, not merely the shortage. Related old rules are replaced; unrelated limits, stage order and plan fields are preserved. Affected ratio members are removed so they cannot suppress required stages. Required stages follow annihilation and retain normal stage-availability handling.

## 3. Subsystem Invariants

- **[INV-WORKSHOP-01] Rejected Recipe Handoff**: Game-rejected recipes do not dispatch another worker against unchanged relevant inventory and configuration; rejections remain transient, renewed inventory observations permit retries without fabricated counts, and processing failures stop consecutive handoffs.

- **[INV-GROWTH-02] Public Survey Isolation**: Public survey retrieval sends no local identity or credentials, missing survey rates remain unknown, and survey display or filtering never mutates plans; a configured write-only token permits one fixed-endpoint upload of game identity and progression after each successful Skland refresh or an explicit manual sync, without exposing the credential or invalidating local refresh success on upload failure.

- **[INV-GROWTH-01] Shared Growth Budget**: Growth planning admits unready operators without dispatching training, counts shared prerequisites once, reserves stock in crafting-project order, emits only outstanding permitted recipes for fully supplied projects, and keeps manual chip conversion separate from automatic crafting.

- **[INV-GROWTH-03] Ordered Crafting Prerequisites**: The saved unified plan order determines crafting priority and relative skill training priority, active training remains fixed first, each admitted project prepares its minimum unsatisfied promotion and basic-skill prerequisites before its own costs without counting shared prerequisites twice, and an unstarted shortage skips that project while a protected training shortage blocks later preparation.

- **[INV-STOCK-01] Confirmed Workshop Inventory**: A later cloud request timestamp alone never replaces locally confirmed crafting changes. Pending outputs and consumed ingredients remain protected until single-direction cloud counts reach the predicted inventory in that direction, or a newer actual inventory read reconciles them. Items both produced and consumed require exact predicted cloud counts or a newer actual inventory read. Workshop upper and lower limits remain absolute inventory thresholds.

## 4. Local Operator Statistics

`personal_statistics` in the recommendation response aggregates the locally synchronized roster across all one- through six-star rarities. `OperatorStatistics.vue` starts collapsed and, when expanded, presents three tabs: operator statistics, material consumption and per-operator investment ranking. Rarity checkboxes apply to the local aggregates. Recruitment and elite-two counts merge forms sharing a `progression_owner`; shared level and basic-skill costs count once, while each form's distinct skills and modules count separately. Recruitment availability is the current resource catalog, including unowned operators, not historical pulls. Skill and module columns count the exact current level one, two or three. Each rarity includes `supports_mastery`, `supports_modules`, `max_phase` and `max_level_limit`; unavailable progression is displayed as not applicable. Full level uses the resource cap: elite zero level 30 for one/two stars, elite one level 55 for three stars and elite two 70/80/90 for four/five/six stars. The module-level threshold applies only to supported rarities and means elite two at least 40/50/60 for four/five/six stars.

Completed promotion, leveling, basic skills, mastery and module stages are valued with the pinned offline [Yituliu item-value snapshot](../../arknights_mower/data/growth_values.json). Its metadata records the source commit, retrieval date and [algorithm reference](https://ark.yituliu.cn/docs/item-value-algorithm). Observed progression reconstructs quantities, which are multiplied by published values without deducting warehouse stock or including unfinished plans. EXP uses the intermediate battle record value divided by 1000. The material tab exposes direct LMD and EXP consumption, module data blocks and volume-three skill-summary equivalents: volume one / 9 + volume two / 3 + volume three, excluding crafting byproducts. Direct LMD excludes inferred historical crafting fees. Equivalent natural-regeneration time uses 240 sanity per day. Searchable material details paginate; the investment ranking shows its leading entries and a collapsed complete list.

The valuation estimates standard material investment, not actual sanity spent, and cannot reconstruct historical promotion tickets or other discounts. Integrated-strategy progression does not consume ordinary warehouse materials. Unpriced materials and missing definitions remain visible as coverage limitations. Personal aggregation makes no remote requests.

Historical snapshots preserve actual synchronization timestamps and their original counting semantics, including separately counted operator forms. At most 3000 observations remain cached, and trends appear only with multiple observations. New snapshots cover every rarity. Older snapshots missing low-rarity counts or any metric remain absent rather than becoming zero; they cannot provide a fabricated low-rarity trend. Goal and history files participate in configuration backup.

## 5. Public Growth Survey

The locally authenticated `GET /growth-survey` retrieves public aggregates from the fixed `https://auth.yituliu.cn/open/ak-operator-statistics/result` endpoint. The outbound request has no local identity, token or account fields; its isolated HTTP session also excludes ambient credentials and cookies and rejects redirects. Connect and read timeouts are three and eight seconds. Validated operator identifiers, ownership/sample counts and elite/skill/module histograms are cached in `@app/tmp/yituliu_statistics.json` for twenty-four hours. The response contains `operators`, `fetched_at`, `stale`, `error` and `source_url`. Failed refreshes preserve the last valid snapshot with `stale: true`; no valid cache produces an empty list and unknown timestamp. Invalid responses never replace a valid cache.

`GrowthSurveyFilters.vue` replaces the former general filter surface with capsule-style segmented selectors for mastery three, module unlock, elite one and elite two, alongside local operator search and idle/busy filters. Each selector presents fixed percentage nodes from left to right: 90, 80, 70, 60, 50, 40, 30, 20, 10 and 0.325. Clicking a node selects its threshold; clicking it again clears the threshold. Arbitrary percentage entry and continuous sliders are absent. A rate divides the selected histogram ranks by surveyed owners of that operator, not all survey participants. Elite-one attainment includes elite two; module unlock includes levels one through three. Histograms with missing coverage or no owners yield unknown rates. Thresholds highlight qualifying skills, modules and promotion goals. The hide-completed option is enabled initially and after resetting filters. It hides an operator only when selected dimensions have complete known coverage and the corresponding local goals are all satisfied; missing samples remain visible. Default, recommendation-rate and descending-level ordering alter presentation only. Operator cards, saved plans, material budgets and execution actions retain their existing behavior.

The UI links the [Yituliu survey](https://ark.yituliu.cn/survey/operators) and [CC BY-NC 4.0 content license](https://creativecommons.org/licenses/by-nc/4.0/deed.zh), credits its data source, and describes the statistics as unofficial and not a strength ranking. Mower's implementation is independently written. Public retrieval does not depend on an upload token and never uploads local progression.

## 6. Authorized Progression Synchronization

`YituliuSyncSettings.vue` appears immediately below Skland accounts in Mower settings. A configured write-only token enables one upload after each actual successful Skland refresh. Saving the token and reading existing caches do not upload. A process-shared lock serializes the complete remote fetch, local persistence and upload sequence across concurrent refresh requests. After local cache and inventory writes finish, `cultivate.start` passes that exact refresh snapshot to `sync_after_cultivate`; the upload does not reread a potentially replaced cache. A delayed response from one refresh cannot overtake a later refresh and replace newer remote progression. An upload failure preserves local data and the successful Skland result. `/cultivate-fetch` reports the separate `yituliu_sync` result.

The locally authenticated `/growth-sync-token` supports `GET`, `PUT` and `DELETE`. The token resides only in `@app/config/yituliu_sync.json` with mode `0600`, outside the general configuration response. Status returns `configured`, `last_synced_at`, `last_synced_count`, `last_attempt_at` and `last_sync_error`, with no complete or partial token. Local settings and upload errors do not expose credentials or cached payloads in responses or logs. Deleting the token disables future uploads. Authenticated `POST /growth-sync` with `confirmed: true` performs the separate manual action against the current cache.

Uploads use only `POST https://backend.yituliu.cn/open-api/operator/upload`, with the raw write-only token in `Authorization`. The verified contract is the provider's [published OpenAPI document](https://backend.yituliu.cn/v3/api-docs). The payload contains game UID, nickname, channel/server identity and `operatorDataList` entries for ownership, level, elite phase, potential, rarity, basic-skill level, mastery and module levels. It excludes warehouse inventory, account passwords and Skland credentials. Explicit player binding is stored in the refresh snapshot; older caches without binding require a new successful Skland refresh before upload. Uploads reject redirects, have finite connect/read timeouts, and do not retry uncertain requests. The status records success or a readable failure independently of the refresh result.
