# Scheduling Plan Editor

## 1. Facility Display

`PlanEditor` displays office, training and recycling cards in the local `right_side_room_order`. Dragging any of these cards onto another swaps their positions. The default order is office, training, recycling; the legacy office/training switch migrates to the equivalent three-room order. Main, backup and rescue editors share this setting and retain their facility identities and assignments. The running-plan edit lock also prevents dragging. Recycling provides two operator rows.

## 2. Plan Transfer

The order lives in local configuration and controls backend map navigation. It is absent from Scheduling Plan exports and advanced settings. Importing or switching a Scheduling Plan preserves the local order. Dragging these cards changes neither staffing, backup conditions nor explicit tasks; users match the order to their game layout.

Image export splits the complete compressed Scheduling Plan into fourteen QR codes, with seven in each existing left-side row. The right-side facility cards remain unobstructed and ordinary editor captures retain their dimensions. Normal and rescue images preserve recycling staffing, backup plans, explicit tasks and group bindings; normal exports also retain their advanced settings. JSON export retains the same plan fields. Images smaller than the QR-code area receive enough canvas space to prevent clipping. Import scans only QR symbols, excluding other barcode types from the compressed payload. It accepts both fourteen-code images and legacy sixteen-code images, retrying incomplete scans within the existing scale limit before reporting invalid data.

## 3. Subsystem Invariants

- <a id="operator-replacement-coverage"></a>**Operator Replacement Coverage**: One-click replacement candidates and existing-target warnings include primary operators and replacements from every main and backup plan binding, without duplicate names or mutations during collection.

- <a id="backup-operator-list-removal"></a>**Backup Operator List Removal**: Active backups apply operator additions followed by per-field removals in backup order; deactivation rebuilds effective lists from the main Scheduling Plan and remaining active backups without mutating source lists, and legacy backups retain additive behavior.

- <a id="backup-facility-import-isolation"></a>**Backup Facility Import Isolation**: Importing a main-plan facility replaces only the selected backup facility with a deep copy of its type, product and operator bindings; subsequent edits preserve the source main plan, other facilities, backup conditions and explicit staffing tasks, and the edit lock prevents import.
- <a id="facility-display-order-isolation"></a>**Facility Display Order Isolation**: The local `right_side_room_order` permutes office, training and recycling positions for display and map navigation; dragging preserves every Scheduling Plan facility identity, assignment, condition and task, and the order remains absent from plan exports.

The [recycling and local layout decision](../../.agents/notes/implemented/feature/2026-10-08-recycle-station-selection.md) records shared rendering, legacy migration and verification.

Facility cards retain the [global update drop exclusion](software-update.md#2-global-update-drop).

## 4. Backup Operator Lists

Normal backup lists contain additions. `BackupPlanConf.removed_operators` maps the same operator-list field names to comma-separated removal lists. Each active backup adds entries, then removes named entries from the effective list. Later backups can re-add entries. Empty lists inherit earlier results, and removing every inherited entry produces an empty effective list. Unsupported removal fields fail schema validation. Main-plan lists remain direct selections. Backup controls divide each original selection area horizontally into 增 and 减 columns; row height and vertical spacing retain the existing form styles. Rescue plans retain their existing single-list controls.

The editor displays separate 增 and 减 selections for each backup operator option, including 宿舍保留干员 directly below the dormitory blacklist on the plan page. Import, export, autosave and operator replacement retain both lists. Refresh-trading removals match complete operator names, including entries with room qualifiers. Dormitory room order and mood limits retain their own override contracts.

The [operator-list decision](../../.agents/notes/implemented/feature/2026-10-06-backup-operator-list-removal.md) records the merge boundary and verification.

## 5. Operator Group Columns

The plus button beside an operator's group field adds an independent group/replacement column beneath the first column. The first row displays only the add button; subsequent rows display only the remove button and retain the other bindings when removed. Empty operators, `Free`, `Current` and Fiammetta cannot add bindings. Running-plan edit locks cover addition, deletion and every field. Facility clearing removes all bindings with the operator.

Every avatar uses one equal-width color segment per configured column in a 5-pixel bottom strip, with its neutral background preserved in the editor and exported images. Unfinished empty columns retain a transparent segment. The main plan and all backup plans share a color map, so selecting another table preserves the colors of identically named groups. Plan saving, import, export and facility movement retain nested bindings.

The one-click operator replacement source menu and existing-target warning use a shared collection of primary operators, first-column replacements and all `group_bindings[].replacement` entries across the main and backup plans. Collection deduplicates names without changing plan data. Selecting a source replaces its entries in every corresponding column while preserving group names and other operators.

The [replacement coverage decision](../../.agents/notes/implemented/bug-fix/2026-10-07-group-binding-replacement-candidates.md) records the regression verification.

The [scheduling contract](base-scheduler.md#211-multiple-group-bindings) defines persisted fields, validation and shift behavior. The [shared rendering decision](../../.agents/notes/implemented/simplification/2026-10-06-shared-group-shift-selection.md) records the simplification.

The [shared color decision](../../.agents/notes/implemented/simplification/2026-10-06-shared-plan-group-colors.md) defines color assignment and rendering.

## 6. Backup Facility Import

The backup facility toolbar copies the selected main-plan facility, including its type, product, primary operators and all group/replacement bindings. The copy replaces only that facility in the selected backup and shares no mutable rows or replacement lists with the main plan. Backup conditions, explicit staffing tasks, other facilities and other backups remain unchanged. The button is hidden on the main plan and disabled by the edit lock.

## 7. Income Image Export

The normal editor's green income button, alongside advanced settings below the schedule image, opens `PlanIncomeDialog` for a detached copy of the current complete plan and advanced settings. The original export menu retains its existing actions. Default simulation duration is three warmup days and twenty-eight measured days, totaling thirty-one days. The initial drone target comes from the user's current Mower drone setting when that facility exists in the captured plan; otherwise it starts disabled. Changing the target in this dialog affects only this simulation. Both windows are independently editable; warmup output and initial stock are excluded from measured income.

The dialog reads owned operators, elite phases and levels from Mower's shared Skland cache through the authenticated read-only `/riic/income-cache` endpoint. Manual roster input and an explicit maximum-development assumption remain available. Inventory can use cached quantities, with editable additions, or manual quantities. Missing quantities in an available, valid cached item list default to zero for every simulation resource and remain editable. Missing or malformed inventory caches remain unavailable; unavailable growth never becomes maximum development. Only simulation fields are returned, without account identities or credentials; opening the dialog performs no remote sync or cache write.

Starting a calculation automatically sends its captured plan and roster mode to the authenticated `/validate-plan` endpoint. Native main/backup combination validation uses detached plan and configuration models, including the captured advanced settings, without saving or replacing the live configuration. Maximum development and manual roster modes skip Skland ownership and training eligibility checks entirely. Cached roster mode checks existing local ownership and training data without refreshing it; a known missing operator blocks calculation. This roster choice does not bypass inventory requirements. The Worker starts only after successful validation and receives the same captured plan and parameters. Validation failure, an incomplete combination check or a request error prevents startup and brings the error into view; closing discards late responses. Combination analysis and its frontend request have no elapsed-time cutoff. The dialog identifies the validation phase and lets the user close it to stop waiting; this does not cancel server-side analysis. State and combination count limits remain enforced, and an incomplete result reports its cause without starting the Worker. Static single-backup warnings remain advisory and identify the affected backup and replacements before starting.

Simulation drone capacity is 250, including recovery and overflow; preserved legacy capacity fields do not override it. Finite inventory runs continuously through warmup and measurement, without outside income. Inventory-conditioned backups always use this ledger. Backup conditions support native `facility_product_count(product)` and `facility_product_type_count()` queries over distinct facilities, with actual observed products overriding the original main plan; product observation changes wake dependent conditions. Gold debt is enabled by default: order delivery can make gold negative, representing a modeled shortfall. Disabling debt blocks unfunded deliveries; all other materials remain constrained. The income table and image report gold as LMD equivalent: manufactured gold multiplied by 500 plus report-only premiums from Tequila and other special orders, using the source model's selected output mode. Delivered gold is not deducted from this income metric; ordinary deliveries alone contribute no gold equivalent. The premium remains a reporting quantity and never enters the physical inventory. This matches the gold valuation used by the weighted score, which remains unchanged. Actual consumption and initial, sample-opening and closing balances remain available in inventory details. Archived summaries use their saved manufacturing and premium quantities for the same display, without rerunning or changing their weighted score. LMD net change subtracts manufacturing costs from income within the measured window; potential-output mode records those costs without changing its unlimited ledger. Recycling contributes only daily and sample-total production counts, without random material identities, inventory inflows or material value.

In the income simulator, every working primary in the group configured for full rest must reach their personal recovery limit, including low-priority and shared primaries. Group recovery spread and its triggered full-recovery wait include only non-standby working primaries bound to this group alone. Resting standby operators, replacements and shared primaries do not trigger or extend this wait. Explicit full-rest requirements still apply to shared primaries. Explicit full-rest or exhaustion settings retain their existing precedence over standby eligibility. The default threshold is 75 minutes; saved explicit values remain unchanged. These requirements accumulate: completing all explicit full-rest requirements does not bypass an activated group wait. They survive completed members leaving their beds. Fixed dormitory managers and workaholics are excluded from the named group recovery requirement. Strict simulation recovery has no early-return allowance or extra-wait cap; the preserved extra-wait setting still applies to the native scheduler. Explicit backup staffing retains its override of automatic group return. Automatic return execution, including correction-driven recalls, rereads actual mood and recovery deadlines, rescheduling against observed recovery when necessary; unknown recovery retains the task until relevant observations or arrangements change. Temporary single-target ordering reads departures before removal and preserves confirmed full-mood observations after the intermediate roster is verified. Dormitory release also rereads members with mandatory full-recovery requirements before removing them; an expired timer cannot replace a measured personal recovery limit. Incomplete recovery uses the current measured deadline, while unknown recovery retains the original release task. Exhaustion-timer refresh preserves a measured full-recovery record while its owner remains idle; working and predicted mood observations still require the existing refresh.

Weights default to the shared Mower income algorithm, read again before each run. Choosing a named algorithm in the dialog saves its coefficients through `/report/recycling_settings`, preserving the current recycling efficiency; opening and calculating only read settings. Saved custom coefficients are supported. An independent per-run custom weight option is temporary. Reports identify the actual algorithm used, even after later parameter edits.

The Worker runs the fixed calculator dependency closure under `ui/src/riic/vendor/`, with source hashes and local patches recorded in `source.json`. The model assumes ideal order runs, saved facility levels with inference for unset rooms, initial mood 24 subject to personal limits and maximum dormitory ambience for the applied level. New simulations always assume no unfinished training plan: `op_data.facility_has_mastery_plan('train')` is false, and legacy training-state input cannot override it. Training progress and completion times are not simulated. Archived successful results retain their original assumptions. The fixed model is not automatically synchronized with native scheduler changes. Ordinary off-duty planning retains explicit admissions across the same round, so later groups cannot treat earlier groups' reserved temporary beds as empty Free positions and recall their primaries. Failed arrangement previews retain the original task, remaining plan and timestamp, following the [runtime task failure contract](base-scheduler.md#211-runtime-task-failure). They release dispatch and notification collection for other work. Completed or full-queue order observations do not create past-due completion wakes; collection and inventory dependencies remain owned by production. Retained failed tasks retry only after relevant measured observations or arrangements change; predicted mood and elapsed time alone do not release them. Unresolved failures at the end of the window make the calculation incomplete. A Fiammetta exchange whose actual participants are both full retains the charging task through the same failure mechanism, instead of repeating an ineffective exchange or polling on a fixed timer. This offline safeguard supplements the native selection rule. Fiammetta target priority excludes shared multi-group members from the single-group lowest-mood comparison, matching the native selector. During shared-group dorm admission, hypothetical group transitions determine the active binding and optional standby eligibility. The planner restores confirmed group states and bindings after the attempt; successful bed reservations remain available to that planning round. The log tab shows current tasks, operator observations and reported constraints during calculation. Historical slow observations remain visible after completion, cancellation or failure; activity correlation does not establish a cause. Workers and pending reads are released on close; stale results cannot publish into another run.

Dorm recovery allocation follows the complete configured bed order, including explicit ordinary-bed entries before later single-target beds, and the eligibility and reservation boundaries of native [event-driven recovery allocation](base-scheduler.md#event-driven-recovery-allocation). The simulator adds a displacement rule: when an arrangement changes any movable single-target bed owner, all movable recovering residents are reassigned by recovery tier and then by deficit from their personal mood upper limits. A resident displaced from a fast bed must not fall behind an equal-tier resident with a smaller deficit merely because that resident already occupies a faster room. Equal deficits prefer actual residents, and selected residents retain positions within a same-speed group. Without a single-target ownership change, compatible same-tier residents keep their beds; mood changes alone do not move them. This displacement rule is a simulator extension and does not change the Python scheduler. Pending positional and named reservations, product beds and excluded occupants protect their rooms. Dorm isolation applies after recovery allocation. Configuration-only reallocation and crafting recovery ordering remain outside this selective synchronization. Single-target recovery keeps a valid confirmed recipient. Without one, it selects the lowest-morale eligible resident in the same dormitory; the provider is excluded when its skill excludes itself, and Fiammetta is always excluded. The automatic recipient stays selected until full recovery, departure or a provider/recipient position change; equal-morale candidates use slot order. These automatic choices do not move residents or create native confirmation markers. Explicit simulation target overrides retain precedence.

Exhausted-shift support retains its prerequisite role in the simulator task queue and task clones. Its preparation evaluates required backup actions without appending ordinary recovery or idle bed filling; ordinary shift and backup coalescing leave the support task intact. Once the prerequisite arrangement finishes, the exhausted shift recomputes replacements and beds from observed occupancy. This selective synchronization does not change production skills or establish complete native scheduling parity.

### Recruitment Refresh Production

The income observer integrates office contact progress over the simulator's actual occupancy intervals, using each operator's unlocked skills and current morale. An empty office produces no progress; an exhausted occupant contributes baseline progress without the 5% staffing bonus or workplace skills. The baseline is twelve hours per refresh. Current skill conditions include office recruitment slots, dormitory levels, elite-operator facilities and control-center providers. Completed refreshes during warmup are excluded while unfinished progress carries into sampling. The count assumes immediate use of generated refreshes and does not simulate stopping at the three-refresh storage limit, actual refresh clicks, recruitment outcomes or clue effects. It does not contribute to weighted income or resource inventories.

The result table reports daily and sample-total refresh counts. The JPG uses the office recognition template's symbol, cropped without its text and framed like the recycling badge; no refresh output means no badge. Header height expands when the product badges require another row, preserving the original schedule and QR geometry. Office and dormitory levels use the saved facility configuration described below, with inference for unset rooms.

The baseline and staffing conditions follow [PRTS's office description](https://prts.wiki/w/罗德岛基建/办公室) and [the pinned building data](https://github.com/Kengxxiao/ArknightsGameData/blob/17759cc8cdf37388414145d16262a3a06f3ab25e/zh_CN/gamedata/excel/building_data.json); skill descriptions and group identities use the bundled calculator catalog. The interval observer must not alter scheduling, mood, production or resource settlement.

### Reception clue production

The income observer counts clues completed by staffed reception rooms over actual simulation intervals. The report shows daily and sample-total counts; the exported image adds a reception badge in the upper-right daily-output grid, using clues as the unit. Old saved results without this observation omit the badge and require a new calculation for clue counts.

The calculation follows the [reception speed formula](https://prts.wiki/w/罗德岛基建/会客室#线索搜集速度): twenty base hours per clue, facility level, maximum dormitory ambience at the simulated levels, each occupant's rarity and supplied elite phase, and unlocked skills. Exhausted occupants retain passive rarity and promotion bonuses but lose the awake bonus and workplace skills. An empty or unbuilt reception room produces no progress. Conditional skills use the current facility assignments and morale; Ines's speed increase follows her continuous active reception tenure and stops at its cap. Warmup completions are excluded while partial progress carries into sampling.

The count assumes prompt collection, inventory clearance and continuously active clue exchange, including unlocked exchange speed skills of non-exhausted occupants. It excludes inventory-cap stoppages, daily free clues, gifts from friends, clue-type probabilities, set completion and exchange activation or expiry. This production assumption does not enable native clue tasks or change the scheduler's empty Party Time condition. Results record `clueExchangeMode: "always-on"`; older clue results without this marker retain the closed-exchange explanation and require recalculation to use the new assumption. It does not estimate credit rewards or affect weighted income, inventories, scheduling or resource settlement.

### Saved facility levels and power

The editor stores explicit building levels in the schedule's `facility_levels` mapping, shared by the main and backup plans. Selecting a facility exposes its level to the left of the facility-type control; default values are labeled. The power summary appears immediately to the right of the income button, wrapping with the action row on narrow screens. The rescue editor shows its own summary below the roster. Levels are integers from zero (unbuilt) to five for dormitories and the control center, or three for output and right-side facilities. Unset right-side facilities (reception, workshop, office, training and recycling) default to level three, including unstaffed rooms. Other unset rooms retain the existing inference rules; the UI does not claim that inferred levels came from the game. An unstaffed support building can have a saved level without adding a staffing assignment. Levels persist through automatic saves, JSON and image round trips. Removing a manual level restores the applicable default or inference. These settings describe buildings for estimation; they do not upgrade or downgrade buildings in the game.

The editor and simulator share the same power calculation. It counts built rooms even without staff, shows generation, consumption and remaining power, and reports deficits or staffing beyond level capacity without deleting assignments. Equal generation and consumption is valid. Invalid intermediate edits can still be saved; simulation rejects insufficient power, unbuilt staffed rooms and excess staffing. Backup overlays cannot raise or bypass an explicitly saved level, or introduce left-side positions absent from the main plan.

Simulation compiles the saved levels before evaluating production, office conditions and morale. Dormitories use maximum ambience for their level: levels one through five have 1000 through 5000 ambience and base recovery rates of 2, 2.5, 3, 3.5 and 4 mood points per hour, before applicable skills. Working mood consumption uses actual occupancy, control-center effects and unlocked skills, rather than an arbitrary per-level multiplier. The completed report describes the levels from its frozen schedule snapshot. The existing game-data [building table](https://github.com/Kengxxiao/ArknightsGameData/blob/17759cc8cdf37388414145d16262a3a06f3ab25e/zh_CN/gamedata/excel/building_data.json) supplies the power, capacity and dormitory constants: recycling consumes no power and the workshop consumes ten at each built level.
