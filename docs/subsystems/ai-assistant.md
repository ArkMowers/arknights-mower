# AI Assistant

The settings page exposes one DeepSeek provider (`ai_type=deepseek`). Its `ai_deepseek_model` field defaults to `deepseek-flash`, offers `deepseek-flash` and `deepseek-v4-pro` presets matching the [official model IDs](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/), and accepts a custom model ID. `build_llm` trims the ID, rejects a blank value and sends requests to `https://api.deepseek.com` with the DeepSeek key. The Pro preset retains its existing thinking parameters. Local and online custom providers keep their separate model, endpoint and key fields.

Configuration loading migrates the legacy provider selections `deepseek-v4-flash`, `deepseek-flash` and `deepseek-v4-pro` to the shared provider and corresponding model ID, preserving credentials and unrelated custom-provider settings. Loading adds no unselected default fields to explicit-field serialization. The frontend saves model edits as a partial configuration update without overwriting other provider fields.

### Custom Model API Protocol

`ai_api_protocol` applies to both local and online custom model services. Its values are `auto` (the default for existing configurations), `chat-completions` and `responses`. Loading an absent field does not persist a selection. The settings page saves explicit protocol edits independently of the model, endpoint and credentials; switching to DeepSeek retains the custom protocol setting without applying it to DeepSeek.

Automatic mode uses Responses for the normalized official online address `https://api.openai.com/v1`, and Chat Completions for other addresses. Only official Responses model-unavailable or protocol-incompatibility errors trigger one Chat Completions fallback; authentication, rate limits and unrelated errors do not. A successful fallback lasts for that model instance. Explicit selections use only the selected protocol, including on third-party and local endpoints, and propagate errors without switching protocols.

The shared `build_llm` entry applies this choice to assistant conversations, missed-order summaries, schedule-error analysis, captcha matching and navigation ranking. Responses tool calls retain their call IDs; calls without tools return string content for existing text consumers. Navigation passes the protocol into its isolated model worker and retains its existing deadline and cleanup rules. Responses requests omit the fixed temperature; DeepSeek retains its existing parameters.

## 1. Conversation Interface

`agent._build_messages` supplies one system instruction, user/assistant history and the current request. The instruction uses one local timezone-aware time snapshot. Stored chat uses the controlled tool loop; legacy `ask_llm` calls without an execution owner use the manual tool loop, preserving the model HTTP stream. Both use `get_tools()` and `tool_func_map`. The graph builder remains a compatibility helper and does not control either chat entry point. Tool progress messages describe the current operation in neutral Chinese.

The instruction includes the installed Mower version. Built-in FAQ entries describe current interfaces and retain local `sources` references for maintenance. Latin keyword matching ignores case. The standalone one-stop guide at `ui/Mower入门指北.html` is copied to `/docs/` by the existing UI packaging step. The help page renders the guide directly, with no additional link bar above it. The guide's feedback section, feedback modal and FAQ expose the user-supplied feedback sheet; opening that link does not submit a report, and editing requires permission. The [help content decision](../../.agents/notes/implemented/bug-fix/2026-10-09-alpha-help-content.md) records content scope and verification.

The standalone guide follows the system color preference unless a valid `theme=light` or `theme=dark` query selects an explicit theme. `Doc.vue` supplies the initial Mower theme, then sends the effective theme colors after iframe loading and on theme or palette changes using messages restricted to the same origin. The guide accepts only its parent's same-origin messages with valid theme values, applies an allowlist of CSS color tokens, and ignores invalid colors and unrelated properties. Theme-only messages clear prior color overrides and use the standalone defaults. Theme changes do not reload the iframe or reset its reading position. The page uses Mower's body and card backgrounds without a gradient; callouts share neutral control backgrounds and symmetric spacing. Scheduling tutorials explain current [base scheduling rules](base-scheduler.md) and [editor operations](plan-editor.md) through examples, including dormitory bindings, fixed and dynamic recovery positions, multiple bindings and backup inheritance.

`ask_llm` handles missed-order intent through its dedicated confirmation and target-selection flow before model dispatch. For requests reaching the model, instructions route general usage questions to FAQ and explicit record queries, missed-order analysis, mastery operations and feedback requests to their corresponding tools. FAQ matching supplies candidate advice rather than confirmed causes. Stack extraction requires existing stack text; source reading requires a valid path and positive line number and retains the [source allowlist boundary](web-access.md).

The system instruction requests concise Chinese Markdown, separates evidence from inference, treats supplied records as data and reports actual tool outcomes. HTML tool results are summarized as Markdown or plain text. Simple questions receive direct answers; complex work receives a brief next step and a final account of results and remaining work. Already-requested read-only queries proceed without redundant confirmation, and tools supply available information before asking for missing details that affect the target, scope or result. The assistant identifies the supplied file evidence and relevant extraction or provider limitations, without claiming complete history or access to absent files. These are model instructions; tool authorization and cancellation remain enforced by the execution owner.

### Chat Panel and Completion

The assistant opens in a right-side panel, initially 560 CSS pixels wide. At viewport widths of at least 1200 pixels it shares the application workspace with the business page; its left separator supports pointer and keyboard resizing, bounded to leave space for that page. Narrower screens overlay the business page, and mobile fills the available workspace below the application header. The header can expand the assistant across the workspace or select a draggable floating window. Expanded layouts at least 900 pixels wide show history beside the conversation. Layout changes retain one mounted chat component, message scroll element and composer; they do not reconnect or submit a request. Layout mode, width and floating position are transient preferences.

A hidden active task has a compact button for returning to its conversation. It distinguishes execution, pending confirmation and lost connection, and retains an unread result indicator when that task finishes while hidden. Reopening clears the unread indicator. The button follows existing task events without polling or browser notifications.

`ChatBot.vue` keeps the unsent draft, scroll position and connection in component memory. Suggestions fill the draft without sending. Enter sends; Shift+Enter inserts a newline and composition confirmation never sends. One request remains active until `/ws/chat` emits `{"done": true}` after all reply chunks, a terminal reconnection snapshot, or a terminal error. Losing the browser connection does not end a stored turn. Progress chunks do not enable a second request or expose completion actions. An empty completed stream produces a visible failure message.

Changing internal pages or hiding the panel retains its draft and connection. New conversation closes the connection and opens an empty composer, preserving the previous saved conversation. Starting a new conversation and changing the selected history are disabled during a reply. Opening the panel after page reload restores the most recently updated conversation; the history view lets the user continue or delete a selected conversation, or clear the current profile's history after confirmation. Failed history loading blocks sending until a successful retry. Component disposal closes the socket and clears its connection and reconnection timers. Reconnection observes the accepted request without sending another question; a new question is accepted only after the observed turn ends.

Messages and model-driven tool writes follow [Selected Configuration Isolation](config-profiles.md#atomic-activation). The frontend sends its loaded configuration generation with every message and history request; the backend validates that generation before accessing history or dispatching the model and keeps profile activation unavailable during the operation. Idle connections allow profile switching; a stale request requires a page refresh. Drafts, panel position and follow-up action markers remain transient and are not saved into configuration.

<a id="persistent-conversation-history"></a>
### Persistent Conversation History

The instance stores conversations and bounded execution records in `@app/ai-history.sqlite3`, outside configuration archives and runtime snapshots. Stable profile identifiers own the records: switching back to a profile restores its own history, while new or imported profiles have separate histories. History is not copied by profile inheritance or configuration export. Deleted profiles' history becomes inaccessible and remains subject to instance retention; this feature does not add cross-profile browsing.

Authenticated `GET /ai/conversations` lists the active profile's conversations, and `GET /ai/conversations/<id>` returns its retained turns. The same paths accept `DELETE` for clearing that profile or deleting one conversation. GET and HEAD representations and both DELETE operations require the existing Web UI token before storage access, plus the running instance's assistant authorization and the current configuration generation. A missing or foreign conversation is rejected, never replaced by an implicit new conversation. History reads have no model or tool side effects. SQL failures produce an unavailable result rather than resetting history.

A WebSocket message containing `conversation_id: null` creates a conversation on the first question; subsequent messages carry the acknowledged identifier. The server commits the user's question before invoking the model and emits the identifier before reply chunks. It accumulates the final answer separately from tool progress, including embedded missed-order state, and saves it before emitting completion. Clients without the new field retain socket-local context, with the complete streamed reply now retained. Restoring stored text does not load graph checkpoints, provider response identifiers or tool calls.

A persisted turn starts as interrupted and becomes complete only after the stream finishes successfully. A model error or oversized reply preserves available text as interrupted; browser disconnection alone does not terminate execution. A process crash can lose partial output, but its previously committed question remains interrupted on restart. Opening that history never retries the request. The UI warns that some operations may already have happened; deleting history does not undo tool effects. One process admits only one active turn per conversation and rejects deletion or clearing that includes an active conversation. Another browser can view saved state and subscribe to the active execution. Separate processes sharing the same instance directory are outside the supported instance model.

Retention keeps the most recently updated 20 conversations per profile and 100 per instance, evicting the oldest inactive records. A request that would evict an active conversation is rejected. Each conversation retains the newest 100 turns within 262,144 characters including tool events, attempted-operation records, continuation notes and failure details; user messages have 4,000 characters and replies have 32,768. Replies exceeding that limit end as interrupted rather than silently truncating a successful answer. The panel also bounds its visible messages to 100 turns and 262,144 characters. SQLite reuses freed pages; deletion does not promise filesystem compaction or removal from external backups.

Model context selects the most recent contiguous suffix of complete retained turns, within half the configured context capacity. The estimate includes the current question, selected attachments and any adopted summary before adding historical turns. Storage still bounds available history to 100 turns and 262,144 characters; a larger model window does not recover evicted records. Selection stops at an interrupted or oversized turn instead of replaying an uncertain request or splitting a turn. Earlier historical text remains viewable even when excluded from context; users may need to restate relevant background. The acknowledgement reports how many retained turns were included and whether selection omitted or truncated records. Users can generate a summary draft without tools, inspect it and explicitly adopt its server-saved text. Summary generation reads at most 48,000 characters from retained turns, marks partial records and includes interrupted outcomes as uncertain evidence. Only a completed summary can be adopted; adoption during an active turn is rejected. The adopted summary has at most 8,000 characters, supplements recent turns after its boundary and is labelled historical background, never current state or fresh operation permission. Users can disable it. No summary is adopted automatically, and no long-term user memory is added.

The [conversation persistence decision](../../.agents/notes/implemented/architecture/2026-11-12-ai-conversation-history.md) records storage ownership and the choice to restore text without resuming execution. Focused checks live in `ai_history_tests.py`, `ai_security_tests.py`, `config_profile_chat_tests.py` and `ChatBot.test.js`.

<a id="turn-context-compaction"></a>
### Turn Context Compaction

The model settings expose context capacity in tokens. DeepSeek uses `ai_deepseek_context_tokens`, defaulting to 1,000,000; local and online custom services share `ai_context_tokens`, defaulting to 256,000. Each accepts integers from 8,192 through 4,000,000. Switching services retains both saved values, and loading older configurations does not persist new defaults. The capacity describes the selected model; changing it does not increase the provider's actual limit.

Stored chat uses an approximate token budget, reserving 20% of capacity for output and estimation differences. Text uses a UTF-8 byte estimate; each native image or file reserves 8,192 tokens. System instructions and tool definitions also count. These estimates do not reproduce a provider tokenizer or establish the actual cost of image or PDF input. Replies and tool arguments retain their separate output and storage limits.

The composer includes a context-usage ring. Hover, keyboard focus or a tap opens its detail: used and remaining percentages, token count, capacity and this turn's compression count. Before the first request it shows capacity and an unavailable-usage notice. The values describe the most recent model input, excluding unsent drafts. Before a response they are explicitly estimated; provider-reported input usage replaces the estimate when available. After compression the next model request updates the indicator with its reduced context. Overflow can show more than 100% used, while the ring and remaining percentage stay bounded.

Transient `context_usage` events travel only through the existing authenticated chat WebSocket, after its token, assistant authorization, profile and generation checks. Events contain counts, estimate status and compression progress, never prompt text. The execution owner's in-memory snapshot retains the latest value for live reconnection. New questions, history selection and new conversations clear the old display; saved history does not invent a historical token count. Display and theme changes initiate no model request or polling.

When accumulated tool records exceed the input budget, the assistant summarizes earlier closed tool exchanges through the same configured provider and protocol, without registering tools. It preserves the original model inputs and continuation requirements, and keeps the newest complete tool exchange verbatim when space permits. The summary replaces only temporary model context: saved evidence, attempted-write records and explicit summary adoption remain unchanged. The summary is labelled uncertain historical data, carries evidence references and omissions, and grants no execution permission. Exact evidence or current state omitted from context requires another read. This works through ordinary model requests; it does not require a provider-specific compaction endpoint. DeepSeek's [Responses compatibility table](https://api-docs.deepseek.com/guides/responses_api/) lists `context_management` as unsupported.

Each compression request reads at most 48,000 source characters, additionally bounded by the configured token estimate, and produces at most 6,000 characters, with a smaller reply limit for small windows. Oversized records retain bounded excerpts with explicit omissions. An empty, oversized, truncated or tool-calling summary fails without replacing context or dispatching further tools. Cancellation and existing provider timeouts also apply. If the original inputs cannot fit, the assistant reports the remaining input limit instead of discarding user requirements or attachments.

A confirmed provider context-length rejection before any streamed output allows one recovery attempt in the turn. Recovery requires eligible earlier records and a smaller replacement; otherwise the provider failure remains visible. Authentication, rate limits, transport errors and other failures do not trigger compaction retries. Stored chat has no fixed model-round or tool-call count limit. It continues until a final response, cancellation or an explicit execution failure; each iteration still checks the context budget and compresses eligible earlier exchanges when needed. Auxiliary compression calls add cost but do not execute tools. Streamed output limits count answer text and argument payload instead of repeated fragment representations. A reported length-truncated model response cannot dispatch its tool calls.

Focused offline checks in `ai_model_protocol_tests.py` exercise real SDK request serialization with simulated DeepSeek, Chat Completions and Responses HTTP streams. `ai_execution_tests.py` covers fragmented arguments, compression failure and stop, preserved evidence, write deduplication and reported token usage; `ai_history_tests.py` covers configured history selection. `configPartial.test.js` verifies independent setting saves and defaults. `ChatBot.test.js` and `ChatContextUsage.test.js` cover usage updates, reconnection, capacity defaults, estimates and percentage bounds. `ai_security_tests.py` verifies the shared chat credential boundary. Live provider tokenizer behavior, summary accuracy and actual API delivery remain unverified.

Replies render Markdown with HTML disabled and omit embedded missed-order state from display and copy. Copy reports clipboard failures. Completed replies offer 打开反馈, which opens the existing feedback form without submitting or attaching the conversation. Dismissing the form leaves this action available. Replies have no manual resolved marker; execution status comes from the stored turn and tool results. Scrolling follows new content only near the bottom and provides an explicit jump to the latest message otherwise. The panel and model settings use existing Mower theme colors. In floating mode, the desktop header supports pointer dragging with capture; header controls do not initiate a drag. CSS clamps the floating position to the viewport when moving or resizing. Its position remains transient across hiding and reopening. Mobile does not initiate dragging. Model configuration remains in Mower settings; the AI navigation entry opens the assistant directly.

<a id="conversation-attachments"></a>
### Conversation Attachments

The shared composer accepts file selection, file drops and clipboard images, with removable filename chips and draft image previews. Its controls use icons and accessible names; summary and continuation-mode actions live in the ellipsis menu. Ordinary text dragging and pasting retain their normal behavior. Uploading stages a file without calling the model. Sending transmits attachment IDs through the existing 64 KiB WebSocket boundary, and a rejected admission restores the files and draft. Unsent files remain transient in the browser; reload does not restore a draft.

Authenticated `POST /ai/attachments` accepts one multipart file, and `DELETE /ai/attachments/<id>` removes an unclaimed staged file. Authenticated `GET /ai/attachments/<id>` (including HEAD) previews a retained attachment. All methods require the existing Web UI token, enabled assistant and current configuration generation before parsing or storage. IDs are bound to the active profile; a chat or preview cannot read another profile’s files. Preview rejects missing or expired staged files and makes no model call. Clicking a draft or sent filename shows the saved text excerpt as escaped text or the normalized image. PDF preview explains original-file input without returning its binary payload. Older preview responses cannot replace a newly selected file. Files are reference data, not instructions or approval to execute their contents. No new runtime dependency is added.

Each upload is at most 2 MiB, and a request carries at most four distinct files including files inherited by continuation and supplied through selected history. Shared attachment IDs count once and are sent once; repeated references do not consume another slot or discard the associated historical question. UTF-8 text is accepted independently of its extension; binary control characters are rejected. PNG, JPEG and WebP are decoded with Pillow, restricted to sixteen million source pixels, reduced to at most 1600 by 1600 pixels and reencoded without metadata as JPEG of at most 512 KiB. PDF is sent as a native model file block. Images and PDF require a model service that supports those inputs in the selected OpenAI protocol; provider rejection is a visible model failure, and upload success does not establish model support.

DOCX body text, PPTX slide text and XLSX cell text and cached values are read with the standard library. They omit images, comments, layout and slide notes; formulas are not evaluated, and cached values can be stale. ZIP inputs read supported UTF-8 text members and explicitly mark omitted members. Archives are never extracted to the filesystem, recursively unpacked or executed. They must be unencrypted, contain at most 256 members and total at most 8 MiB after decompression; Office XML parsing rejects entity and document-type declarations. Text inputs retain the last at most 6000 characters with an explicit omission marker when shortened. Legacy binary Office files, audio, video and other binary formats need conversion; unsupported inputs return an error rather than a filename-only model message.

Normalized payloads live in the existing history database outside configuration export, with separate UTF-8 serialized storage caps of 8 MiB per profile and 32 MiB per instance. Capacity exhaustion rejects the upload without evicting a conversation. Staged files expire after one hour and are removed on subsequent storage access. Accepted turns retain references to the files actually used, including files supplied through prior context, so stopping and continuing can retain them even after source-turn pruning. History exposes metadata without binary payloads. Conversation deletion and retention release unreferenced claimed files; this does not compact SQLite or remove external backups. Summary generation reads extracted text but explicitly omits image and PDF originals. Offline checks in `ai_attachment_tests.py`, `ai_model_protocol_tests.py` and `ChatBot.test.js` exercise admission, ownership, storage, continuation, SDK encoding and composer interactions; they do not establish a live provider’s file support.

<a id="live-conversation-reconnection"></a>

### Live Conversation Reconnection

Stored execution continues after a browser refresh, closed tab or lost connection while the server process remains running. The existing request handler owns execution until it finishes; socket-send failures detach that viewer without cancelling model or tool work. The configuration generation guard remains held for that execution, including pending confirmation. No background service or additional runtime dependency is introduced. Legacy clients without a conversation identifier retain their socket-local behavior.

After the existing first-frame Web UI token check, `/ws/chat` accepts `{resume: true, conversation_id, turn_id?, request_id?, generation}`. Resume requires the running instance's assistant authorization, current configuration generation and active profile ownership before exposing progress. It accepts no new message or tool arguments. A retained request identifier can locate the accepted conversation when the initial acknowledgement was lost; supplied conversation and turn identifiers must match that request. Reconnection stays bound to that turn even if another tab has started a later one. Unknown requests are rejected without redispatch.

The observer receives complete bounded snapshots of the current answer, draft and tool events, replacing its previous display rather than appending replayed text. A terminal snapshot is published after history saving finishes. When execution has already ended, the same request reads its retained history without restarting it. At most eight stored executions per instance and four additional observers per execution are admitted. Observers wait on progress notifications, send a snapshot at least every fifteen seconds to detect disconnected clients, and release their slot on exit. Completed executions leave the registry; no completed-run queue accumulates.

The frontend attempts reconnection three times after a connection failure, with one-, two- and four-second delays, then provides an explicit reconnect action. Closing the component clears those timers. A restored busy conversation attaches to its current execution. While awaiting a fresh snapshot, confirmation buttons remain disabled; repeated confirmation clicks are disabled after the HTTP request succeeds. The displayed approval expiry is an absolute time, and reconnecting does not renew the 180-second confirmation window. Confirmation, rejection and stopping still use the existing authenticated control endpoint.

This reconnects a viewer to an existing execution; it does not recover execution after a process restart. A restart retains SQLite history and attempted-operation records, invalidates pending confirmations and requires an explicit new turn through continuation or retry. In-flight text can still be lost on a process crash. Focused offline checks exercise the WebSocket, HTTP control and SQLite paths in `ai_resume_tests.py`, together with the frontend in `ChatBot.test.js`.

### Continue an Incomplete Task

After the latest chat turn stops or ends incomplete, the user can select “继续处理” or send exactly “继续” or “继续处理”. The client starts a new turn with `continue_of` naming that incomplete turn; it does not resume a suspended model request or tool call. The existing bottom composer owns continuation: after a stopped or incomplete chat turn, its play-icon button submits “继续处理”, identified by its accessible name and tooltip. Ordinary questions use the upward-arrow icon, and the same position shows a square stop control during execution. These controls use the same button dimensions as the attachment and more-actions controls. An empty submission continues without new requirements or a synthetic user-message bubble, including after history restoration. Entered requirements and attachment cards remain visible; requirements clear from the composer after dispatch. “继续” and “继续处理” alone also mean continuation without extra requirements. The ellipsis menu’s “作为新提问” switches the same composer to an ordinary new question, and “继续原任务” switches back; switching preserves the draft. No separate continuation input or chat-message action is added. Summary failures use “重新生成摘要” instead. A completed, older, foreign or busy target is rejected, as is a request combining `continue_of` with `retry_of`. The existing WebSocket token, assistant authorization, configuration generation and profile ownership checks apply before model dispatch.

The server inherits the original goal and attempted-operation journal, adds saved tool evidence and unfinished text as explicitly uncertain historical data, and asks the model to identify completed, uncertain and remaining work. No additional model request creates a continuation summary. Mutable state may need a fresh read. Matching writes already attempted, including uncertain outcomes, remain blocked by the execution owner; previously unexecuted writes need a fresh preview and confirmation. Confirmation identities from ended turns never carry over. This guarantee covers matching normalized operations in the retained continuation chain, not semantically equivalent writes with changed arguments or independent conversations.

Each continuation stores cumulative notes and additional user requirements in a record of at most 16,000 serialized characters in the same SQLite turn. At most 4,000 characters of the preceding unfinished answer enter a record; its combined saved evidence and draft are capped at 10,000 characters. Older notes are removed as needed, and the acknowledgement tells the UI when records are truncated. The model separately receives bounded excerpts of the retained write journal, while the execution owner keeps the full journal for matching. These notes count toward conversation retention and survive reopening storage even if their source turns have been pruned. Repeated continuation preserves the original goal; retrying a continued turn preserves its continuation context. Ordinary new questions retain the complete-turn context rule above. History restoration shows which turns were continuations without starting execution.

`continue_instruction` is an optional string of at most 4,000 characters and is accepted only with `continue_of`. Requirements accumulate in order, separately from untrusted tool evidence; later user requirements may change earlier requirements or the original goal but never authorize a write. The server passes them to the model as user instructions, retains them through retries and source-turn pruning, and includes them in later complete-turn context and summary input. Their serialized list is limited to 8,000 characters; exceeding that limit rejects the request before inserting a turn instead of silently dropping older restrictions. Progress notes use the remaining continuation capacity and may be truncated. History exposes the requirement submitted for each continuation.

User stops retain `cancelled` status and display “已停止” without error styling, including when a blocked provider read later times out after the stop was accepted. Other failed turns remain `interrupted`. Controlled model streaming distinguishes provider timeout, provider connection failure and other model-call failure; errors outside that provider call use a general execution failure. The server saves a bounded failure message of at most 2,000 characters and its category, returning the same distinction through terminal WebSocket frames, live snapshots and saved history. A process crash or older record without saved failure details remains an interruption with unknown cause. Browser connection loss remains a separate observer state and does not imply that execution stopped.

The existing [execution decision](../../.agents/notes/implemented/architecture/2026-11-12-ai-execution-confirmation.md) owns this extension. Focused continuation checks use the real stored-chat, HTTP control and SQLite paths in `ai_execution_tests.py`, together with `ChatBot.test.js`.

<a id="confirmed-tool-execution"></a>

### Confirmed Tool Execution and Evidence

Stored chat uses `agent/execution.py` to classify every registered tool as read-only or requiring confirmation. Unknown classifications are not executed. Adding a mastery plan, replacing a profession route, resetting failed plans and sending feedback all require a concrete preview and a fresh confirmation. The server binds confirmation to the current profile, conversation, turn, one-use nonce and normalized arguments; the client cannot change those arguments. Confirmation expires after 180 seconds. Legacy graph and manual chat calls without an execution owner reject writes.

`POST /ai/conversations/<id>/turns/<turn_id>/control` accepts approve, reject or stop. `POST /ai/conversations/<id>/summary` adopts a completed summary turn or clears the current summary. Both require the Web UI token before storage access, the running assistant authorization and the current configuration generation. A closed turn, stale confirmation or different profile cannot authorize execution. Control bodies are limited to 4096 bytes. Profile activation remains blocked while a chat request owns that profile.

The preview identifies the requested operator and skill, before/after profession route, exact failed-plan list, or feedback content, recipients and attachment scope. Route replacement and failed-plan reset compare the previewed state and write/read back in one transaction; changed state requires another confirmation. Failed-plan reset compares the complete plan snapshots, including target level, skill, failure reason and stored support settings, rather than only plan identifiers. Display names use the same normalization at preview and comparison without writing during comparison. Added mastery plans are read back before reporting verified. Email success means the mail service accepted sending, not that the recipients received it. Failed or uncertain operations remain distinguishable from verified writes.

The server saves an attempted-operation record before invoking a write. A unique request identifier prevents redispatch while that request remains retained. Explicit retry accepts only the latest incomplete turn, uses its original input and carries its operation records forward. Matching attempted, successful, failed or uncertain writes are not repeated; operations previously not executed may be proposed again. This is not exactly-once delivery across independent conversations or new requests. Deleting history cannot undo effects or preserve deduplication for deleted requests.

Stop wakes a pending confirmation and prevents subsequent model and tool dispatch. It cannot undo a started operation or immediately interrupt a blocked provider read; the next chunk or existing timeout releases that call. Results of an already-started operation are recorded before stopping. A crash leaves the committed attempt uncertain, so retry does not repeat it. Opening history does not dispatch model or tool calls. Reattaching to a live turn restores its pending confirmation with the original identity and deadline; confirmations from terminated runs remain invalid.

Model rounds and tool calls have no fixed count limit. Each run retains at most twelve write records; exhaustion of that write journal still prevents additional writes. Context capacity, per-request timeouts, cancellation and write confirmation remain enforced. Structured tool events include an evidence identifier, normalized arguments, observation time, source and outcome. The panel keeps those events separate from streamed drafts and final answers. Events and write records share a 65,536-character per-turn bound; older event previews may be omitted. Visible results are limited to 3000 characters and explicitly indicate truncation. General tool arguments and model-facing results are limited to 8000 and 32,000 characters respectively. Complete `try_riic_plan` documents allow 64,000 argument characters; their history events keep a marked 8000-character excerpt while execution receives the full arguments. `get_riic_context` and `try_riic_plan` results allow 96,000 and 128,000 characters respectively and return a structured error when oversized instead of truncated JSON. Other tool limits and the per-turn event bound remain unchanged; dedicated missed-order processing retains its existing structured result bounds. The normal conversation includes only final answers in later context; evidence is viewable from history, and fresh state requires another read. Citations guide model output but do not verify its semantic claims.

`call_db` uses a read-only connection and an authorizer allowing reads only from `log`, `agent_action` and `trading_history`. It rejects mutations, database attachments and file/extension functions without creating a missing database. Queries have a two-second progress deadline, 100-row result cap, 64-column cap, 8000-character SQL limit and 1 MiB SQLite value limit. Displayed cells are escaped and bounded.

The [execution confirmation decision](../../.agents/notes/implemented/architecture/2026-11-12-ai-execution-confirmation.md) explains the durable attempt record and cooperative stop. Focused offline checks use `ai_execution_tests.py`, `ai_model_protocol_tests.py`, `feedback_inspection_tests.py` and `ChatBot.test.js`.

### Managed Assistant Authorization

`ai_assistant_enabled` in each instance's `config/conf.yml` records the manager's explicit choice for assistant chat. An absent or null value leaves that choice unset. Standalone launches always permit assistant chat, including when the saved value is false, and expose no switch. A launch with `MOWER_MANAGED=1` permits chat only when the saved value is true; an unset choice defaults to disabled. This rule controls conversation requests only, not model-provider settings, diagnostic analysis, navigation or captcha handling.

The server fixes the effective authorization when the process starts and returns it as `ai_assistant_enabled` in `/status`; subsequent configuration loads do not hot-switch the running process. Ordinary `/conf` submissions may echo the unchanged saved choice but cannot alter it. File edits or configuration restoration take effect at the next launch. The local desktop manager uses the existing stopped-process configuration guard, not automation status, and edits the switch in the same instance settings dialog as Token and port. An instance Web UI token does not grant [global manager access](web-access.md#browser-instance-management) or permission to change another instance's assistant choice. Writes preserve unrelated YAML fields and the last saved choice across manager recreation or abnormal termination.

Turning the switch on immediately opens a separate risk dialog while leaving the draft off.
