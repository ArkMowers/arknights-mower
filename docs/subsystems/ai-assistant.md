The standalone guide follows the system color preference unless a valid `theme=light` or `theme=dark` query selects an explicit theme. `Doc.vue` supplies the initial Mower theme, then sends the effective theme colors after iframe loading and on theme or palette changes using messages restricted to the same origin. The guide accepts only its parent's same-origin messages with valid theme values, applies an allowlist of CSS color tokens, and ignores invalid colors and unrelated properties. Theme-only messages clear prior color overrides and use the standalone defaults. Theme changes do not reload the iframe or reset its reading position. The page uses Mower's body and card backgrounds without a gradient; callouts share neutral control backgrounds and symmetric spacing. Scheduling tutorials explain current [base scheduling rules](base-scheduler.md) and [editor operations](plan-editor.md) through examples, including dormitory bindings, fixed and dynamic recovery positions, multiple bindings and backup inheritance.

`ask_llm` handles missed-order intent through its dedicated confirmation and target-selection flow before model dispatch. For requests reaching the model, instructions route general usage questions to FAQ and explicit record queries, missed-order analysis, mastery operations and feedback requests to their corresponding tools. FAQ matching supplies candidate advice rather than confirmed causes. Stack extraction requires existing stack text; source reading requires a valid path and positive line number and retains the [source allowlist boundary](web-access.md).

### Chat Panel and Completion

`ChatBot.vue` keeps messages, the unsent draft, scroll position and the connection in component memory. Suggestions fill the draft without sending. Enter sends; Shift+Enter inserts a newline and composition confirmation never sends. One request remains active until `/ws/chat` emits `{"done": true}` after all reply chunks, or an error or connection failure ends the turn. Progress chunks do not enable a second request or expose completion actions. An empty completed stream produces a visible failure message. Existing clients can ignore the additive completion frame.

Hiding the panel retains the draft and current connection. Starting a new conversation closes the connection and clears the visible history, which also resets server-side context. New-conversation actions are disabled during a reply. Component disposal closes the socket and clears the bounded connection timer. Reconnection after an interrupted reply starts fresh server context and the failure message requests the necessary background again. These states reuse [transient-state isolation](../../CODING_STANDARDS.md#1-core-invariants); they are not saved into configuration.

Messages and model-driven tool writes follow [Selected Configuration Isolation](config-profiles.md#atomic-activation). The frontend sends its loaded configuration generation with every message; the backend checks that generation before dispatch and keeps profile activation unavailable for the active message. Idle connections remain available for profile switching, and a stale message requires a page refresh before another conversation.

Replies render Markdown with HTML disabled and omit embedded missed-order state from display and copy. Copy reports clipboard failures. Completed replies expose resolved/feedback actions; feedback opens the existing modal without sending. Scrolling follows new content only near the bottom and provides an explicit jump to the latest message otherwise. The panel and model settings use existing Mower theme colors. The desktop panel is at most 440 by 560 pixels and its header supports pointer dragging with capture; header controls do not initiate a drag. CSS clamps its position to the viewport when moving or resizing. Its position remains transient across hiding and reopening. Narrow screens use a full-height panel without dragging. Model configuration remains in Mower settings; the AI navigation entry opens the assistant directly.

### Managed Assistant Authorization

`ai_assistant_enabled` in each instance's `config/conf.yml` records the manager's explicit choice for assistant chat. An absent or null value leaves that choice unset. Standalone launches always permit assistant chat, including when the saved value is false, and expose no switch. A launch with `MOWER_MANAGED=1` permits chat only when the saved value is true; an unset choice defaults to disabled. This rule controls conversation requests only, not model-provider settings, diagnostic analysis, navigation or captcha handling.

The server fixes the effective authorization when the process starts and returns it as `ai_assistant_enabled` in `/status`; subsequent configuration loads do not hot-switch the running process. Ordinary `/conf` submissions may echo the unchanged saved choice but cannot alter it. File edits or configuration restoration take effect at the next launch. The local desktop manager uses the existing stopped-process configuration guard, not automation status, and edits the switch in the same instance settings dialog as Token and port. An instance Web UI token does not grant [global manager access](web-access.md#browser-instance-management) or permission to change another instance's assistant choice. Writes preserve unrelated YAML fields and the last saved choice across manager recreation or abnormal termination.

Turning the switch on immediately opens a separate risk dialog while leaving the draft off. Its confirmation requires acknowledgement and at least five seconds measured with a monotonic clock after rendering, then enables only the draft. Turning the switch off changes the draft without a reading dialog. Neither gesture writes configuration: Save commits Token, port and the changed switch together without another risk dialog. Cancelling the reading dialog leaves the switch off and retains other drafts; cancelling instance settings discards all drafts. Failed writes retain the previous saved data. Each attempt to turn the switch on starts a fresh reading interval. A state refresh cancels confirmation when the instance becomes non-editable, its row changes or its saved authorization changes. Closing the manager clears the temporary confirmation and its timer without saving. The notice explains model-service data transfer, possible disclosure of sensitive information across instances, model-call costs and supported configuration operations; it does not claim that multiple instances provide a security isolation boundary.

The existing assistant entry remains visible. A disabled instance displays “管理员未开启” with “当前实例暂未开启该功能，请联系管理员。” without creating a chat WebSocket. An unknown status blocks sending until authorization is available, without reporting an administrator refusal. The backend retains credential checks and rejects disabled chat with `code=ai_assistant_disabled`, then closes with code 4403 before reading a user message or dispatching the model. The frontend also handles this refusal after a backend restart. Provider configuration and unrelated AI consumers retain their existing behavior.

If a status refresh reports disabled authorization during connection or a reply, the frontend ends the active turn before closing the socket, clears its loading state and connection timer, and retains any partial reply with a failure indication. This cleanup also applies while the panel is hidden; only a visible panel displays the refusal dialog. A later enabled status permits a new request and a new conversation without reloading the page. Single-instance saves follow the [captured-target and opening-choice rules](web-access.md#7-desktop-instance-manager), so unrelated connection edits do not restore an externally changed authorization or apply a confirmed choice to a replacement instance.

The [manager-owned assistant decision](../../.agents/notes/implemented/feature/2026-10-13-managed-ai-assistant-switch.md) explains the scope and stopped-instance choice. Focused offline checks use `managed_ai_assistant_tests.py`, `manager_instance_controls_tests.py` and the `WebSocketSecurityTests` class in `ai_security_tests.py`; frontend checks use `manager/MowerManager.test.js`, `src/components/ChatBot.test.js` and `src/stores/mower.test.js` from `ui/`.

The batch table reuses this risk notice once for the captured instance list: the first attempt to enable an individual AI cell or use All On requires five seconds and acknowledgement. Confirmation enables only the requested draft cell or rows; subsequent AI edits in that same table session share the acknowledgement. All Off requires no reading notice. Save Changes submits only edited cells for eligible stopped instances. The [batch settings rules](web-access.md#batch-instance-settings) define target validation, partial field updates and per-instance failure results; running instances remain unchanged. Cancelling or reopening the batch editor discards its temporary acknowledgement and requires a fresh notice before enabling.

## 2. Tool Argument Contract

Database examples use the schema in `solvers.record._DB_TABLE_STMTS`, explicit ordering and bounded SELECT results. `agent_current_room` records the previous position; `current_room` records the updated position. Unix-second timestamps are converted with SQLite local-time expressions. The published instructions do not depend on an unregistered time-conversion tool.

Mastery status filters use `idle`, `arranging`, `training`, `waiting_collect`, `completed` and `failed`. Retry resets all failed plans; its compatibility arguments do not filter the affected records. Instructions require clarification of batch scope when the user requests a single retry. Route saving replaces the selected profession's route.

Feedback sends email through `submit_issue`. Instructions require an explicit sending request and describe Bug start/end arguments as local `YYYY-MM-DD HH:MM:SS` strings. They request a positive interval of at most fifteen minutes before invocation. The feedback tool also validates this interval at runtime. Instructions do not implement runtime SQL restrictions or a mutation authorization gate.

Bug-report instructions preserve the user's observations and expected behavior, then separate reproduction conditions, queried evidence with times, AI inferences and unconfirmed details. Missing optional information remains unknown rather than causing repeated confirmation requests. Task names, queue snapshots and task creation are not treated as proof of completed execution; missing later records are not treated as proof that execution never happened. The selected interval covers the known trigger and subsequent handling, and limited chat queries do not substitute for attached source evidence. These are model instructions, not a runtime guarantee that the model follows them.

`/submit_feedback` and the assistant use the same email tool, sending feedback to `354013233@qq.com` and `1273725854@qq.com` through an explicit recipient list. A successful email send returns `邮件发送成功！`, which the feedback component recognizes before showing its success notice and copying the description. Tencent sheet writes are not part of submission.

### Bounded Feedback Evidence

Each Bug email sends exactly one `feedback-YYYYMMDD-HHMMSS-<problem>.zip` attachment. The timestamp uses the selected interval's start; the problem summary uses the first nonempty description line after version and platform metadata. Unsafe filename characters and control characters are removed, and the summary is limited to 40 characters. The bundle follows the [diagnostic export layout](web-access.md#diagnostic-export-contents): `runtime.log`, `screenshots/`, mandatory current `plan.json` and `readme.txt`. Feedback adds the quick preview `runtime.txt`, `context.json` and `evidence.json`. The interval log is copied into the outer bundle without nesting another ZIP. Screenshot bytes are stored directly, and evidence references point to the actual bundle members. The email body identifies the bundle and its contents. Feature feedback does not create a bundle.

Bug feedback through the assistant and `/submit_feedback` attaches a log excerpt and selected screenshots from the same local start/end interval. `submit_issue` accepts optional `screenshot_times`: at most four local datetime strings inside that interval. The assistant supplies these only when the user's description or queried records establish relevant moments. An empty list disables screenshot attachments. Without this argument, different ERROR/CRITICAL messages take priority over WARNING messages; repeated messages with differing numbers share a selection slot. Each moment uses the last capture in the same second or up to thirty seconds earlier. These are temporal associations, not visual diagnoses; unrelated errors can still be selected. No arbitrary screenshot is attached when there is no matching observation.

Selection reuses the log schedule's timestamp lookup and includes retained error-archive screenshots and saved logs after ordinary history expires. Automatic selection supplements the tail preview with up to 256 anchors from the streamed interval, retaining at most two initial occurrences for each of 128 distinct error or warning signatures. Signatures normalize digits in the first 500 message characters. Combined candidates prioritize errors over warnings and then time, so an early failure outside the tail preview can still supply a screenshot. It keeps at most four distinct image byte sequences, each at most 512 KiB and at most 2 MiB combined. Missing, oversized, duplicate and unreadable screenshots are omitted without blocking the log report. The first readable matching frame per error is preferred. The selected original JPEG bytes are copied into a temporary workspace; no capture, image re-encoding or complete screenshot archive is requested.

The selected interval streams from the existing hourly runtime files in original file order, retaining repeated records, long messages and multiline tracebacks. Collection uses a bounded temporary log archive, then copies its contents to `runtime.log` in the final bundle. Reads are at most 64 KiB each. The log has a 3 MiB compressed budget and a 64 MiB uncompressed budget; reaching either budget stops collection and marks the log as truncated. Retained error-archive excerpts are appended when available and explicitly marked as a limited source that may overlap ordinary logs. Missing or unreadable source files cannot establish complete historical coverage. The separate `runtime.txt` remains a quick preview with at most the latest 1000 selected records, 1000 characters per record and 256 KiB total; its limits do not truncate the interval log.

`evidence.json` records the requested interval, actual first and last archived record times, record count, compressed and uncompressed sizes, completed-scan and truncation flags, limited archive sources and unreadable filenames. It separately records preview coverage. Screenshot entries include the associated log or requested time, capture time with UTC offset and signed capture-time difference; these remain temporal associations. The body states the actual screenshot count, requested interval with UTC offsets and compressed-log coverage or omissions, without claiming continuous coverage between records. A missing log interval prevents sending.

Bug feedback also queries the existing SQLite database through a read-only URI and `query_only`, using fixed parameterized queries. `task_history.jsonl` preserves the selected interval's `log` time, task, level and full message; `operator_history.jsonl` preserves the available allowlisted `agent_action` fields, including mood, previous and updated rooms, related operator, context and slot. Original timestamps and fractional seconds are retained. Both queries include the final selected second, matching the file-log selection. No full database, other tables, saved-state BLOB or general configuration is exported.

Each table has a 5000-record, 1 MiB and two-second query budget, including bounded lock waiting. `evidence.json.database_records` records these limits and each table's actual count, first and last timestamps, bytes, truncation, missing legacy columns, scan result and failure reason. Missing or locked databases, unavailable tables and interrupted queries do not prevent sending the other retained evidence and do not create or migrate a database. The body distinguishes unavailable, empty and partial exports. A completed scan or empty query does not establish complete historical coverage. Feature feedback does not read these records.

Bug feedback also includes `context.json` containing the installed version and available revision, operating system, architecture, Python version, Android marker, timezone-aware generation and problem times, and the right-side room order. `plan.json` uses the existing Scheduling Plan export and its allowlisted advanced settings. A successful Bug email always includes the complete current plan, including one exceeding 256 KiB; if the complete encoded email exceeds its size limit, sending fails instead of dropping the plan. These are the current configuration when feedback is generated, not a historical or effective-backup snapshot. No full general configuration, credentials, hostname, username or device paths are collected for these context attachments. The Bug message supplies a timezone-aware `Date` header. Feature feedback keeps its existing description-only behavior.

The complete MIME message must fit within 8 MiB, including attachment encoding and the description; an oversized message returns an explicit unsent result. SMTP providers may impose lower limits. Temporary attachments are removed after success or failure; existing history remains available under its normal retention policy. The successful response remains `邮件发送成功！` for the feedback form.

Focused offline verification uses `issue_evidence_tests.py`, `feedback_context_tests.py`, `feedback_records_tests.py` and `ai_prompt_contract_tests.py`; the AI tool-loop test dispatches the real feedback function against an isolated database and captures the resulting MIME ZIP, while replacing the model and SMTP transport. Actual SMTP delivery and model compliance are not exercised.

## 4. RIIC Tools

`get_riic_context` reads the saved BOX and primary Scheduling Plan, returns owned operator names and growth, configured facility capacity and current assignments, and joins the curated base combinations with owned, missing and unknown members. Combination membership alone does not establish skill eligibility or simultaneous placement. Full credentials, configuration and backup trigger expressions are excluded.

`get_riic_knowledge` queries at most twelve formal operator names and one fixed mechanics topic. It reads the shared catalog and term resource, expands nested term references, and selects the highest unlocked version of each independent skill slot. All catalog skill stages remain visible with their status, including when BOX data is absent. Missing or unowned operators never receive assumed maximum skills. External mechanics provenance and resource coverage remain separate.

`try_riic_plan` accepts at most twenty-four room assignments, overlays a detached primary-plan copy, and validates all primary occupants including preserved rooms. Capacity follows the configured number of positions within the facility's physical maximum; no facility or position is created. Modified rooms clear their old group and replacement bindings. Missing occupants and occupants without a matching facility skill produce warnings; facility skills that exist but remain locked produce errors. The response contains the draft, structured errors, warnings and unchecked conditions. `valid` means primary staffing checks passed; it does not assert a complete, executable or optimal Scheduling Plan. Nothing is saved.

All three tools accept at most sixty-four explicit `roster_overrides` containing a formal name, ownership and optional elite phase and level. Overrides take precedence in that call, report `source=user`, and never update BOX. The AI uses them only for roster facts explicitly stated by the user. An ownership override without complete growth keeps growth unknown.

## 5. Mechanics Boundary

The compact guide adapts the fixed external mechanics skill and retains its version and freshness result. Duplicate full skill catalogs, term exports, HTML browser assets and Node query scripts are omitted. The shared catalog adds only the three absent operators from the fixed snapshot; installed resource records take precedence as soon as they contain those operators. Supplemental character IDs resolve BOX ownership when the general operator map predates them. The frontend and AI read the same twenty curated combination definitions. Runtime skills and nested terms use Mower resources; their coverage can differ from the external guide. Unknown operators and missing terms are explicit. Trials do not calculate global interactions, power, current Operator Mood, Dormitory Recovery, replacement matching, backup activation, Drone Acceleration or long-term yield. Primary staffing success never establishes those properties.

The existing `/ws/chat` credential and model configuration boundaries apply. Both model workflows register the same tools. Tool output is reference data, not instructions.
