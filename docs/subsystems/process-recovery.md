# Main Instance Process Recovery

## Ownership and Launch

**Owned Process Recovery**: Windows desktop instances have an independent supervisor with exclusive configuration-space ownership. Unexpected exits and sustained HTTP unavailability receive continuing recovery attempts with bounded delays. Intentional exits and active update or process-control jobs prohibit recovery by the old supervisor. Saved tasks resume automatically through fresh observations, successful checkpointing and existing solver recovery. Explicit task stopping takes priority; uncertain input coordinates are never replayed.

The source and frozen Windows entry points separate worker invocations from instance supervision before GUI, configuration, Flask or native image imports. Source launches inherit an attached launcher console so `python webview_ui.py` keeps instance logs in the invoking terminal. Frozen launches and source launches without an attached console keep the instance console hidden. A supervisor holds its instance lock throughout the owned child lifetime and backoff; the child holds a separate lifetime lock. Both locks live under the resolved configuration data directory, so different installations opening the same configuration share ownership. A new explicit launcher waits at most fifteen seconds for the supervisor lock and rejects a surviving child. Supervisor termination therefore cannot authorize a second instance while its child survives. The multi-instance manager launches this same entry; its own closure does not abandon a surviving instance.

Windows launches the child suspended, assigns it to an owned Job and resumes it. A registered leaf PID is accepted only after Job membership is verified; the retained handle distinguishes that child from a reused or foreign PID. Wrapper termination alone does not end supervision while the registered leaf remains alive. The Job has no kill-on-close policy because simulator and shared ADB processes keep their own lifecycles. Desktop splash, tray and window helpers use the existing parent watcher, so a main-process exit also closes those helpers. Helper cleanup depends on that watcher obtaining the GIL. Update and explicit replacement workers wait within their existing shutdown budget for supervisor ownership to be released before installation or relaunch. A confirmed normal closure whose intent report cannot be written finishes resource shutdown and exits with the dedicated intent code; an unmarked native exit, including zero, remains unexpected. Internal device failures preserve task-run intent and do not become intentional user closure.

Startup has a 120-second readiness budget. Process creation failure, an unready child and an established-instance failure all enter recovery. Failures within a fifteen-minute window select 2, 5 and 15 second initial delays, followed by 60, 120 and at most 300 second cooldowns; reaching the initial retry count does not end supervision. Each ready child receives an independent direct loopback HTTP probe every ten seconds, with a three-second request budget. Continuous HTTP unavailability for 120 seconds recycles only the verified owned main process. Active installation, intentional closure and a pending shutdown request suppress this recycling and relaunch. Healthy HTTP during a long task wait does not trigger a restart. These checks establish process and service availability, not progress of every automation task.

Task-run intent uses a generation-specific named shared mapping before its JSON report is written. This preserves Stop across report-write failure and native exit. An uninitialized intent remains unknown until the child's actual startup configuration determines it; startup failure alone does not authorize or suppress task execution. Initial readiness and internal automatic starts respect a previously published Stop. An accepted ordinary Start renews run intent. Explicit user shutdown and replacement jobs terminate the old recovery owner.

The supervisor receives console Ctrl+C while its child uses a separate Windows process group and retains inherited console output. The first interrupt cancels recovery, publishes stopped task intent and requests the child's existing cooperative shutdown. A subsequent interrupt or the 60-second shutdown deadline permits termination of only the launched process and its registered, Job-verified main process. The signal handler records flags without I/O or locks and remains installed through ownership-lock acquisition and release, so repeated interrupts cannot abort cleanup. A launcher waiting for ownership can cancel without stopping the existing owner.

<a id="shared-ocr-service-boundary"></a>
**Shared OCR Service Boundary**: The on-demand shared OCR coordinator and its model worker are outside the ownership boundary of a main instance, its launcher and its supervisor. The instance that starts the service only reaps the launched process's exit status and must not register `close_process` (or another own-child termination) for the shared service. Only the registered software-update shutdown path stops it. Instance supervision and recovery cover only the processes launched and supervised for that instance, not the shared service. Closing the manager or the launching instance leaves the service available to other instances sharing the installation, data root and network namespace. [Independent Shared OCR](recognition.md#independent-shared-ocr) owns admission, request budgets, service lifetime and failure behavior; [Shared OCR Update Lifecycle](software-update.md#shared-ocr-update-lifecycle) owns update shutdown.

This boundary is the explicit exception to [Guaranteed Compensation](../../CODING_STANDARDS.md#3-concurrency--resource-lifecycle). The coordinator compensates its own worker as described by [Independent Shared OCR](recognition.md#independent-shared-ocr).

## Dispatch Recovery

An unexpected exit creates a recovery notice outside user configuration. A persistent controller also activates that notice when an ordinary Python automation worker fails; it remains available for later failures after an episode resolves. Automatic recovery uses the existing saved-state start mode and SQLite task snapshot. Recovery attempts wait 2, 5, 15, 60 and at most 300 seconds after failures, continuing while task-run intent remains active. A completed episode resets the retry sequence. Ordinary Stop cancels further dispatch attempts, including internal update-resume starts; the existing ordinary Start control can resume them explicitly.

An explicit Start retains its selected mode during recovery: mode `0` restores the saved state and queue, mode `1` restores state with an empty queue, and mode `2` does not deserialize the old snapshot and starts from fresh observations. The selected mode remains in the recovery notice during failed observation or startup attempts, so automatic retry does not revert a requested reset to loading a corrupt snapshot. All three modes retain the observation and checkpoint boundary. The old SQLite snapshot remains intact until a successful new checkpoint replaces it. A cache-reset start accepted before any failure records its pending observation separately in the recovery notice. Stop, a later ordinary Start, worker failure and process exit retain mode `2` until fresh facility observations have been checkpointed; they cannot reload the pre-reset tasks, replacement reservations or recovery relationships. A successful initial reset clears that pending observation; later independent failures after a reset or recovery use ordinary saved-state recovery.

`GET /crash-recovery/status` exposes `active`, `phase`, `message`, `automatic`, `attempt` and `next_retry_at`. The phases are `waiting`, `observing`, `resolved` and `stopped`. The UI displays this progress and can refresh it; recovery requires no separate acknowledgement or task-result disposition API.

Every saved task remains available to its existing high-level solver. Before recovered dispatch, cached operator positions and dorm occupancy become unverified and the Capture Frame and scene are invalidated. The scheduler observes every effective-plan facility and every supported compensation room, including actual training-room state. Ambiguous occupied slots, invalid mood, unavailable compensation-room layout, cancellation and checkpoint failure retain the notice and pending tasks for a later attempt. A successful fresh checkpoint precedes clearing the notice and returning to dispatch. A later uncertain input within a surviving process rebuilds its owned DeviceSession, refreshes observations and checkpoints before solver reentry; it does not reuse the original touch callback or a previous fault's observation cutoff.

Due dynamic trade-order tasks are replanned from the observed order state through the existing `REFRESH_TIME` task when no original roster needs restoration. A saved original roster retains immediate restoration before another order run. Due Fiammetta charging tasks use freshly observed mood and dorm recovery time; saved original-roster compensation remains immediate. An unknown recovery deadline retains the unfinished charging task and its timestamp without a speculative timer; related observations or arrangements must change and a valid measured full-mood reading must confirm Fiammetta's readiness before charging resumes. Tasks retained after execution failure, including reopened tasks, keep their original objects, remaining work, times and reservations under [Runtime Task Failure](base-scheduler.md#211-runtime-task-failure). Return-phase tasks and future explicit appointments retain their payloads and times. Other task solvers retain their existing scene checks and recovery behavior rather than receiving a second execution engine.

Potentially stale Workshop inventory is invalidated through the existing inventory record helper. Recovery requests one existing depot observation; unresolved required counts keep crafting disabled through the existing batch limit until a later inventory observation confirms them. An unsuccessful scan creates no polling tasks, and existing saved tasks and appointments remain queued. Other scheduling continues. This does not establish instantaneous cloud inventory freshness or exactly-once processing. The saved queue is not a complete action journal and cannot reconstruct an original roster stored only on an interrupted Python stack.

A saved SQLite row must deserialize to the required running-state structure. An unreadable, empty or incomplete existing row preserves the original data and retries recovery; only absence of a row selects fresh initialization with the same observation boundary. An unreadable recovery notice is preserved rather than silently rewritten into dispatch permission. A failed partial restore does not overwrite the only saved snapshot. Normal Stop remains effective when its durable status report cannot be written. Confirmed configuration errors retain existing validation behavior.

Existing [device recovery](device-control.md) owns faults inside a surviving process, while [base scheduling](base-scheduler.md) owns task preservation and actual occupancy.
